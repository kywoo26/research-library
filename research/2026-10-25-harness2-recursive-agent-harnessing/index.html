Harness² 가 모델 가중치를 고정한 채 agent 성능을 올리는 방식

Harness² 는 모델은 그대로 두고 주위의 프롬프트, skill, script 같은 harness 파일을 과제마다 고쳐 쓰는 방법이다. 고친 harness 로 같은 과제를 다시 돌려 보고, 행동 차이를 근거로 편집을 고른다. 논문을 읽은 이 글의 판단으로는 원래 harness 대비 향상은 12개 조건 모두에서 측정됐지만, 다른 기법보다 낫다는 주장과 개선하는 법을 배운다는 주장은 근거가 얇다. 가져갈 것은 재실행으로 편집을 고르는 고리이고, 과제를 안전하게 다시 돌릴 수 있어야 쓸 수 있다.

논문은 Harness² 가 compute 대비 향상의 Pareto frontier 에 있다고 보고한다. 다만 원래 harness 와 견주면 k=1 에서도 토큰을 JobBench 에서 약 5배, WorkBuddy 에서 약 8배 더 쓰고 얻은 향상이라, 도입 비용은 과제당 토큰으로 따져야 한다.

재실행할 수 없거나 후보가 같이 틀리면 원리가 멈춘다

논문이 보여 주지 않은 상황은 원리가 기대는 조건으로 예측한다. 아래 예측은 논문 수치와 코드에서 끌어낸 추론이고, 논문이 직접 시험한 것은 아니다.

  • 되돌릴 수 없는 작업메일 발송이나 결제처럼 실행이 바깥을 바꾸는 과제는 4k 번 다시 돌릴 수 없다. 논문의 세 benchmark 는 모두 매번 새 container 나 문서 사본에서 다시 돌릴 수 있는 과제다.
  • 편집 모델도 모르는 지식이 필요한 실패분야 지식은 편집 모델이 skill 로 적어 줄 수 있을 때만 메워진다. 절차 실패와 지식 실패를 나눠 잰 결과는 논문에 없어서, 지식이 모자라 틀리는 과제의 향상 폭은 예측할 근거가 약하다.
  • 모델이 강할 때향상이 준다는 경향은 일관되지 않다. 같은 모델로 편집한 실험에서 Opus 5 는 WorkBuddy +3.3 이었지만 JobBench 에서는 +5.5 로 다섯 모델 중 가장 컸다. k=1 본표에서도 GLM-5 가 Gemini 보다 크게 오른 것은 WorkBuddy 와 LAB 이고, JobBench 에서는 Gemini 쪽이 더 올랐다.
  • 모든 후보가 같은 틀린 전제를 공유할 때재실행 비교로는 잡히지 않는다. 논문의 실패 분석에서 틀린 전제가 후보 넷에 모두 퍼져 점수가 50 에서 42 로 내려간 사례가 있다.
  • 원래 결과물이 더 나을 때공개 코드의 선택 단계는 기준 실행의 결과물을 후보에 넣지 않는다. 그래서 편집이 해를 끼친 과제에서도 원래 결과물로 돌아갈 수 없고, 되돌리는 길은 합성 단계가 원래 harness 를 유지하는 것뿐이다.

자기 agent 에 적용할 때는 과제를 안전하게 여러 번 재실행할 수 있는지부터 확인한다. 논문의 출발 harness 는 거의 비어 있었으므로, 이미 다듬은 harness 에서 시작한다면 논문의 최대 향상을 그대로 기대하지 않는다.

다른 기법과 갈리는 곳은 재실행 비교와 합성이다

논문이 실제로 돌린 baseline 은 아래 넷이고, 모두 같은 실행 모델과 같은 Opus 4.8 편집 모델을 쓴다. 표는 각 기법이 무엇을 언제 바꾸는지를 논문 설명대로 옮겼다.

기법무엇을 언제, 무엇을 근거로 바꾸나Harness² 와의 차이
Best-of-kharness 는 그대로 두고, 과제마다 원래 harness 로 k 번 돌린 결과물 중 하나를 고른다재실행은 같고 harness 편집이 없다
ReasoningBank과제 사이에 context 로 넣는 memory 를 바꾼다. 정답 없는 자기 판정으로 나눈 trajectory 가 근거다harness 파일을 고치지 않는다
Harness Scaling과제마다 harness 파일을 고치고 상태는 넘기지 않는다. 지금까지의 trajectory 가 근거다두 갈래 제안, 합성, library 가 없다
Meta-Harness배포 전에 한 번 harness 코드를 찾는다. train 절반의 채점 점수가 근거다정답 신호를 쓰고 배포 뒤에는 고정한다
Harness²과제마다 harness 파일 여덟 종을 고치고 library 를 넘긴다. 기준 실행과 후보 실행의 행동 차이가 근거다
  • 논문 부록의 비교표에서 Improver Update 열의 표시에 대해, 저자들은 그 표시가 갱신 장치가 있다는 뜻일 뿐 개선 능력이 검증됐다는 뜻이 아니라고 적는다.
  • 저자들이 내세우는 새로움도 하나의 장치가 아니다. 정답 없이 과제 흐름에서 두 harness 를 함께 고치는 조합이라고 적는다.

그래서 Harness² 가 낫다는 주장은 Harness Scaling 대비 두 갈래 제안과 합성, Best-of-k 대비 harness 편집이 더하는 몫으로 읽어야 한다. 그 몫의 크기는 9장과 10장의 수치가 정한다.

원래 harness 대비 향상은 12개 조건 모두에서 났다

세 benchmark 와 네 실행 설정의 12개 조건에서 Harness² 한 걸음(k=1)은 모두 원래 harness 보다 점수가 높았다. WorkBuddy 와 LAB 에서는 빈 harness 위의 GLM-5 가 가장 크게 올랐다.

  • 점수는 세 번 실행한 평균이다. Gemini Codex JobBench 의 +1.4 와 GLM-5 Codex JobBench 의 +1.2 는 원래 harness 쪽 표준편차(2.6, 2.3)보다 작아서 실행 사이 흔들림과 구별되지 않는다.
  • k=1 의 제출물은 합성한 harness 의 실행 한 번이다. 그래서 이 향상은 여러 결과물 중에 고른 효과가 아니라 harness 편집의 효과로 읽을 수 있다.
  • JobBench 수치는 13장의 network 항목 때문에 채점 기준표 노출 가능성을 배제할 수 없다.
  • k=5 parallel recursion 은 여기에 WorkBuddy 2.9~3.9점, JobBench 3.0~4.2점, LAB 2.6~6.7%p 를 더한다.
  • GLM-5 는 한 걸음 뒤 WorkBuddy 에서 75.7(OpenCode)과 75.3(Codex)이 되어 원래 harness 의 Gemini 3.5 Flash 72.4, 74.5 를 넘는다.

가장 강한 baseline 과의 차이는 8개 조건에서 1.1점 안이다

같은 12개 조건에서 Harness² k=1 점수와 본표의 baseline 셋(ReasoningBank, Meta-Harness, Harness Scaling) 중 가장 높은 점수의 차이를 계산했다. 차이가 두 쪽 표준편차보다 큰 조건은 3개이고, LAB 의 한 조건에서는 Meta-Harness 가 앞선다.

  • 차이가 1.1점 안인 8개 조건에서 두 쪽 표준편차는 0.2에서 4.5 사이라서, 세 번 실행만으로는 순위를 가를 수 없다.
  • GLM-5 Codex LAB 의 +2.1 은 두 쪽 표준편차(2.7, 3.3)보다 작다. 그래서 흔들림보다 크게 앞선 조건은 +3.7, +6.0, +3.3 의 3개다.
  • WorkBuddy Code 와 Office 의 scaling 그림에서 Harness² 는 k=2 에서 이미 k=5 의 모든 baseline 보다 높다. Code 에서는 근소한 차이다. 원래 harness 를 k 번 돌려 고르는 Best-of-k 도 여기 들어간다. 다만 같은 k 가 같은 compute 는 아니다. Harness² 는 k 마다 실행 4k 번이고 Best-of-k 는 k 번이다.
  • compute 를 축으로 놓은 비교는 Gemini 3.5 Flash 와 OpenCode 조합 하나의 Figure total_cost 뿐이다. 거기서 JobBench 의 Harness² k=1(약 27M, +4.5)은 비슷한 compute 의 ReasoningBank k=5(약 25M, 약 +1.5)보다 높다.

그래서 실증된 우위는 흔들림보다 크게 앞선 3개 조건과, 조합 하나에서 잰 scaling 그림과 compute 그림이다. 나머지 9개 조건의 차이는 실행 사이 흔들림 안에 있어서, 다른 기법보다 낫다는 주장은 조건마다 따로 확인해야 한다.

채점 모델과 network 접근이 결과 해석을 제약한다

항목마다 논문이 인정한 것인지, 코드와 표를 읽고 찾은 것인지를 괄호에 밝혔다. 할 일이 있는 항목은 끝에 그 일을 붙였다.

  • 채점 모델 겹침(이 글의 지적)JobBench 는 Claude Opus 4.8 이 채점하는데, 같은 모델이 편집과 선택도 맡는다. WorkBuddy 의 판정 항목은 Gemini 3.5 Flash 가 채점해서, Gemini 실행 설정에서는 실행 모델과 채점 모델이 같다. 논문은 shared model bias 를 한계로 적지만 이 겹침은 따로 다루지 않는다. 재현할 때는 채점 모델을 편집 모델과 다른 계열로 바꿔 본다.
  • network 접근(이 글의 지적)공개 코드는 network 접근을 막지 않고, 검증 실행에서 Codex rollout 이 JobBench 채점 기준표를 스스로 내려받았다고 문서에 적혀 있다. 논문은 실험 때의 network 설정을 적지 않았다. 재현할 때는 huggingface.co 와 github.com 을 실행 host 에서 막는다.
  • 표본 크기(이 글의 지적)시험 과제는 WorkBuddy 40, 35, 25개, JobBench 34개, LAB 100개이고 실행은 세 번이다. 표준편차가 4.5까지 나와서 1점 안팎의 차이로 순위를 매기지 않는다.
  • 공개 코드와 논문 실행의 차이(저장소가 밝힘)저장소는 논문 실행이 다른 과제, 모델 배포, 추가 도구를 썼을 수 있다고 적는다. 기본 편집 모델은 실행 모델과 같고, 제공 설정은 Vertex Gemini 실행 모델만 다룬다. 논문의 split 파일과 baseline 구현도 들어 있지 않다. 그래서 본표 수치는 이 저장소로 바로 다시 낼 수 없다.
  • 누출 검사의 범위(이 글의 지적)코드의 검사는 일곱 개 표지 문자열을 찾는 tripwire 이고, 주석도 그것이 방어 자체가 아니라고 적는다. 채점 기준표는 benchmark 별 경로 제외 목록으로 막는다. 새 benchmark 를 붙일 때는 그 목록을 직접 채워야 한다.
  • library 입장 조건(이 글의 지적)논문은 실행 대조로 지지된 교훈만 남긴다고 적지만, 코드가 확인하는 것은 반성 모델의 출력에 cue, lesson, evidence 칸이 채워졌는지다. 지지 여부는 반성 모델의 판단에 맡겨져 있다.
  • 저자들이 인정한 한계재실행과 편집 세션만큼 추론 비용이 늘고, 행동 대조는 정답을 보장하지 않으며, 채택한 편집이 다른 과제로 옮겨 간다는 보장도 없다.
  • 외부 재현 없음2026-10-25 에 검색한 범위에서는 논문을 다시 요약한 글만 있었고 독립 재현은 찾지 못했다.
