agent 의 기억은 미래에 쓸모 있으리라는 예측일 수 있다

Anthropic 은 session 이 끝나도 남아서 다음 session 이 읽을 수 있는 맥락만 agent memory 로 부른다. 이 기억을 언제 적고 언제 정리할지가 글 전체의 질문이다.

저자는 Kierkegaard 의 말로 글을 연다. 삶은 거꾸로 돌아봐야 이해되지만 앞으로 살아가야 한다는 말이다. agent 도 같은 처지에 있다. 일을 하는 동안 노트를 적어야 하는데, 그 노트가 나중에 쓸모 있을지는 일이 끝나 봐야 안다.

저자는 사람의 기억에서 힌트를 얻는다. 사람은 깨어 있는 동안 hippocampus 가 경험을 바로 기록하고, 잠을 자거나 쉬는 동안 최근 경험을 다시 재생하면서 오래 남길 지식으로 옮긴다. agent 에서는 session 이 일하면서 log 와 노트를 남기고, session 밖의 별도 과정이 그 log 를 돌아보며 노트를 고치거나 새로 만든다. 이 과정을 dreaming 이라고 부른다. Letta 와 UC Berkeley 연구진이 제안한 sleep-time compute, 곧 대화 사이의 빈 시간에 맥락을 재정리하는 아이디어를 기억에 적용한 것이다.

기억의 범위도 좁게 잡는다. 학습으로 weight 가 바뀌는 것, 한 대화 안에서 배우는 in-context learning, 오래된 turn 을 요약으로 갈아 끼우는 compaction 은 모두 빠진다. 남는 것은 경험에서 얻어 session 사이에 보존하고 나중에 읽을 수 있게 저장한 맥락이다.

이렇게 정의하면 노트를 적는 일은 때로 예측이 된다. 규칙을 적으면 그 패턴이 다시 나오리라고 예측하는 셈이고, 확인한 사실을 적으면 다음 session 이 그 사실을 다시 확인하지 않고 믿으리라고 예측하는 셈이다. 다음에 무슨 일이 올지 모르는 상태에서 하는 예측이라 틀릴 수 있다. 글의 나머지는 이 예측을 잘하는 법과 틀렸을 때 고치는 법이다.

표의 순서대로 memory 의 쓰임새가 바뀐다. Sonnet 4.6 은 왜 틀렸는지 추측까지는 했지만 그 추측을 시험하지 않았고, memory 를 써도 점수가 0.330 에서 0.364 로 조금 올랐다. Opus 5 는 규칙을 적을 때 그 규칙을 어떻게 알았는지도 함께 적었고, memory 로 0.564 에서 0.828 로 올랐다. Opus 5.5 와 Sonnet 5.5 도 loop 를 닫았다. 두 모델은 memory 를 쓴 점수가 Opus 5 와 비슷하고, memory 없는 baseline 은 조금 더 높다.

막대에서 두 값을 빼 보면 읽는 법이 하나 더 생긴다. memory 로 오른 폭은 Opus 4.7 이 0.317 로 가장 크고, Opus 5 는 0.264, Opus 5.5 는 0.183 이다. loop 를 닫은 모델은 memory 를 쓴 점수가 가장 높지만, 오른 폭까지 가장 큰 것은 아니다. baseline 이 모델마다 달라서 오른 폭만으로는 노트의 질을 견줄 수 없다. 오른 폭은 막대 값으로 직접 계산한 것이고, 원문은 이 비교를 하지 않는다.

그래서: loop 를 닫은 모델은 memory 를 쓴 점수도 가장 높았지만, 모델 세대가 함께 바뀌어서 loop 만의 효과로 떼어 낼 수는 없다. 분명한 것은 가설을 시험하지 않은 Sonnet 4.6 이 memory 를 붙여도 거의 오르지 않았다는 점이다. 쓰려는 모델의 memory directory 를 몇 질문 뒤에 열어 보고, 규칙 옆에 근거가 있는지 확인하면 된다.

Pokémon Red 를 약 10,000 step 진행한 시점에서 두 모델의 run 하나씩을 비교했다. 갈린 것은 무엇을 적을 가치가 있다고 보았느냐다.

Sonnet 3.7 은 모든 것이 중요할 수 있다고 보고 가리지 않고 적었다. 전투마다, 찾은 아이템마다, 만난 NPC 마다 파일을 따로 만들었고, 결국 225개 폴더에 413개 파일을 남기고 뱃지 1개를 얻었다. 문제는 Pokémon 의 게임 상태가 계속 바뀐다는 데 있었다. 자세히 적은 기록이 계속 낡았고, 게임이 진행될수록 Claude 는 게임보다 기억을 뒤지는 데 시간을 썼다. step 10,000 무렵 Sonnet 3.7 은 네 번째 “master” 폴더를 만들었고, 이어진 17 step 동안 파일 6개를 만들고 9개를 지우면서 게임 안에서는 아무 행동도 하지 않았다.

Fable 5 는 폴더 2개의 파일 9개와 맨 위의 global.md 하나만 적고 뱃지 4개를 얻었다. 기준은 게임이 알려 주지 않는 것이었다. 가진 돈이나 지도 위 위치는 매 턴 화면에서 다시 읽을 수 있으니 적을 필요가 없다. 전략, 계획, 시험해 본 규칙은 Claude 가 알아내야만 생기고, 적지 않으면 사라진다. global.md 는 현재 목표와 체육관 공략 계획, memory 를 쓰는 자기 규칙을 담은 dashboard 역할을 했다. 예를 들어 Magikarp 를 잡으려다 Poké Ball 이 일곱 번 연달아 실패하자, Claude 는 세 번 이상 실패하면 메뉴 사이에 ‘wait’ 입력을 넣어 timing 을 바꾸라는 규칙을 적었다. 그렇게 하자 바로 잡혔기 때문이다.

Opus 5.5 도 같은 방식을 썼다. 현재 목표와 다음 단계를 담은 작은 노트 폴더를 두고, 플레이하면서 노트를 고쳐 쓰고, 게임을 끝까지 깼다.

두 run 은 세대가 다른 모델이라, 뱃지 수의 차이에는 기억 방식 말고도 게임 실력의 차이가 섞여 있다. 같은 모델에 두 기억 방식을 시킨 비교는 원문에 없다. 그래서 이 장에서 가져갈 것은 뱃지 수보다 위의 기준, 곧 환경에서 다시 읽히는 것은 적지 않는다는 원칙이다.

기억의 용도만 알려 주고 쓰는 법은 모델에 맡긴다

CL-Bench 에서 “실패만 적어라” 는 고정 규칙은 Opus 5 와 Opus 4.7 의 memory 이득을 크게 깎았다. 반대로 memory 를 먼저 읽고 가설을 시험하라는 지시는 Sonnet 4.6 의 점수를 거의 두 배로 올렸다.

Anthropic 은 CL-Bench 에서 memory 폴더가 있다고만 알렸고, Opus 4.7 과 Opus 5 에는 그것으로 충분했다. 여기에 “실패만 기록하라” 는 규칙을 하나 더하자 두 모델 모두 memory 로 얻던 이득을 크게 잃었다. 4장 막대로 계산하면 Opus 5 는 memory 이득 0.264 가운데 0.234 를, Opus 4.7 은 0.317 가운데 0.150 을 잃었다. 두 그림이 같은 run 묶음에서 나왔는지는 원문에 없어서 이 비율은 대략의 크기로만 읽어야 한다. 무엇이 중요한지 스스로 판단하던 모델에게 미리 정한 규칙이 판단을 대신한 셈이다.

오래된 모델에서는 다른 지시가 효과를 냈다. Sonnet 4.6 은 memory directory 를 자주 열지 않았고 원인 가설도 시험하지 않았다. 답하기 전에 memory 파일을 읽고 가설을 명시적으로 시험하라고 지시하자 점수가 0.364 에서 0.641 로 올랐다. Sonnet 5 는 지시 없이도 10번 중 9번 답하기 전에 memory 를 읽었고, Sonnet 4.6 은 절반이 안 됐다.

그래서 Anthropic 은 최신 모델에 단순한 지침만 준다. 사람이 기억하라고 하거나 분명히 기억할 가치가 있을 때 노트를 만들라는 정도이고, 나머지 판단은 Claude 에 맡긴다.

그래서: 두 실험은 서로 다른 지시를 다른 모델에 준 것이다. 강한 모델에 “읽고 시험하라” 를 준 결과는 원문에 없으므로, 지시가 모델에 따라 효과를 뒤집는다고까지 말할 수는 없다. 다만 무엇을 적을지 정한 고정 규칙은 강한 모델의 이득을 깎았다. memory 규칙을 둔 채 새 모델로 옮긴다면 규칙을 뺀 설정도 함께 재 보는 편이 안전하다.

§Steering Claude to write memory: “We’ve found that it helps to tell Claude what memory is for, but not how to use it.”

이 사례에서 눈여겨볼 곳은 틀린 노트가 스스로를 지킨 방식이다. ledge 아래로 떨어진 Claude 는 노트를 의심하는 대신 서쪽으로 너무 많이 왔다고 해석했고, 처음부터 맞는 쪽에 있었다고 결론 내렸다. 세 번째 실패 뒤에는 “I’m going to stop rather than keep looping” 이라고 적으며 멈추려 했다. 실험 설정의 자동 응답이 계속하라고 하자 회복하고 물건을 채우려고 산 앞 마을인 Pewter City 까지 되돌아갔다.

dreaming 을 늘릴수록 wiki 만으로 답하는 점수가 올랐다

Anthropic 이 5월에 인수한 Stainless 의 내부 문서 약 350,000개 파일, 약 420M token 으로 실험했다. 여기서 dreaming 의 입력은 session transcript 대신 이 문서 묶음이었고, Opus 5 agent 들이 128 session 에 걸쳐 wiki 를 만들었다.

wiki 는 Claude 가 쓰고 관리하는 page 모음이다. page 마다 한 주제에 대해 Claude 가 아는 것을 모으고 다른 노트로 link 를 건다. 그래서 늘어나는 기억 속에서 필요한 것을 찾아가는 지도 역할을 한다. 각 session 의 agent 는 파일을 살펴보고, link 된 wiki page 를 쓰거나 고치고, 중복을 합치고, 주장을 원본과 대조했다. session 들은 공유 log 로 일을 나눠 앞 session 의 결과 위에 쌓았다.

dreaming 을 2 session 에서 128 session 으로 늘리자 wiki 만으로 답한 점수가 채점 기준의 13% 에서 48% 로 올랐다. 저자는 이것을 신입 직원이 노련한 직원이 되는 과정에 비유한다. 그런데 wiki 만 쓴 최고 점수 48% 는 search tool 만 쓴 53% 보다 낮다. wiki 의 값은 search 와 함께 쓸 때 드러났다. 둘을 함께 쓴 점수는 wiki 가 자라면서 54% 에서 61% 로 올랐고, search 와 wiki 를 함께 쓰면 질문당 약 20,000 token 을 아꼈다. 무엇과 견준 절약인지는 원문에 나와 있지 않다.

같은 dreaming 이라는 이름 아래 입력이 다르다는 점도 기억해 둘 만하다. 7장의 교정은 session transcript 를 읽었고, 이 실험은 회사 문서 묶음을 읽어 wiki 를 썼다. 저자는 둘 다 session 밖에서 기억을 정리하는 과정으로 묶는다.

그래서: wiki 는 search 를 대신하는 장치로 쓰기보다 search 위에 얹는 지도로 쓰는 편이 이 결과와 맞다. 다만 search 만 쓴 53% 와 견주면 wiki 를 2M 에서 128M token 예산까지 키워 얻은 차이가 질문 25개에서 8%p 다. 내 질문 수와 dreaming 예산으로 같은 차이가 나는지 먼저 재 봐야 한다.

같은 절: “Using search and the wiki also saved about 20,000 tokens per question.”

빠진 것이 있으면

처음 wiki 에서는 여러 agent 가 계약 조건을 모은 공유 표 하나에 동시에 썼다. 표는 조건을 엉성하게 요약했고, agent 들이 서로의 작업을 덮어써서 일부 조건은 아예 빠졌다. 그 wiki 로 만든 brief 는 사실 57개 가운데 41개만 담았다. Anthropic 은 Claude 가 실패를 돌아보고 지시문 수정을 제안하고 wiki 를 다시 만드는 loop 를 돌렸고, Claude 가 계약 조건이 핵심이라는 것을 찾아 지시문을 고쳐 썼다.

고친 지시문은 여러 가지를 함께 바꿨다. 계약 조건이 핵심이라고 밝힌 것, 계약마다 page 하나를 agent 하나에 맡긴 것, 조건을 요약하지 않고 그대로 인용한 것이다. 어느 쪽이 41개를 57개로 올렸는지는 Anthropic 이 나눠 재지 않았고, 사례도 과제 하나다. 개선된 wiki 의 크기는 원글에 나오지 않는다. 다만 조건을 그대로 옮기면 page 가 길어지기 쉬우므로, 9장의 원본보다 큰 wiki 와 맞부딪칠 수 있다는 추측도 함께 적어 둔다.

그래서: 어느 변경이 효과를 냈는지는 나뉘지 않았지만, 실패 원인으로 확인된 덮어쓰기는 page 마다 쓰는 agent 를 하나로 정하면 막힌다. 여러 agent 가 동시에 wiki 를 쓴다면 이것부터 정하고, 무엇이 핵심 사실인지를 지시문에 적어 두는 편이 좋다.

dreaming 은 노트를 hierarchy 의 맨 위로 올릴 수 있고, agent harness 는 그 층을 session 시작마다 Claude 의 context 에 미리 싣는다. 그러면 Claude 는 그 노트를 찾을 필요가 없다. 하지만 저자는 이 주입을 조심해서 하라고 적는다. 주입한 기억은 token 을 쓰고, 틀린 노트 하나가 모든 session 으로 옮겨 간다. 실었다고 해서 Claude 가 따른다는 보장도 없다. 그래서 이 층에서 dreaming 이 하는 일의 상당 부분은 크기를 지키는 것이다. 자세한 내용은 아래 층으로 내리고 link 만 남긴다. Claude Code 에서 Claude 가 스스로 쓰는 auto memory 의 색인 MEMORY.md 가 위 판의 방식으로 이를 session 안에서 한다.

그래서: MEMORY.md 같은 기억 색인에는 내용 본문보다 무엇이 어디 있는지를 적는 편이 낫다. 줄 수가 한도에 가까워지면 오래된 항목을 합치거나 topic 파일로 내리면 된다.

이 예측이 맞지 않을 수 있는 조건은 7장에서 끌어낸 해석 하나와 Anthropic 이 결론부에 남긴 열린 질문들이다.

  • transcript 에 반대 증거가 없을 때7장에서 끌어낸 해석이다. dreaming 은 transcript 와 대조해 노트를 고친다. 바뀐 사실을 agent 가 한 번도 마주치지 않았다면 대조할 것이 없어서 틀린 노트가 그대로 남는다.
  • 환경이 dreaming 주기보다 빨리 바뀔 때dreaming 은 compute 를 쓰므로 모든 기억을 계속 점검하기 어렵다. 저자는 바뀌기 쉬운 정보에 dreaming 을 집중하거나, 기억이 얼마나 자주 읽히는지에 맞춰 주기를 조정하라고 제안한다.
  • 그 자리에서 적을지 나중에 정리할지session 중에 적으면 바로 쓸 수 있지만 본 작업에서 주의를 뺏는다. dreaming 에 맡기면 배경으로 돌릴 수 있지만 결과가 바로 쓰이지 않는다.
  • 모델이 약할 때6장처럼 memory 를 읽고 가설을 시험하라는 명시적 지시가 필요하다. 표의 예상은 최신 모델 기준이다.
  • wiki 의 유지 비용wiki 를 쓰려면 오류나 hallucination 이 쌓이지 않게 계속 compute 를 써야 한다. 저자는 transcript search 를 기억의 바탕으로 두는 것도 합리적이라고 본다.

그래서: dreaming 을 직접 써 보려면 Claude Managed Agents 에서 접근을 신청해야 한다. Anthropic 발표에 따르면 dreaming 은 research preview 이고, 기억을 자동으로 고치게 하거나 바뀐 내용을 사람이 먼저 검토하게 고를 수 있다. 처음에는 검토 모드로 두면 7장 같은 교정이 실제로 일어나는지 직접 볼 수 있다.

사례 대부분이 run 한두 번과 수십 문항 평가에서 나왔다

숫자는 모두 Anthropic 이 자사 모델로 잰 값이고, 외부 재현 결과는 글에 실려 있지 않다. 아래 한계는 내 환경에서 무엇을 다시 재야 하는지를 정한다.

  • Pokémon 비교는 모델당 run 하나다Sonnet 3.7 과 Fable 5 의 memory folder 는 run 하나씩을 비교했고, Mt. Moon 사례도 교정한 run 과 교정하지 않은 run 을 하나씩 보여 준다. 방향을 보여 주는 사례로 읽고, 효과의 크기는 직접 재야 한다.
  • 비교한 모델의 세대가 다르다Sonnet 3.7 과 Fable 5 의 차이에는 기억 방식과 함께 모델의 실력이 섞여 있다. CL-Bench 에서도 모델마다 baseline 이 달라 memory 로 오른 폭만으로 노트의 질을 견줄 수 없다.
  • run 수가 조건마다 다르다Figure 5 에서 memory 를 쓴 Opus 5 는 run 16회, 다른 조건은 3회, “실패만 적어라” 규칙의 Sonnet 4.6 은 1회다. Sonnet 4.6 의 작은 감소 폭은 run 하나의 값이다.
  • 평가 문항이 적다Stainless 실험은 질문 25개, 합병 실험은 질문 24개다. 87% 와 73% 의 차이는 그 안의 일부 항목에서 나왔다.
  • Stainless 코퍼스는 내부 문서다글에는 이 코퍼스를 받을 곳이 없으므로, 같은 실험을 밖에서 그대로 되풀이하기는 어렵다. wiki 가 이기는 조건은 9장의 질문 모양으로 내 데이터에서 확인해야 한다.
  • Figure 10 의 가로축은 예산이다session 당 1M token 예산으로 계산한 값이라 dreaming 의 실제 비용을 가늠하는 데 쓰면 안 된다. 실제 지출은 글에 나와 있지 않다.
  • Figure 11 의 분류는 모델이 붙였다원문도 개별 선보다 전체 모양을 믿으라고 적는다.
  • dreaming 의 prompt 와 설정은 이 글에 없다Anthropic 은 시작용 cookbook 으로 link 한다. 그 cookbook 은 열지 않았으므로 구현 세부는 다루지 않았다.
