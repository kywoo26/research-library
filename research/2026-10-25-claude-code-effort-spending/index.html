Claude Code 의 effort 가 바꾸는 일과 단계를 고르는 법

Claude Code 의 effort 는 한 작업에 계산을 얼마나 쓸지 모델에 알려 주는 다섯 단계 설정이다. 글쓴이 Thariq Shihipar 는 단계를 올리면 Claude 가 스스로 검증하고 edge case 를 시험하는 일과 혼자 내리는 판단이 함께 는다고 설명한다. 그가 실은 내부 벤치마크에서 높은 단계는 edge case 를 놓친 실패를 크게 줄였지만, 과제 설명을 달리 읽을 여지가 있을 때 틀린 해석을 고른 실패는 오히려 늘었다. 그래서 그는 사람이 결과를 보며 이끌 구현은 낮은 단계로, 검증은 높은 단계로 돌리기를 권한다.

Claude Code 블로그(claude.dev)의 Engineering 글 「Using Claude Code: Spending your effort」(2026-09-25)다. 글쓴이 Thariq Shihipar 는 Claude 모델을 “우리 모델”이라 부르며 Anthropic 내부 실행 결과를 싣는다. 2026-10-25 에 읽은 판이고, Claude Code 와 Claude API 의 effort 공식 문서를 함께 읽었다.

tl-dr

단계를 고를 때 기억할 것

effort 는 Claude 가 얼마나 확인하고 얼마나 혼자 정할지를 바꾼다. 그래서 edge case 를 시험으로 찾을 수 있는 일에 높은 단계를 쓰고, 방향을 함께 잡는 일에는 낮은 단계로 빨리 돌린다.

  • 1effort 는 정해진 토큰 상한으로 작동하지 않는다. 단계마다 생각할지, tool call 을 얼마나 할지, 결과를 얼마나 확인할지를 모델이 정하는 신호다. 원리
  • 2원문 사례에서 높은 단계의 Claude 는 기준 구현이나 brute-force 풀이처럼 따로 맞춰 볼 대상을 만들어 결과를 비교했다. 낮은 단계는 한 번에 쓰고 예시 몇 개로 확인한 뒤 끝냈다. 사례
  • 3Terminal-Bench 3.0 에서 Fable 5.1 을 low 에서 max 로 올리자 edge case 를 놓친 실패는 59건에서 24건으로 줄었다. 요구를 다른 뜻으로 읽은 실패는 25건에서 47건으로 늘었다. 실패 종류
  • 4보안과 하드웨어 과제에서 단계를 올린 효과가 가장 컸고, 규칙을 따라 처리하는 운영 과제는 높은 단계에서도 22% 에 머물렀다. 분야
  • 5글쓴이의 기준은 빠르게 주고받는 일 low, 보통의 기능 구현 medium, 검증이 중요한 일 high, 사람 없이 끝까지 맡기는 어려운 일 max 다. 고르는 기준
  • 6Claude Code 에서는 /effort 로 대화 중에 바꾼다. 글쓴이는 최신 모델이 effort 를 바꿔도 prompt cache 를 깨지 않는다고 쓴다. 모델을 바꾸면 단계는 다시 고른다. 설정

problem

단계에 따라 몇 배씩 달라지는 시간과 토큰

effort 단계 하나로 같은 과제에 드는 시간과 토큰이 몇 배씩 달라진다. 어느 단계가 언제 그만한 값을 하는지 모르면 쉬운 일에 시간을 쓰거나, 어려운 일에서 edge case 를 놓친 결과를 받는다.

  • 1.5분 / 67분명세 없이 “운동 기록 앱을 만들어 줘”라고 했을 때 Opus 5.5 의 low 와 max 가 걸린 시간
  • 2분 / 33분HTML sanitizer 과제에서 low 시도 하나와 high-effort 실행 하나가 걸린 시간
  • 약 43k / 약 276kTerminal-Bench 3.0 에서 Opus 5.5 의 low 와 max 가 시도 하나에 쓴 토큰의 중앙값
  • mediumClaude Code 에서 Opus 5.5 의 기본 단계. Sonnet 5.5 와 Haiku 5.5 도 medium 이고, Opus 4.7 은 xhigh, 그 밖의 모델은 high 에서 시작한다

글쓴이는 effort 가 무엇이고 언제 어느 단계를 쓰는지 묻는 사용자 질문이 많아서 이 글을 썼다고 밝힌다. 답을 찾으려고 같은 과제를 여러 단계로 직접 돌려 보고, Terminal-Bench 3.0 결과를 과제별로 들여다봤다. 위의 값들은 서로 다른 과제와 측정에서 왔지만, 단계 하나가 시간과 토큰을 몇 배로 바꾼다는 점은 같다.

첨언: 원문과 값의 출처

블로그 첫 문단: “What is effort really, and when do you use which effort level? Why do we need effort at all?” 토큰 값은 원문 FIG A 의 SVG 점 좌표를 축 눈금으로 환산한 근삿값이다. 시간은 원문 carousel 의 단계 표시(low(1.5 min) … max(67 min))와 html-js-filter 단락에서 옮겼다. 기본 단계는 Claude Code 문서 §Adjust effort level 이다.

mechanism

effort 가 바꾸는 것

effort 는 이 작업에 계산을 얼마나 쓰길 바라는지 모델에 알려 주는 신호다. 단계를 올리면 Claude 는 더 자주 생각하고, tool call 을 더 하고, 스스로 확인하고 판단하는 일을 늘린다. 토큰 상한이 정해지는 것은 아니어서 낮은 단계에서도 충분히 어려운 문제에는 생각한다.

글쓴이는 effort 를 시간 약속에 빗댄다. 누군가 어떤 일을 12시간 내내 해 달라고 하면 정말 공들여 해 달라는 뜻으로 받아들인다. 같은 일을 1시간 안에 해 달라고 하면 요구에 맞는 가장 나은 판을 내고 이어서 고쳐 갈 것을 예상한다. Claude 도 어느 단계에서나 일을 합리적으로 하려 하지만, 높은 단계에서는 판단과 검증을 위해 혼자 움직이는 일이 늘어난다는 것이 그의 설명이다.

그래서 단계를 올린 결과는 답이 길어지는 데서 그치지 않고 작업의 모양이 바뀌는 데서 드러난다. 다음 장의 사례가 그 모양을 보여 준다.

첨언: 원문

블로그 §What is effort?: “At a high level, effort gives the model an approximation of how much compute you want it to spend on the task. It’s somewhat related to your modeling of the difficulty of the task.” “Claude will always try and do your task reasonably, but higher effort will involve Claude taking more independent action for judgement and verification.”

Claude Code 문서 §Adjust effort level: “Effort levels control adaptive reasoning, which lets the model decide whether and how much to think on each step based on task complexity.” §Extended thinking: “On these models, the model decides per step how much to think based on the effort level.”

Claude API 문서 §Effort levels: “Effort is a behavioral signal, not a strict token budget. At lower effort levels, Claude still thinks on sufficiently difficult problems, but thinks less than it would at higher effort levels for the same problem.” §How effort works: “Because effort applies to every output token, it works with or without thinking. Lower effort also means fewer and terser tool calls.”

case

HTML sanitizer 과제를 low 와 high 로 돌렸을 때

html-js-filter 에서 Fable 5.1 은 low 로 다섯 번 중 한 번, xhigh 로 다섯 번 모두 통과했다. 두 실행은 필터를 다 쓴 뒤 무엇에 맞춰 확인했는지에서 갈렸다.

과제는 페이지에 JavaScript 를 몰래 넣는 모든 방법을 걸러 내는 HTML sanitizer 를 만드는 것이다. 걸러 내야 할 경우가 숨어 있어서, 예시 몇 개를 통과한 필터도 채점에서는 떨어지기 쉽다.

Opus 5.5 로 돌린 다른 세 과제도 같은 모양이다. 낮은 단계는 답을 한 번 만들고 쉬운 예로 확인한 뒤 멈췄다. 높은 단계는 따로 맞춰 볼 대상을 만든 다음 그것과 비교했다.

첨언: 원문

html-js-filter: “Fable 5.1 went from 1/5 at low to 5/5 at xhigh.” “A typical attempt at low effort takes about 2 minutes. Each of these attempts wrote a filter in roughly one pass, then tested it against a single hand-written page.” “A high-effort run finishes in about 33 minutes. In the run I traced, it adversarially reviewed its first draft, then read the installed parser’s source to check for bugs, ran many clean test cases until they gave the same output as the input, ran a standard XSS test suite, and finally, wrote a random-document fuzzer.”

mvcc-lsm-compaction: “At xhigh (about 11 minutes), Claude reproduced the crash first, wrote a randomized test against a reference that never compacts, and checked that its tests failed on half-finished fixes.” gsea-proteomics: “If a user were in the loop, Claude may have asked the user about the way to set up the problem, but without a user in the loop, high effort does better.”

각주: “The worked examples come from individual runs, some at intermediate effort settings.”

result-curve

단계별 통과율과 토큰 곡선

Terminal-Bench 3.0 에서 Opus 5.5 와 Fable 5.1 은 단계를 올릴 때마다 통과율과 시도당 토큰이 함께 올랐다. Opus 5.5 는 low 36.6% 에서 max 65.7% 까지 오르는데 상승폭은 medium 이후 작아지고, high 에서 Fable 5.1 max(58.0%)와 비슷한 58.9% 를 토큰 절반으로 냈다.

곡선이 꾸준히 오른다고 단계마다 같은 값을 하지는 않는다. Opus 5.5 의 점을 이어 보면 오르는 폭은 아래쪽 단계에서 크고 위로 갈수록 작아진다.

  • low→medium약 35k 토큰을 더 써서 약 18%p 오른다
  • medium→high약 25k 토큰을 더 써서 약 4%p 오른다
  • high→xhigh약 77k 토큰을 더 써서 약 4%p 오른다
  • xhigh→max약 96k 토큰을 더 써서 약 3%p 오른다

그림 좌표에서 읽은 근삿값이라 위쪽 세 구간의 차이끼리는 견줄 수 없고, low 에서 medium 으로 갈 때 가장 크게 오른다는 것만 분명하다. high 에서 max 까지 가면 토큰은 약 2.7배가 되고 통과율은 약 7%p 오른다. 그래서 실패 하나가 비싼 일, 예를 들어 보안 점검이나 운영 중인 코드의 버그 수정에서 고를 만하다.

첨언: 계산과 원문

단계 사이의 차이는 위 근삿값으로 계산했다. 원문에는 이 비교가 없다. 토큰은 SVG 좌표 환산값이라 한 자리까지만 믿을 만하다.

블로그 §Effort curves: “Fable 5.1 and Opus 5.5’s effort curves are our best yet: at each level, there is an uptick in benchmark scores and tokens consumed.” FIG A 설명문: “Opus 5.5 at high matches Fable 5.1 at max (58.9% against 58.0%) on half the tokens. Fable 5 levels off at 43.4% from xhigh to max.”

result-failure

높은 단계가 줄인 실패와 늘린 실패

Fable 5.1 을 low 에서 max 로 올리자 edge case 를 놓친 실패는 59건에서 24건으로 줄었고, 접근을 잘못 잡은 실패는 133건에서 107건으로 덜 줄었다. 과제 설명이 다르게 읽힐 여지가 있을 때 테스트와 다른 해석을 고른 실패는 25건에서 47건으로 늘었다.

모델과 단계마다 시도 368~370번. 실패 종류는 원문 그림의 분류를 옮겼다. “edge case 를 놓침”은 원문의 missed a case, “접근을 잘못 잡음”은 made the wrong call 이다. Opus 5 의 max 열은 effort 이름이 max 인 실행이다. 곡선 그림의 Opus 5 max 는 effort-120 실행이고, 그 실행으로 세면 놓친 edge case 는 63건에서 39건, 틀린 해석은 28건에서 41건이다. 규칙을 틀린 칸은 Fable 5.1 만 옮겼다.

edge case 를 놓친 실패에는 자기 테스트가 못 잡은 버그, 보이는 예시에만 맞춘 코드, 정확히 같지 않은 출력, 자기 환경에서만 돈 코드가 들어간다. 모두 더 꼼꼼히 시험하면 드러날 수 있는 실패이고, 높은 단계에서 세 모델 모두 크게 줄었다. 접근을 잘못 잡은 실패 안에서는 방향이 갈린다. 과제 설명에 적힌 요구를 어긴 실패는 줄었는데, 설명이 두 가지로 읽히는 과제에서 테스트와 다른 쪽을 고른 실패는 세 모델 모두 늘었다.

글쓴이는 이 칸을 따로 풀이하지 않는다. 높은 단계의 Claude 가 사용자를 대신해 더 많이 가정한다는 그의 관찰과 맞는 결과이기는 하다. 다만 시도 하나에는 실패 종류가 하나만 붙으므로, edge case 를 고친 시도가 다음 걸림돌인 해석 문제로 다시 분류되었을 수도 있다. 어느 쪽이든 요구가 모호한 일에서는 단계를 올려도 이 실패가 줄지 않았으므로, 명세를 채우는 쪽이 먼저다.

첨언: 분류의 정의와 원문

원문 그림의 분류 정의(같은 페이지의 차트 스크립트): “The brief allowed two readings. It chose the one the tests did not.”(picked the wrong reading), “The right design with a real bug. Its own tests never hit the case that breaks it.”(a bug its tests missed). 블로그 본문: “Overall, increasing effort tends to reduce failures due to missing edgecases (purple blocks), but does not fix when the model has the wrong approach (blue blocks).” 그림 설명: “Each square is one attempt. Failure kinds come from a model judge and are approximate.”

Fable 5.1 의 값은 원문 화면에 보이는 low 와 max 칸이다. Opus 5 와 Fable 5 는 같은 그림의 다른 탭이고, 값은 페이지에 실린 차트 데이터에서 옮겼다. Opus 5 의 데이터에는 max 라는 이름이 붙은 실행이 둘 있어 effort 이름이 max 인 쪽을 썼다. 다른 하나(effort-120, 통과 178)도 놓친 edge case 39건, 틀린 해석 41건으로 방향이 같다. 원문 그림에 Opus 5.5 탭은 없다.

result-domain

분야마다 다른 effort 의 값

Fable 5.1 에서 단계를 올린 효과가 가장 큰 분야는 하드웨어(34%→75%)와 보안(64%→87%)이다. 운영(12%→22%)과 미디어(18%→30%)는 높은 단계에서도 통과율이 낮게 머문다.

글쓴이는 검증과 edge case 시험이 쓸모 있는 하드웨어, 코드 리뷰, 보안에서 높은 단계가 더 나은 결과를 냈다고 쓴다. 그림에 코드 리뷰 분야는 없지만, 하드웨어와 보안은 여기서도 가장 크게 올랐다. 개발자 일에 가장 가까운 소프트웨어 분야(20과제)는 43% 에서 56% 로 13%p 올랐다. 원문은 운영 칸에 규칙서형 업무는 낮게 머문다고만 적는다. 운영 과제는 회사의 월말 무역 통계 신고를 끝까지 처리하는 식이라, 확인을 더 해도 모델이 모르는 규칙은 채워지지 않기 때문으로 읽힌다. 이 풀이는 원문에 없다.

첨언: 원문과 다른 모델

같은 그림의 다른 탭에서 Opus 5 는 보안 53%→82%, 하드웨어 42%→68%, 운영 2%→13% 였고, Fable 5 의 미디어는 28% 에서 25% 로 내려갔다.

블로그 첫머리: “Extra effort gave better results in domains where verification and edgecase testing was more useful like hardware, code review, and security.” 그림 설명: “Pass rate. Low effort pools each model's two lowest settings, top effort its three highest, since categories are small.” Fable 5.1 의 낮은 단계는 low 와 medium, 높은 단계는 xhigh, effort-120, max 실행이다.

loop

명세가 느슨할수록 커지는 단계별 차이

명세가 거의 없는 앱 만들기에서는 단계가 오를수록 만든 기능이 크게 늘고 Claude 가 대신 정한 것도 늘었다. 인터뷰로 만든 명세를 주자 단계별 결과가 비슷해졌다. 그래서 글쓴이는 자신이 얼마나 곁에서 이끌지를 단계를 고르는 기준으로 삼는다.

과제달라진 것
명세 없이 운동 기록 앱low 는 기록과 단순한 그래프뿐이고, 단계가 오를수록 기능이 늘어 max 에는 heat chart 까지 있다
Claude Code 의 /config 메뉴 재설계하위 메뉴와 나은 검색이라는 생각은 모두 같다. low 는 Claude Code 같지 않은 sketch, max 는 Claude Code 와 닮은 mockup 과 흐름별 walkthrough 다
인터뷰로 만든 명세로 같은 앱. 원문은 여러 모델로 돌렸다고 쓴다디자인과 구현이 서로 비슷하고 세부만 다르다. max 는 몇 부분을 단순하게 다듬었다

명세가 없을 때 높은 단계가 더 많이 만드는 것은 그만큼 사용자 대신 정하는 것이 많다는 뜻이다. 글쓴이는 낮은 단계가 빨리 출발점을 주고, 높은 단계는 일을 더 해 주지만 내 대신 더 많이 가정한다고 정리한다. /config 재설계에서 그는 max 의 다듬어진 결과보다 low 로 Claude 의 생각을 먼저 보는 쪽을 골랐다. 고쳐 가며 방향을 잡을 생각이면 low 가 훨씬 빨리 거기에 닿기 때문이다.

명세를 주면 low 도 16분이 걸린다. 할 일이 명세에 적혀 있으니 낮은 단계도 그만큼 일을 하고, 단계가 바꿀 여지는 세부로 줄어든 것으로 읽힌다.

첨언: 원문

§Takeaways: “For regular software engineering, particularly new feature work, the effort level depends a lot on how in the loop I want to be. Low effort allows Claude to respond quickly with a starting point, higher effort levels will get more work done but Claude will also make more assumptions on my behalf.”

/config: “For this particular task, I think I prefer using low effort to understand Claude’s vision.” 명세 빌드: “I found that given this spec, the models behaved much more similarly.” 결과 화면은 원문 carousel 의 캡처라 열지 않았고, 달라진 것은 글쓴이의 서술을 옮겼다.

choose

작업에 맞는 단계 고르기

글쓴이의 기준은 곁에서 빠르게 주고받는 일 low, 보통의 기능 구현 medium, 검증이 중요하거나 edge case 가 있는 일 high, 사람 없이 끝까지 맡기는 어려운 일 max 다. Claude Code 공식 문서도 같은 기준을 싣고, max 는 수확이 줄고 생각이 지나칠 수 있으니 넓게 쓰기 전에 시험해 보라고 덧붙인다.

지금 하는 일단계근거
아이디어 내기, 첫 sketch, 이름 바꾸기처럼 결과를 하나씩 보고 다음을 정하는 일low글쓴이의 low(brainstorming, sketch, 쉬운 변경)와 문서의 low(이름 바꾸기). 출발점을 빨리 받고 방향은 사람이 잡는다
범위가 분명한 새 기능 구현medium글쓴이의 평소 작업 단계이자 Opus 5.5 의 기본값. Opus 5.5 곡선은 low 에서 medium 으로 갈 때 가장 크게 오른다
기존 코드베이스의 버그 수정, 검증이 중요한 일high글쓴이와 문서의 high. simplex 와 gsea 사례는 high 에서 비교 확인을 하며 통과했다
코드 리뷰, 보안 점검high 이상글쓴이가 높은 단계가 더 나았다고 꼽은 분야다. Fable 5.1 의 보안 과제는 높은 단계에서 64% 에서 87% 로 올랐다
오래 도는 agent 작업, 더 깊이 따져야 하는 일xhigh글쓴이의 기준표에는 없다. Claude Code 문서는 토큰을 더 쓰는 깊은 추론이라고 적고, API 문서는 30분 넘게 도는 agent 와 coding 작업을 예로 든다. html-js-filter 와 mvcc 는 xhigh 에서 통과했다
보안 취약점 찾기, 앱을 처음부터 만들고 검증까지 사람 없이 맡기는 일max, 그 전에 xhigh 를 먼저 시험글쓴이의 max. 문서는 수확 체감과 지나친 생각을 경고하고, Fable 5.1 의 실패 종류 데이터에서도 max 가 xhigh 보다 많이 통과하지 않았다(한계)
요구가 두 가지로 읽히는데 곁에 사람이 없는 일단계보다 명세 먼저높은 단계에서 틀린 해석을 고른 실패가 늘었다(실패 종류)

단계를 올리는 값은 시간으로 치른다. 원문 사례에서 low 대비 sanitizer 는 2분에서 33분, mvcc 는 1분에서 11분, 명세 없는 앱은 1.5분에서 67분이 걸렸다.

글쓴이는 새 기능을 만들 때 쓰는 순서도 소개한다.

벤치마크는 단계를 고정해 돌렸으므로 이 순서 자체를 잰 결과는 없다. 앞의 결과에 비추어 읽으면 인터뷰가 해석이 갈릴 곳을 먼저 없애고, low 구현은 사람이 방향을 보는 동안 빠르게 돌고, edge case 를 찾는 일은 높은 단계가 잘하는 마지막 단계에 몰린다. 표의 medium 과 이 순서의 low 구현은 사람이 곁에 있는지로 갈린다고 보면 두 기준이 맞는다. 결과를 바로 보며 고칠 생각이면 low, 맡겨 두고 끝난 뒤에 볼 생각이면 medium 이다.

첨언: 원문

블로그 §When to use different effort levels in Claude Code: “Low: for when I want quick responses that are in the loop, e.g. brainstorming, sketching, easy changes” “Medium: for most of my regular software engineering work, e.g. new feature implementation.” “High: for work where verification is important or there are edge cases, e.g. fixing a bug in a brownfield codebase.” “Max: When I want Claude to operate fully autonomously to solve difficult problems, e.g. end to end building and verification of an app, finding security vulnerabilities in critical software.”

predict

원문에 없는 작업에 옮겨 보기

실패를 시험으로 찾을 수 있는지, 요구가 한 가지로 읽히는지, 모델이 모르는 규칙이 걸렸는지를 보면 원문에 없는 작업에서도 단계의 효과를 짐작할 수 있다. 시험으로 찾을 edge case 가 많으면 단계를 올리고, 요구가 모호하거나 규칙이 빠졌으면 단계를 올리기 전에 명세에 적는다.

사내 회계 규칙대로 월말 정산 스크립트 쓰기단계를 올려도 덜 오른다. 규칙을 명세에 적는 것이 먼저다운영 분야 12%→22%, 분야 규칙을 틀린 실패 32건→24건규칙이 공개 표준이면 모델이 이미 알고 있을 수 있다

표의 예측은 원문 결과에서 끌어낸 것이고 글쓴이가 한 말이 아니다. 근거가 된 Terminal-Bench 3.0 과제는 글쓴이 말대로 보통의 업무보다 훨씬 크고 야심 찬 과제다. 일상 작업에서도 통과율 차이가 이만큼 나는지는 원문으로 알 수 없으니, 표의 예측은 방향으로만 쓴다.

claude-code

Claude Code 에서 단계를 바꾸고 남기는 곳

/effort 로 작업 중에도 단계를 바꿀 수 있고, 글쓴이는 최신 모델이 Claude Code 에서 단계를 바꿔도 prompt cache 를 깨지 않는다고 쓴다. 같은 단계 이름도 모델마다 실제 값이 달라서 모델을 바꾸면 단계도 다시 고른다.

  • 모델 이동문서는 Opus 5 에서 Opus 5.5 로 옮길 때 쓰던 단계를 가져오지 말고 medium 에서 시작하라고 한다. Anthropic 의 coding 과 지식 업무 평가에서 Opus 5.5 medium 이 Opus 5 high 와 같거나 나았다
  • ultrathinkprompt 에 넣으면 그 턴만 더 깊이 생각하라는 지시가 붙는다. API 로 보내는 effort 는 그대로다

대화 중에 단계를 바꾸는 비용이 작아서 앞 장의 순서를 한 대화 안에서 쓰기 쉽다. API 문서도 Fable 5.1, Opus 5.5, Opus 5 같은 모델은 메시지 단위로 단계를 바꿔 cache 를 지키고, 다른 모델은 cache 를 새로 시작한다고 설명한다. 다만 API 에서 메시지 단위 변경은 beta 기능이라 beta header 를 붙여야 한다. Claude Code 는 작업 중에 /effort 를 실행해도 받고, cache 경고가 뜨면 확인한 뒤 그 턴의 다음 요청부터 새 단계를 쓴다. 검증을 high 로 고정하고 싶다면 검증용 subagent 의 frontmatter 에 effort: high 를 적어 두는 방법도 있다.

첨언: 원문

블로그 첫 문단: “One of the best parts of our newest Claude models is how they respond to effort without breaking the prompt cache in Claude Code”

critique

이 결과를 옮겨 쓸 수 있는 범위

수치는 모두 Anthropic 내부 실행이고 Fable 5.1 은 제품의 안전 개입을 끈 상태였다. Opus 5.5 는 곡선 그림에만 있어서 실패 종류와 분야 분석은 다른 모델의 결과다. 자기 작업에 맞는 단계는 자기 작업으로 몇 번 돌려 보고 정한다.

  • 1그림마다 다른 기준. 곡선 그림은 과제 70개이고 Fable 5.1 low 가 약 32% 인데, 실패 종류 그림은 Fable 5.1 low 를 370번 중 140번(37.8%) 통과로 센다. 실패 종류 데이터에서 Fable 5.1 은 xhigh 217번, max 214번으로 max 가 낫지 않은데 곡선 그림은 max 를 위에 그린다. 그래서 Fable 5.1 에서 xhigh 와 max 중 무엇이 나은지는 원문으로 정해지지 않고, 문서의 max 경고대로 xhigh 부터 시험하는 편이 낫다.
  • 2측정한 모델. 결과가 있는 모델은 Opus 5.5, Fable 5.1, Opus 5, Fable 5 다. Sonnet 5.5 나 Haiku 5.5 에서 같은 모양이 나오는지는 원문에 없으므로, 그 모델을 쓴다면 자기 작업 몇 개로 단계를 바꿔 보고 정한다.
  • 3내부 실행. 과제당 5번씩 돌렸고, Fable 5.1 은 제품의 안전 개입을 끈 채 돌렸다. Claude 제품에서는 Fable 5.1 의 보안 요청 일부가 Opus 로 넘어가므로, 보안 과제의 수치를 제품에서 그대로 기대하기는 어렵다. 보안 과제는 인터넷 없이 돌려서 공개 리더보드와도 맞지 않는다.
  • 4Opus 5.5 의 빈칸. 실패 종류와 분야 그림에는 Fable 5.1, Opus 5, Fable 5 탭만 있다. Opus 5.5 에서 놓친 edge case 가 줄고 틀린 해석이 느는지는 사례 세 개로만 짐작할 수 있다.
  • 5모델 판정. 실패 종류는 다른 모델이 붙인 분류이고 원문이 근사치라고 밝힌다. 칸 사이의 작은 차이보다 세 모델에서 같은 방향인지를 보는 편이 안전하다.
  • 6골라 온 사례. 과제별 사례는 글쓴이가 low 에서 실패하고 높은 단계에서 통과한 과제를 골라 실행 하나씩 따라간 것이고, 일부는 중간 단계에서 나왔다. 높은 단계가 한 확인이 통과의 원인이라는 설명은 서술이고 통제된 비교는 아니다. 앱 빌드 실험은 글쓴이 한 사람의 예시이고 숫자로 남은 것은 걸린 시간뿐이다.
  • 7작은 분야. 분야별 과제는 4~20개라 미디어(4개)나 하드웨어(5개)는 과제 하나가 통과율을 크게 움직인다.
첨언: 원문

각주: “these come from our own internal runs, 5 attempts per task, with our production safety interventions off for Fable 5.1; in Claude products, Fable 5.1’s safeguards hand some security requests to Opus.” “The security tasks also ran without internet access, so the per-task counts here won’t line up with the public leaderboard or the launch post.”

37.8% 는 140 / 370 으로 계산했다. 원문에는 이 비율이 없다. 두 그림의 기준이 왜 다른지는 원문이 설명하지 않는다.

setup

읽은 자료와 열지 않은 자료

  • 읽음Claude Code 문서 Model configuration 의 effort 와 thinking 절, Claude API 문서 Effort 의 단계, tool use, thinking, 대화 중 변경 절
  • 안 염앱 빌드 carousel 의 화면 캡처. 그래서 빌드 결과는 글쓴이의 서술로만 옮겼다
  • 안 염Terminal-Bench 3.0 릴리스의 과제 목록. 과제 설명은 블로그에 적힌 대로다
  • 안 염Claude Code 문서가 연결한 다른 블로그 글(모델과 effort 고르기)과 Opus 5.5 prompting guide 의 Calibrate effort 절. 자기 작업으로 단계를 재는 절차는 그쪽에 있다

원문의 중심 그림인 FIG A 는 곡선 장에 다시 그렸다. FIG B 는 시도 하나를 네모 하나로 그린 그림이라 네모 대신 칸별 건수를 실패 종류 장의 표로 옮겼고, FIG C 는 분야 장의 막대로 옮겼다.
