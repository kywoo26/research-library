Claude Code 의 effort 가 바꾸는 일과 단계를 고르는 법

effort 는 한 작업에 계산을 얼마나 쓸지 모델에 알려 주는 다섯 단계 설정이다. 단계를 올리면 Claude 는 더 많이 확인하고 더 많이 혼자 정한다. 그래서 edge case 를 놓친 실패는 크게 줄지만, 과제 설명이 두 가지로 읽히면 틀린 해석을 고른 실패는 오히려 늘었다. Anthropic 의 가이드와 블로그는 모델의 기본 단계에서 시작해 자기 작업으로 몇 단계를 견주어 보고, 이득을 잰 일에만 xhigh 와 max 를 쓰라고 권한다.

중심 자료는 Claude Code 블로그(claude.dev)의 Engineering 글 「Using Claude Code: Spending your effort」(2026-09-25)다. 글쓴이 Thariq Shihipar 는 Claude 모델을 “우리 모델”이라 부르며 Anthropic 내부 실행 결과를 싣는다. 단계를 재는 방법은 Anthropic 의 Opus 5.5 prompting guide 와 Claude Code 팀 Lydia Hallie 의 블로그 글에서 옮겼고, Claude Code 와 Claude API 의 effort 공식 문서를 함께 읽었다. 모두 2026-10-25 에 읽은 판이다.

높은 단계는 파일을 더 읽고 테스트를 더 돌린 뒤 돌아온다. 낮은 단계는 스스로 알아내기보다 사용자에게 맥락을 묻는다

블로그 §What is effort?, Claude Code 팀 블로그

작업의 모양이 바뀐다
  • 테스트를 한 번 더 돌린다
  • 다른 방법으로 답을 맞춰 본다
  • 말하지 않은 부분을 스스로 정한다
  • 원문에는 이 그림이 없다. 네 자료가 각자 설명한 층을 한 그림에 모았고, 어느 층이 어느 행동을 낳는지는 원문이 나누지 않는다.
  • 글쓴이 Thariq 는 effort 를 시간 약속에 빗댄다. 12시간을 주면 공들여 해 달라는 뜻으로, 1시간을 주면 쓸 만한 판을 먼저 내고 고쳐 가자는 뜻으로 받아들이는 것과 같다고 한다.
  • Claude Code 팀 블로그는 높은 단계에서도 쉬운 일에 토큰을 일부러 부풀리지는 않는다고 덧붙인다.

그래서 단계를 올린 결과는 답이 길어지는 데서 그치지 않고 작업의 모양이 바뀌는 데서 드러난다.

원문

Claude API 문서 §Effort levels: “Effort is a behavioral signal, not a strict token budget. At lower effort levels, Claude still thinks on sufficiently difficult problems, but thinks less than it would at higher effort levels for the same problem.”

Claude Code 팀 블로그: “At a higher effort, Claude will take more of those actions (for example, read files, run tests, and double-check) before it comes back to you. At lower effort, it would rather ask you for more context than spend tokens figuring something out on its own.”

블로그 §What is effort?: “Claude will always try and do your task reasonably, but higher effort will involve Claude taking more independent action for judgement and verification.”

높은 단계에서 틀린 해석을 고른 실패만 세 모델 모두 늘었다

Fable 5.1 을 low 에서 max 로 올리자 edge case 를 놓친 실패는 59건에서 24건으로 줄었다. 과제 설명을 달리 읽을 여지가 있을 때 테스트와 다른 쪽을 고른 실패는 25건에서 47건으로 늘었다.

  • Opus 5 의 max 는 effort 이름이 max 인 실행이다. 곡선 그림이 쓰는 effort-120 실행으로 세면 놓친 edge case 는 63건에서 39건, 틀린 해석은 28건에서 41건이다.
  • edge case 를 놓친 실패에는 자기 테스트가 못 잡은 버그, 보이는 예시에만 맞춘 코드, 정확히 같지 않은 출력, 자기 환경에서만 돈 코드가 들어간다.

글쓴이는 틀린 해석 칸을 따로 풀이하지 않는다. 높은 단계의 Claude 가 사용자 대신 더 많이 가정한다는 그의 관찰과는 맞는다. 다만 시도 하나에는 실패 종류가 하나만 붙으므로, edge case 를 고친 시도가 다음 걸림돌인 해석 문제로 다시 분류되었을 수도 있다. 어느 쪽이든 요구가 모호한 일에서는 단계를 올려도 이 실패가 줄지 않았으므로, 명세를 채우는 쪽이 먼저다.

단계를 올린 효과는 하드웨어와 보안 과제에서 가장 컸다

Fable 5.1 의 하드웨어 과제는 34% 에서 75% 로, 보안 과제는 64% 에서 87% 로 올랐다. 운영과 미디어 과제는 높은 단계에서도 30% 이하에 머문다.

  • 글쓴이는 검증과 edge case 시험이 쓸모 있는 하드웨어, 코드 리뷰, 보안에서 높은 단계가 더 나은 결과를 냈다고 쓴다. 그림에 코드 리뷰 분야는 없다.
  • 운영 과제는 회사의 월말 EU 무역 통계 신고를 끝까지 처리하는 식이다.

개발자 일에 가장 가까운 소프트웨어 분야(20과제)는 43% 에서 56% 로 13%p 올랐다. 운영 과제가 낮게 머무는 것은 확인을 더 해도 모델이 모르는 규칙은 채워지지 않기 때문으로 읽힌다. 이 풀이는 원문에 없다.

Fable 5.1 은 제품의 안전 개입을 끈 상태로 돌렸다. Opus 5.5 는 곡선 그림에만 있어서 실패 종류와 분야 분석은 다른 모델의 결과다.

  • 그림마다 다른 기준곡선 그림은 Fable 5.1 low 를 약 32% 로 그리는데, 실패 종류 그림은 370번 중 140번(37.8%) 통과로 센다. 실패 종류 데이터에서 Fable 5.1 은 xhigh 217번, max 214번으로 max 가 낫지 않은데 곡선 그림은 max 를 위에 그린다. 그래서 Fable 5.1 에서는 xhigh 부터 시험한다.
  • 측정한 모델결과가 있는 모델은 Opus 5.5, Fable 5.1, Opus 5, Fable 5 다. Sonnet 5.5 나 Haiku 5.5 를 쓴다면 11장의 순서로 단계를 직접 잰다.
  • 내부 실행과제당 5번씩 돌렸다. Claude 제품에서는 Fable 5.1 의 보안 요청 일부가 Opus 로 넘어가므로, 보안 과제의 수치를 제품에서 그대로 기대하지 않는다. 보안 과제는 인터넷 없이 돌려서 공개 리더보드와도 맞지 않는다.
  • Opus 5.5 의 빈칸실패 종류와 분야 그림에는 Fable 5.1, Opus 5, Fable 5 탭만 있다. Opus 5.5 에서도 놓친 edge case 가 줄고 틀린 해석이 느는지는 사례 세 개로만 짐작한다.
  • 모델 판정실패 종류는 다른 모델이 붙인 분류이고 원문이 근사치라고 밝힌다. 칸 사이의 작은 차이보다 세 모델에서 같은 방향인지를 본다.
  • 골라 온 사례과제별 사례는 글쓴이가 low 에서 실패하고 높은 단계에서 통과한 과제를 골라 실행 하나씩 따라간 것이고, 일부는 중간 단계에서 나왔다. 높은 단계가 한 확인이 통과의 원인이라는 설명은 서술이고 통제된 비교가 아니다.
  • 작은 분야분야별 과제는 4~20개라 미디어(4개)나 하드웨어(5개)는 과제 하나가 통과율을 크게 움직인다.
  • 단계 재기의 두 자료Claude Code 팀 블로그는 2026-07-07 에 Opus 4.8 출시를 두고 쓰였다. 두 질문의 갈래는 특정 모델에 매이지 않지만, 글 속 Opus 4.8 과 4.7 의 비교를 Opus 5.5 에 옮기지 않는다. prompting guide 의 max_tokens 와 cache 조언은 API 요청에 관한 것이라, Claude Code 에서는 11장의 단계 순서만 쓴다.
