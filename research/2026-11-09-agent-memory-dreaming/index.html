dreaming 으로 기억을 고치는 Claude 의 agent memory 설계

Agent 가 일하면서 적는 기억은 앞일을 모른 채 내리는 예측이라 틀리거나 불어나기 쉽다. Anthropic 은 기억을 transcript, 노트, wiki, 매 세션 맥락의 네 층으로 나누고, 사람이 자면서 기억을 정리하듯 세션 사이에 기억을 고치고 엮는 dreaming 을 더했다. 실험에서 dreaming 은 transcript 와 대조해 틀린 노트를 고쳤고, 문서로 엮은 wiki 는 답이 여러 문서에 흩어진 질문에서 이득이 컸지만 한 문서로 답이 나오는 과제에서는 뚜렷한 이득이 없었다. 결과를 따라가면 기억의 질은 얼마나 쌓느냐보다 무엇을 버리고, 맞춰 볼 원본을 남기고, 언제 다시 확인하느냐에서 갈린다.

Anthropic Engineering 의 Lance Martin 이 쓴 블로그 글 「The components of agent memory」(2026-11-06 게시, 2026-11-09 판)다. 글에 나오는 실험은 모두 Anthropic 이 자기 환경에서 돌린 것이다.

사람이 자면서 기억을 정리하듯 agent 도 일할 때 적고 쉴 때 고친다

Lance Martin 은 Kierkegaard 의 말로 글을 연다. 삶은 앞으로 살아야 하지만 이해는 뒤를 돌아볼 때만 된다는 말이다. agent 의 기억을 설계할 때도 같은 곤란이 생긴다. 일하는 도중에는 무엇이 나중에 쓸모 있을지 모르는 채로 적어야 하고, 무엇이 중요했는지는 일이 끝난 뒤에야 보인다.

사람의 뇌는 이 일을 둘로 나눈다. 해마가 경험을 그 자리에서 바로 기록해 곧장 꺼내 쓸 수 있게 하고, 잠을 자거나 조용히 쉬는 동안 해마가 최근 경험을 다시 재생(replay)하면서 그중 일부를 신피질의 오래가는 지식으로 옮긴다. 경험 직전이나 직후의 화학 신호가 기억에 중요하다는 표시를 붙이면, 표시된 기억이 더 자주 재생된다.

Anthropic 은 agent 에도 같은 분업을 쓸 수 있다고 본다. 세션 안에서는 transcript 가 쌓이고 Claude 가 눈에 띄는 것을 노트로 적는다. 세션과 세션 사이에는 Claude 가 그 기록을 다시 읽어 실수를 고치고 새 노트와 표현을 만든다. 이 두 번째 일을 dreaming 이라고 부른다. 발상의 뿌리는 Letta 와 UC Berkeley 연구진이 제안한 sleep-time compute 다. 질문이 오기 전에 쉬는 시간을 써서 맥락을 미리 생각해 두는 방법인데, 이 논문은 다음 질문을 예측하기 쉬울수록 효과가 크다고 보고한다.

다음 세션이 읽거나 처음부터 싣고 시작한다

여기서 말하는 agent memory 는 범위가 좁다. Claude 가 사람과의 대화나 맡은 일에서 얻어 세션이 끝난 뒤에도 남기는 지식, 그것도 나중에 읽을 수 있는 맥락으로 저장한 것만 가리킨다. 학습으로 가중치를 바꾸는 것, 한 대화 안에서만 쓰는 in-context learning, 긴 대화의 앞부분을 요약으로 바꾸는 compaction 은 빼 두었다. 그래서 이 글이 말하는 기억은 모두 폴더나 저장소에 글로 남아, 다음 세션이 읽을 수 있다.

세션 안의 Claude 는 앞을 보며 적고, dreaming 은 뒤를 보며 고친다. 4장에서 6장까지가 앞쪽 이야기이고, 7장에서 11장까지가 뒤쪽 이야기다.

기억은 네 층으로 쌓이고 위로 갈수록 작아지며 더 자주 읽힌다

표지의 Figure 1 이 네 층을 보여 준다. 맨 아래 transcript 는 세션에서 일어난 일을 모두 담은 기록이고, 그 위에 Claude 가 골라 적은 노트, 노트와 transcript 를 엮어 만든 wiki 같은 표현, 맨 위에 매 세션 시작에 싣는 맥락이 있다. 층마다 쓰는 쪽과 읽히는 방식이 다르다.

층누가 언제 쓰고, 어떻게 읽나약한 곳
transcript세션이 진행되는 동안 쌓이고, 필요할 때 검색한다찾으려면 검색해야 한다. 지워지면 노트를 맞춰 볼 원본이 사라진다

매 세션 맥락dreaming 이 위로 올리고 harness 가 세션 시작에 싣는다. 검색 없이 늘 보인다매번 토큰을 쓰고, 틀린 내용이 모든 세션에 실려 간다

위로 올라갈수록 읽기는 싸지고 담을 수 있는 양은 줄어든다. 맨 아래 transcript 는 빠진 것이 없지만 찾으려면 검색해야 하고, 맨 위 맥락은 찾을 필요 없이 늘 보이지만 짧아야 한다. 그리고 위층의 내용이 틀리면 그만큼 넓게 퍼진다. CPU cache 와 닮은 구도인데, 이 비유는 글에 없고 표에서 읽어 낸 해석이다. dreaming 이 왜 필요한지가 여기서 드러난다. 위층으로 갈수록 빠르고 위험하니, 누군가 아래층의 원본과 맞춰 봐야 한다.

Claude Code 를 쓰고 있다면 이 구조의 일부를 이미 갖고 있다. Claude Code memory 문서에 비춰 보면 층마다 이렇게 대응한다.

  • transcript세션 기록이다. 보존 기간(cleanupPeriodDays)이 지나면 Claude Code 가 지운다.
  • 노트프로젝트의 memory 폴더에 쌓이는 topic 파일이다.
  • wiki 같은 표현문서에 해당하는 기능이 없다.
  • 매 세션 맥락memory 폴더의 MEMORY.md 색인 가운데 처음 200줄 또는 25KB 다.

노트를 transcript 와 맞춰 보는 dreaming 단계는 Claude Code 문서에 없다. 12장에서 다시 다룬다.

기억을 적는 일은 다음 세션에 무엇이 필요할지 내다보는 예측이다

규칙 하나를 적어 두는 것은 그 패턴이 다시 나올 거라는 예측이다. 확인한 사실을 적는 것도 다음 세션이 그 사실을 다시 확인하지 않고 믿으리라는 예측이다. Anthropic 은 Claude 가 이 예측을 점점 잘하게 됐다고 보고, 그 변화를 CL-Bench 1.0 으로 보여 준다.

CL-Bench 는 UC Berkeley, UW-Madison, Snorkel AI 의 연구진이 낸 벤치마크로, 앞 과제의 경험을 다음 과제에 쓰는지를 잰다. 같은 모델을 기억 없이(stateless) 돌린 점수와 비교해, 경험에서 얻은 몫과 원래 실력을 나누는 것이 이 벤치마크의 방식이다. Anthropic 이 고른 과제는 데이터베이스를 찾아 질문에 답하는 일이다. Claude 는 질문마다 새 세션에서 시작하고, 이어지는 것은 기억 폴더 하나뿐이다. 답을 내면 정답을 알려 주고, Claude 는 다음 질문을 위해 기억을 적을 수 있다.

이 구조에서는 기억이 배우는 고리를 만들 수 있다. 틀리면 실패를 적고, 왜 틀렸는지 가설을 세우고, 가설을 시험해, 맞는 것을 규칙으로 남긴다.

화면에서 다시 읽을 수 있는 것을 적지 않은 모델이 더 멀리 갔다

무엇을 기억할지 고르는 판단은 Pokémon Red 에서 크게 갈렸다. Anthropic 은 모델마다 읽고 쓸 수 있는 기억 폴더를 주고 게임을 시켰고, Sonnet 3.7 과 Fable 5 를 한 번씩 돌려 약 1만 걸음째의 기억 폴더를 비교했다.

Sonnet 3.7 은 무엇이든 중요할 수 있다고 보고 닥치는 대로 적었다. 싸움 하나, 주운 아이템 하나, 만난 인물 하나마다 파일을 따로 만들었고, 그렇게 225개 폴더에 413개 파일, 977,930자가 쌓였다. 배지는 1개를 땄다. 게임 상태가 계속 바뀌니 자세히 적은 기록은 계속 낡았고, 진행할수록 게임보다 기억을 뒤지는 데 시간을 썼다. 1만 걸음 무렵에는 네 번째 "master" 기억 폴더를 새로 만들었고, 이어진 17걸음 동안 파일 6개를 만들고 9개를 지우면서 게임에서는 한 걸음도 움직이지 않았다.

Fable 5 는 폴더 두 개에 파일 9개, 그리고 맨 위의 global.md 하나를 남겼다. 글자 수는 43,406자로, 나눠 보면 Sonnet 3.7 의 약 23분의 1이다. 배지는 4개를 땄다. global.md 는 현재 목표와 체육관 공략 계획, 기억을 쓰는 자기 규칙을 담은 계기판 노릇을 했다. 가진 돈이나 지도 위의 위치처럼 매 턴 화면에서 읽을 수 있는 것은 적지 않았다. 대신 전략, 계획, 시험해 본 규칙처럼 Claude 가 스스로 알아내야 하고 적지 않으면 사라지는 것을 적었다. 몬스터볼 7개가 연달아 잉어킹(Magikarp)을 놓치자 남긴 "3번 이상 연달아 실패하면 메뉴 사이에 기다림을 넣어 타이밍을 바꿔라, 그렇게 하자 잡혔다" 같은 규칙이 그 예다. Opus 5.5 도 현재 목표와 다음 할 일만 담은 작은 노트를 두고 고쳐 쓰면서 게임을 끝까지 깼다.

다시 알아낼 수 있는 것은 적지 않는다는 기준은 Claude Code 의 auto memory 에도 그대로 들어 있다. Claude Code 문서는 아키텍처, 파일 경로, 디버깅 수정처럼 코드에서 다시 끌어낼 수 있는 것은 Claude 가 기억으로 남기지 않는다고 설명한다.

이 비교는 모델당 한 번씩 돌린 결과이고, 두 모델은 세대가 크게 다르다. 그러니 작은 폴더가 진척을 만든다는 증거로 읽으면 지나치고, 무엇을 적을지 고르는 판단과 게임 실력이 함께 좋아진 결과로 읽는 편이 안전하다. 그래도 Sonnet 3.7 이 17걸음을 기억 정리에만 쓴 장면은 기억이 많을수록 좋다는 생각이 어디서 깨지는지를 분명히 보여 준다.

강한 모델에는 기억의 목적만 알리고 약한 모델에는 방법까지 알린다

Anthropic 이 찾은 원칙은 기억이 무엇을 위한 것인지는 알려 주되 어떻게 쓸지는 정해 주지 않는 것이다. CL-Bench 에서는 기억 폴더가 있다는 사실만 알렸고, Opus 4.7 과 Opus 5 는 그것만으로 기억을 잘 써서 점수가 뚜렷이 올랐다.

반대로 무엇을 적을지 규칙을 정해 주면 어떻게 되는지도 시험했다. 규칙 하나씩을 걸고, 그 규칙이 있을 때 기억이 더해 준 몫이 규칙 없을 때보다 얼마나 변했는지를 쟀다. "실패만 기록하라"는 규칙을 걸자 Opus 5 의 몫은 0.234, Opus 4.7 의 몫은 0.150 줄었다(각각 3회 실행). Anthropic 은 강한 모델일수록 무엇이 중요한지 스스로 판단하게 두는 편이 미리 정한 규칙보다 낫고, 규칙이 오히려 성능을 깎을 수 있다고 결론짓는다.

오래된 모델은 사정이 달랐다. Sonnet 4.6 은 기억 폴더를 자주 읽지 않았고 틀린 이유에 대한 가설을 시험하지도 않았다. 그래서 답하기 전에 기억 파일을 읽고 가설을 직접 시험하라고 지시하자 점수가 0.330 에서 0.641 로 거의 두 배가 됐다(기억만 준 경우는 0.364). 두 가지 지시를 한꺼번에 바꿨으니 어느 쪽이 효과를 냈는지는 나눌 수 없고, 3회 실행의 편차 막대도 넓다. Sonnet 5 는 시키지 않아도 10번 중 9번은 답하기 전에 기억을 읽었고, Sonnet 4.6 은 절반이 안 됐다.

지금 Anthropic 은 최신 모델에게 사람이 부탁하거나 분명히 기억할 만한 것이 있을 때 노트를 만들라는 정도로만 안내하고, 나머지 판단은 Claude 에게 맡긴다.

dreaming 으로 쌓은 wiki 는 search 와 함께 쓸 때 가장 도움이 됐다

여기서부터 dreaming 이 하는 일의 재료가 바뀐다. Mt Moon 에서는 Claude 가 자기 세션의 transcript 를 다시 읽었다. 이번 실험들에서는 Claude 가 지난 경험 대신 바깥 문서 더미를 세션을 거듭하며 읽고 wiki 로 엮는다. 둘 다 세션 바깥에서 연산을 들여 기억을 정리한다는 점에서 같은 이름을 쓰지만, 맞춰 보는 기준이 하나는 transcript, 하나는 원본 문서다.

wiki 는 Claude 가 쓰고 관리하는 페이지 묶음으로, 한 주제에 대해 아는 것을 모으고 다른 노트로 링크를 잇는다. 이 링크가 지도 노릇을 해서, 기억이 커져도 필요한 것을 찾아갈 수 있다. 글은 wiki 라는 말에 Andrej Karpathy 의 LLM Wiki 를 링크해 두었다.

Anthropic 은 5월에 인수한 소프트웨어 회사 Stainless 의 내부 문서 약 35만 개, 약 4억 2천만 토큰으로 이를 시험했다. 이 문서에 대한 질문 25개를 만들고 Claude 에게 search 도구를 줬다. 그리고 Opus 5 agent 들에게 128번의 세션에 걸쳐 파일을 탐색하고, 링크된 wiki 페이지를 쓰거나 고치고, 중복을 합치고, 주장을 원본과 대조하게 했다. 세션마다 공유 로그로 앞선 세션의 진척을 이어받았다.

wiki 만으로 답하게 하면 채운 채점 기준이 2세션 뒤 13% 에서 128세션 뒤 48% 로 올랐다. 그래도 search 만 쓴 53% 에는 못 미친다. wiki 가 가장 쓸모 있었던 것은 search 와 함께 쓸 때로, wiki 가 자라면서 54% 에서 61% 까지 올랐고 질문당 약 2만 토큰을 아꼈다. wiki 는 search 를 대신하지 못했고, search 곁에서 찾아갈 길을 알려 주는 지도 노릇을 할 때 가장 쓸모 있었다.

비용 쪽은 대략만 가늠할 수 있다. 128세션에 세션당 1M 토큰이면 예산은 128M 토큰이고, 질문당 2만 토큰을 아낀다면 약 6,400개 질문을 받아야 예산만큼을 되찾는다. 예산이 실제 사용량이 아니고 모델과 단가도 따지지 않은 상한이라 정확한 손익은 아니다. 다만 같은 문서 더미에 질문이 많이 몰릴수록 wiki 가 제값을 한다는 방향은 분명하다. sleep-time compute 논문도 맥락 하나에 관련 질문이 10개 올 때 미리 생각해 둔 비용을 나눠, 질문당 평균 비용을 질문이 하나일 때보다 최대 2.5배 낮췄다고 보고한다.

Karpathy 의 LLM Wiki 는 지식을 한 번 엮어 두고 계속 최신으로 유지해, 질문마다 원문에서 다시 끌어내지 않게 하자고 제안한다. 그는 색인 하나로 찾아가는 방식이 출처 100개 안팎, 페이지 수백 개 규모에서 잘 통한다고 적었다. 35만 개 파일 규모의 Anthropic 실험에서는 wiki 혼자서는 search 를 넘지 못했고 둘을 함께 쓸 때 가장 좋았다. 두 글이 다룬 규모가 다르므로, 규모가 커지면 wiki 옆에 search 를 남겨 두라는 조건이 붙는다고 읽으면 두 글이 함께 선다. 이 비교는 두 글을 나란히 놓고 한 것이다.

매 세션에 싣는 맨 위층은 색인처럼 작게 지킨다

dreaming 은 노트를 기억 계층의 맨 위로 올릴 수도 있다. 맨 위에 오른 노트는 harness 가 세션 시작마다 Claude 의 맥락에 미리 싣는다. 그러면 Claude 는 그 노트를 찾을 필요가 없고, 찾을 것이 있다는 사실을 알 필요조차 없다.

대신 대가가 있다. 실린 기억은 매번 토큰을 쓰고, 틀린 노트는 모든 세션에 실려 간다. 실었다고 Claude 가 따른다는 보장도 없다. Claude Code 문서는 지시 파일이 길수록 맥락을 더 쓰고 지시를 따르는 정도가 떨어진다고 경고한다. 그래서 맨 위층은 작아야 하고, dreaming 이 여기서 하는 일의 대부분은 자세한 내용을 아래층으로 내리고 그 자리에 링크만 남겨 이 층을 작게 지키는 것이다.

Claude Code 의 auto memory 가 바로 이렇게 맨 위층을 작게 지킨다. MEMORY.md 의 처음 200줄이나 25KB 만 세션에 싣고, 이 머리 부분은 Claude 가 무엇을 알고 그것이 어디 있는지 보여 주는 색인 노릇을 한다. 파일이 한도에 가까워지면 Claude Code 가 Claude 에게 한 줄에 한 항목만 두고 자세한 내용은 topic 파일로 옮기며 낡은 항목은 합치거나 지우라고 알린다. 차이는 이 일을 누가 언제 하느냐다. Claude Code 에서는 dreaming 이 아니라 세션 안의 Claude 가 이 층을 관리한다.

Claude Code 문서 §How it works: “If the file is near a limit, Claude Code reminds Claude to shorten it: keep one line per entry, move detail into topic files, and merge or drop stale entries.”

페이지마다 쓰는 쪽을 하나로 정하고 계약 조건을 글자 그대로 옮기자 하나도 빠지지 않았다

dreaming 은 기억이 자라는 방향도 정할 수 있다. 무엇이 정말 중요한지는 과제마다 다르니, wiki 를 만드는 지시에 그것을 담아야 한다. LAB 의 기업 인수 과제가 그 예다. 계약서 묶음을 주고 브리프를 쓰게 한 뒤 계약 조건을 정확히 옮겼는지로 채점한다.

처음에는 wiki 를 어떻게 쓸지 말하지 않은 기본 지시로 시작했다. wiki 를 만드는 동안 agent 여럿이 계약 조건을 모은 공유 표 하나에 동시에 썼고, 한 agent 가 저장하면 다른 agent 가 쓴 줄이 지워졌다. 그렇게 만든 wiki 로 쓴 브리프는 채점 대상 사실 57개 중 41개(72%)만 담았다. 표는 계약 조건을 엉성하게 요약했고 일부는 아예 빠뜨렸다.

계약 조건이 wiki 에서 가장 중요한 부분인데 지시는 그 말을 하지 않았다. 더 나은 지시를 찾으려고 Anthropic 은 Claude 가 실패를 돌아보고, 지시를 고치자고 제안하고, wiki 를 다시 만드는 loop 를 돌렸다. Claude 는 이 과정에서 계약 조건을 그대로 따르는 것이 중요하다는 것을 찾아내고 지시를 다시 썼다. 새 지시에서는 계약서마다 페이지를 하나씩 두고 agent 하나만 그 페이지를 쓰며, 조건을 표로 요약하지 않고 원문 그대로 옮긴다. 이 wiki 로 쓴 브리프는 57개를 모두 채웠다.

새 지시는 두 가지를 한꺼번에 바꿨다. 페이지마다 쓰는 agent 를 하나로 정해 서로 덮어쓰는 일을 없앴고, 요약 대신 원문을 옮겨 요약하며 잃는 것을 없앴다. 어느 쪽이 얼마나 기여했는지는 글로는 나눌 수 없다. 앞쪽은 여러 agent 가 같은 파일을 쓸 때 생기는 동시성 문제라서, 여러 agent 로 wiki 를 만든다면 과제와 상관없이 챙겨야 하는 규칙이다.

dreaming 은 세션 하나가 남긴 빈틈도 메운다. 노트를 쓰는 Claude 는 그 세션의 맥락만 보지만, dreaming 은 여러 세션을 훑어 공통 패턴이나 되풀이되는 실수를 찾을 수 있다. LAB wiki 를 만들 때 Claude 가 아직 없는 페이지로 링크를 거는 일이 있었는데, 두 번째 dreaming 과정이 이런 빈틈을 많이 메웠다. 한 과제에서는 페이지 여섯 개에서 나온 링크 9개가 없는 페이지 escrow-agreement 를 가리키고 있었고, dreaming 이 이를 같은 문서를 다루는 기존 페이지 buyer-form-escrow-agreement 로 돌렸다. 색인을 포함해 새 페이지 3개도 더했다. Karpathy 가 LLM Wiki 에서 주기적으로 돌리라고 한 lint, 곧 고아 페이지와 모순과 낡은 주장을 찾는 점검과 같은 일이다.

제품으로 쓸 수 있는 dreaming 은 Managed Agents 의 research preview 다

앞 장들의 dreaming 을 정리하면 두 종류다. 하나는 자기 경험을 되짚는 일로, Mt Moon 처럼 기억을 그 세션의 transcript 와 맞춰 고친다. 다른 하나는 바깥 문서를 엮는 일로, Stainless 와 LAB 처럼 원본 문서를 읽어 wiki 를 쌓는다. Anthropic 은 둘을 같은 이름으로 부르는데, 쓰는 쪽에서는 재료와 기준이 다르니 따로 준비해야 한다. 이 구분은 글에 없는 정리다.

제품으로 쓸 수 있는 것은 앞쪽이다. Claude Platform 문서의 Dreams 는 Managed Agents 의 research preview 기능이고, 쓰려면 접근을 따로 신청해야 한다. dream 하나는 기존 기억 저장소 하나와 지난 세션 1개에서 100개를 받아, 중복을 합치고 낡았거나 서로 어긋나는 항목을 최신 값으로 바꾸고 새 통찰을 더한 새 저장소를 만든다. 입력 저장소는 건드리지 않으므로 결과를 검토한 뒤 쓰거나 버리면 된다. 비동기로 돌며 보통 몇 분에서 몇 시간이 걸리고, 비용은 입력 세션의 수와 길이에 거의 비례한다. instructions 로 "코딩 스타일 선호에 집중하라" 같은 방향을 줄 수 있지만, 특정 문장을 고치라는 식의 지시는 대개 아무것도 바꾸지 않는다고 문서는 설명한다. 문서를 엮어 knowledge wiki 를 만드는 쪽은 Anthropic 이 cookbook 으로 안내한다.

Claude Code 쪽 사정은 다르다. Claude Code memory 문서에는 dreaming 단계가 없고, MEMORY.md 는 세션 안의 Claude 가 관리한다. 게다가 Claude Code 는 보존 기간(cleanupPeriodDays)이 지난 세션 transcript 를 지우고 memory 폴더의 파일만 남긴다. 노트를 맞춰 볼 원본이 기본 설정에서는 사라진다는 뜻이다. Managed Agents 의 세션은 지울 때까지 transcript 가 남는다.

남는 질문은 무엇을 적고 버리며 언제 다시 확인하느냐다

Anthropic 은 결론에서 열린 질문을 셋 남긴다. 첫째는 기억을 언제 만드느냐다. 일하는 도중에 적으면 중요한 것을 그 자리에서 잡아 다음 턴부터 쓸 수 있지만, 적는 동안 본래 일에서 주의가 빠진다. dreaming 으로 미루면 일은 방해받지 않지만 결과가 바로 쓰이지 않는다. 둘째는 기억을 어떻게 최신으로 지키느냐다. dreaming 은 연산이 들고 모든 기억을 늘 다시 확인할 수는 없으니, 바뀌기 쉬운 정보에 집중하거나 기억이 얼마나 자주 읽히는지에 맞춰 주기를 정해야 할 수 있다. 셋째는 transcript search 자체를 기억의 바탕으로 삼는 길이다. wiki 같은 표현을 search 와 함께 쓰면 효과가 있을 때가 있지만, 그 표현에 오류와 환각이 쌓이지 않게 지키는 데 연산이 든다.

세 질문을 한데 묶어 읽으면, 기억을 얼마나 많이 쌓느냐보다 무엇을 버리고 언제 다시 확인하느냐가 기억의 질을 정한다는 데로 모인다. Anthropic 은 이것을 질문으로 남겨 두었고, 이렇게 묶은 것은 해석이다. 앞 장들의 결과를 이 질문에 맞춰 할 일로 옮기면 아래와 같다. 근거 칸에 Anthropic 권고나 제안이라고 적은 줄은 Anthropic 이 직접 권하거나 제안한 것이고, 나머지는 실험 결과에서 끌어낸 정리다.

수치는 모두 Anthropic 이 자기 환경에서 잰 값이다

  • Anthropic 이 직접 돌린 실험CL-Bench 는 바깥 벤치마크지만 돌린 쪽은 Anthropic 이고, Pokémon, Stainless, LAB 실험의 설정과 프롬프트는 글에 다 나오지 않는다. Stainless 문서는 내부 자료라 밖에서 되풀이할 수 없다. 숫자는 방향을 읽는 데 쓰고, 자기 일에 들일지는 작은 규모로 직접 재 보고 정하는 편이 맞다.
  • 계산하고 해석한 부분CL-Bench 의 차이 열, 약 6,400개 질문이라는 손익 가늠, 층을 cache 에 빗댄 해석, Mt Moon 에서 노트가 전제였다는 해석, dreaming 의 두 종류 구분, Karpathy 와의 비교는 글에 없다. 각 장에서 그렇게 밝혔다.
  • 돌려 보지 않았다Dreams API 는 research preview 라 실제로 호출해 보지 않았고, 동작은 문서의 설명이다. 글이 안내한 dreaming 과 knowledge wiki 의 cookbook 도 열지 않았다.
