subagent 를 main agent loop 로 fold 하라는 Anthropic 글이 기존 하네스 설계에서 바꾸는 것

Anthropic 의 「When to fold subagents into your main agent loop」는 router, planner, 팀별 subagent 를 main agent 하나의 loop 에 합치라고(fold) 권한다. 글을 쓴 팀은 agent 를 나누던 주된 이유를 skill 과 tool search 가 덜어 준다고 보고, 이미 있는 subagent 는 합친 쪽이 eval 에서 더 나쁠 때만 남기라고 한다. 이 글은 업계 문서를 언급하지 않지만, CrewAI 나 OpenAI Agents SDK 문서가 역할마다 전문 agent 를 두라고 가르치는 것에 대면, 남을 근거를 댈 쪽은 subagent 다.

Anthropic 의 Diane Sarkis 가 claude.com 에 쓴 글(2026-10-22 게시)이고, Anthropic Applied AI 팀이 기업 배포에서 본 패턴을 정리했다. 한국어판 URL 이지만 본문은 영어다. 2026-10-25 사본 기준이다. 맞대어 보려고 LangChain·LangGraph, CrewAI, AutoGen, OpenAI 의 multi-agent 문서와 가이드, 같은 주제의 Anthropic 이전 글 일곱 편, Cognition 의 글 한 편, 글에 딸린 migration kit 저장소를 함께 읽었다.

팀마다 subagent 를 두면 agent 구조가 조직도를 그대로 닮는다

Applied AI 팀은 여러 제품을 한 고객 창구로 묶으려는 큰 조직에서 이 구조를 자주 본다. 각 기능을 맡은 팀이 자기 agent 를 만들고, 중앙 플랫폼 팀이 그 위에 orchestrator 를 얹는 순서다.

팀별 agent 위에 중앙 orchestrator

agent 구조가 조직도의 복사본이 된다. Conway 의 법칙이 작동한 결과다

머리말, §Agent building failure modes for large organizations

context 관리

agent 사이에 무엇을 넘길지 정해야 하고, 주고받는 동안 세부가 빠진다

subagent 난립

겹치는 subagent 가 수백 개로 늘고, 강제되는 표준도 정해진 주인도 없다

Frankenprompt

팀마다 system prompt 에 한 문장씩 보태서 규칙이 부딪치고 목소리가 하나로 모이지 않는다

검토 없이 쪼개진 eval

팀마다 자기 하위 작업에 맞춘 eval 을 더하고, 전체 세트는 아무도 관리하지 않는다

지연

고객 한 곳은 같은 일을 단일 agent loop 로 돌리자 실행 시간이 약 2배 빨라졌다

글에 실린 지연 측정은 이 한 건이다

  • 사례가 하나 더 있다. 전문 subagent 12개를 둔 고객 응대 agent 에서, 그 회사는 브랜드에 맞는 일관된 응대를 유지하기 어려웠고 늘어난 지연이 사용자 경험을 해쳤다.
  • 이 구조는 orchestrator 와 subagent 형태일 수도, 단일 agent 가 다른 팀의 agent 를 MCP tool 로 부르는 형태일 수도 있다.

그래서 이 글이 겨누는 것은 팀 경계를 그대로 agent 경계로 옮기는 설계 습관이다. subagent 자체는 검증, 병렬 작업, 권한 분리에 쓸모 있다는 점을 글머리에서 먼저 인정한다.

같은 절: “The Frankenprompt: Every team adds a sentence to the system prompt, resulting in conflicting rules and no consistent voice.”

업계 문서는 전문 agent 를 supervisor 나 handoff 로 엮는 법을 가르친다

실무자가 multi-agent 를 배우는 LangChain·LangGraph, CrewAI, AutoGen, OpenAI 의 문서에서 구조마다 가르치는 문장을 모았다. 2026-10 글은 이 문서들을 언급하지 않고, 자기 권고를 이 구조들과 견주지도 않는다.

구조업계 문서가 가르치는 방식
역할마다 agentCrewAI 의 agent 는 crew 안의 기능과 전문성을 정하는 role, 성격을 주는 backstory 를 갖는다. AutoGen 의 예제는 web search tool 하나, 계산 tool 하나에 agent 를 하나씩 둔다. OpenAI Agents SDK 문서는 무엇이든 해야 하는 범용 agent 대신 한 가지를 잘하는 전문 agent 를 두라고 한다
supervisor 와 managerLangGraph 의 supervisor 는 모든 통신과 위임을 정하고, supervisor 를 거느린 supervisor 로 research_team, writing_team 같은 층을 쌓는다. CrewAI 의 hierarchical process 는 회사 위계를 본뜬 manager 가 계획, 위임, 검증을 맡는다. OpenAI 가이드의 manager pattern 은 전문 agent 를 tool 로 부른다
handoff 와 group chatOpenAI 가이드의 decentralized pattern 은 agent 끼리 전문 분야를 따라 일을 넘기고, 예로 sales 와 support 를 나눈 고객 응대를 든다. AutoGen 의 SelectorGroupChat 에서는 모델이 공유된 대화를 보고 다음에 말할 agent 를 고른다
router 와 고정 pipelineOpenAI Agents SDK 의 code orchestration 은 agent 가 task 를 분류하게 한 뒤 그 범주로 다음 agent 를 고르거나, 조사, 개요, 작성, 비평을 agent 사슬로 잇는다. CrewAI 의 기본값인 sequential process 는 앞 task 의 출력을 다음 task 의 context 로 넘긴다
  • Anthropic 의 앞선 글도 이 흐름의 한 줄기다. 2024-12 글은 routing 과 orchestrator-workers 를 workflow 로 소개했다. 2026-01 글은 context 오염, 병렬화, 전문화를 multi-agent 가 이기는 상황으로 꼽았다. 2026-04 글은 multi-agent 를 고른 팀에게 대부분의 경우 orchestrator-subagent 로 시작하라고 권했다.
  • 반대 목소리도 있었다. Cognition 의 2025-06 글은 OpenAI 의 swarm 과 Microsoft 의 autogen 이 multi-agent 구조를 민다고 비판하고, context 와 agent trace 전체를 공유하라고 했다.
  • 업계 문서도 단일 agent 를 먼저 권한다. OpenAI 가이드는 단일 agent 의 능력부터 최대로 키우라고 하고, LangChain 문서는 맞는 tool 과 prompt 를 가진 단일 agent 가 비슷한 결과를 낼 때가 많다고 적는다. LangChain 은 skill 을 multi-agent 패턴의 하나로도 싣는다.
  • supervisor 의 모양도 바뀌었다. langgraph-supervisor 의 README 는 이제 대부분의 경우 라이브러리 대신 supervisor 를 tool 로 부르는 방식을 권한다.

그래서 단일 agent 부터 키우라는 말은 업계 문서에도 이미 있다. 업계 문서가 agent 를 나누라고 하는 조건은 4장에, 하네스가 정해 두던 경로는 5장에 2026-10 글의 새 자리와 짝지어 놓았다.

agent 를 나누던 전문화 이유는 skill 과 tool search 로 옮겨 간다

Anthropic 의 2026-01 글과 업계 문서는 tool 이 많을 때, 지시가 부딪치거나 복잡할 때, domain 지식이 클 때 agent 를 나누라고 한다. 2026-04 글은 message bus 패턴의 장점으로, LangChain 문서는 multi-agent 를 찾는 이유로 팀별 독립 개발을 들고, 아래 표는 이 이유마다 2026-10 글과 migration kit 이 주는 새 자리를 짝지어 놓았다.

나누던 이유예전 권고새 자리
domain 지식이 크다domain context 를 한 agent 에 다 싣기보다 전문 agent 가 나눠 든다 (2026-01). LangChain 문서도 긴 prompt 와 domain tool 이 드는 전문 지식을 이유로 든다skill 로 옮긴다. 평소에는 짧은 설명만 context 에 있고, 필요할 때 본문을 읽는다. Skills 글은 metadata 를 약 50 토큰, SKILL.md 본문을 약 500 토큰으로 잡는다
tool 이 많다tool 이 흔히 20개 이상이면 고르기 어렵다. 40개 이상의 tool 을 가진 예에서는 전문 agent 로 나눠 선택 오류를 풀었다 (2026-01). OpenAI 가이드는 겹치는 tool 이면 10개 미만에서도 헤맨다고 보고, tool 설명을 고쳐도 나아지지 않으면 나누라고 한다tool search 와 deferred loading 으로 정의를 필요할 때 불러온다. tool 은 API 마다 하나씩 두지 말고 사용자 의도별로 묶는다. system prompt 에 실린 정의가 30-50개를 넘으면 선택이 나빠진다
행동 방식이 부딪친다공감하는 상담과 엄격한 코드 리뷰처럼 모드가 부딪치면 prompt 를 따로 둔 agent 로 나눈다 (2026-01). OpenAI 가이드는 prompt 에 if-then-else 분기가 많아지면 논리 단위마다 agent 로 나누라고 한다목소리는 main system prompt 하나가 맡고, 작은 중앙 팀이 그 prompt 를 소유한다. kit 은 agent 하나에 목소리 하나라고 적는다. skill 로도 풀리지 않는 지시 충돌만 6장의 조건으로 남는다
맡은 팀이 다르다message bus 에서는 팀이 agent 를 따로 개발하고 배포할 수 있다는 점을 장점으로 든다 (2026-04). LangChain 문서는 팀마다 기능을 따로 개발하고 유지하는 것을 multi-agent 를 찾는 이유로 들면서, skill 패턴에도 같은 점수를 준다팀은 agent 대신 skill, tool, eval 을 소유한다. kit 은 다른 팀이 맡았다는 사실을 따로 context 를 둘 이유로 치지 않는다
  • tool 수 기준은 2026-01 글에서 흔히 20개 이상, 다른 절에서는 15-20개 이상이었고, 2026-10 글은 30-50개를 적는다. 두 글은 세는 대상을 다르게 적는다. 앞의 것은 한 agent 가 가진 tool 이고, 뒤의 것은 system prompt 에 실린 tool 정의다. tool search 로 정의를 미뤄 부르면 두 수가 갈라지므로, 이 차이를 기준이 올라간 정도로 바로 읽지 않는다. 두 숫자를 나란히 놓은 비교는 어느 글에도 없다.
  • tool search 는 2026-01 글도 multi-agent 로 가기 전에 먼저 써 보라고 권했고, 토큰을 최대 85% 줄인다고 적었다.
  • Claude Code 의 system prompt 를 80% 넘게 줄인 일에는 skill 과 tool 을 progressive disclosure 로 바꾼 몫이 들어 있다.

그래서 agent 를 나눌 근거가 이 넷 가운데 하나뿐이라면, 2026-10 글의 기준으로는 나눌 근거가 되지 못한다. 남는 근거는 6장의 조건이다.

하네스가 코드로 정해 두던 판단은 매 턴 모델이 내린다

3장의 router, pipeline, manager 와 Anthropic 2024-12 글의 workflow 는 미리 정한 코드 경로나 따로 둔 agent 로 모델과 tool 을 엮는다. Applied AI 팀은 그 경로가 하던 판단을 매 턴 모델에게 넘기고, 코드에는 기계적인 일과 강한 제한만 남긴다.

tool 묶음, 사용자에게 질문, 답 가운데 하나다. 2026-09 commerce 글의 agent 앞에는 intent router 가 없다

단계를 코드로 정해 두고 앞 단계의 출력을 다음 단계에 넘긴다

CrewAI 의 sequential process, OpenAI SDK 의 agent 사슬

tool 이 사용자별 권한을 확인하고 모델이 읽을 거절을 돌려준다

  • 모델이 매 걸음을 정하므로 규칙 목록으로 계획을 다시 쓰는 코드 단계는 필요 없다. 값싸고 거의 늘 필요한 load(예: entity resolution)는 코드로 남겨도 된다.
  • 권한을 tool 이 확인하므로 권한 수준마다 agent 를 따로 두지 않아도 한 loop 가 접근 범위가 다른 사용자를 받는다.

그래서 하네스가 맡는 일은 모델이 할 판단을 미리 정해 두는 일에서, 모델이 넘으면 안 되는 선을 강제하는 일로 좁아진다. 새 모델이 나올 때마다 판단을 더 옮길 수 있고, Anthropic 이 도운 고객 이행에서는 경직된 multi-agent 구조가 새 모델이 일을 더 맡는 것을 자주 막았다.

MCP toolagent 가 행동을 하거나, 시스템의 실시간 데이터를 읽거나, 정해진 모양의 결과를 돌려줘야 할 때. 이행 중에는 subagent 를 계속 부르는 통로로도 쓴다사용자 의도별로 묶는다. 앞 tool 의 출력이 필요한 tool 은 그것이 있는지 스스로 확인하고 모델이 따를 지시를 돌려준다
skill팀이 일하는 방식이 필요할 때. 예전에 전문 subagent 의 prompt 가 담던 단계, 규칙, 판단이다팀마다 DRI 가 자기 skill 을 맡아 서로 겹치지 않게 다듬고 eval 과 함께 내보낸다. /skill-doctor 로 skill 마다 비용과 실제 사용 빈도를 보고 안 쓰는 것을 지운다
knowledge base가끔만 필요한 참고 자료일 때. 정책, 지표 정의, 제품 사양이 예다모델이 부르는 검색이나 조회 tool 뒤에 두거나 skill 의 참고 파일로 싣는다. 코드가 가져와 prompt 에 붙여 넣는 방식은 피한다
  • 2026-09 commerce 글은 system prompt 와 skill 의 경계로 출발점 하나를 준다. 트래픽의 1/3 이상에 걸리는 것은 system prompt 에 두고 나머지는 skill 에 둔다.
  • 2026-01 글이 multi-agent 의 장점으로 든 전문가 협업 비유는 이 표에서 팀이 소유한 skill 과 tool 로 바뀐다. 팀의 전문성은 남고, 팀마다 따로 있던 context 와 목소리가 사라진다.

그래서 큰 조직에서 달라지는 것은 팀이 내보내는 산출물의 단위다. 팀이 내보내던 agent 가 skill, tool, 그리고 거기 딸린 eval 이 된다.

skill 을 가진 단일 agent 가 낫다는 비교는 숫자 없이 Anthropic 의 관찰로만 제시된다

아래 한계는 이 권고를 자기 시스템에 옮길 때 무엇부터 재야 하는지로 이어진다. 2026-10 글과 kit 이 모두 Anthropic 의 자료라는 점이 바탕에 있다.

  • 숫자 없는 비교skill 을 가진 단일 agent 가 품질에서 앞섰다는 비교는 ‘여러 기업 배포’라고만 적고 배포 수, 과제, 점수를 밝히지 않는다. 링크된 commerce 글의 같은 문장도 숫자가 없다. 그래서 자기 시스템의 eval 로 재기 전에는 이 결론을 가설로 둔다.
  • 한 단계 낮아진 표현2026-09 commerce 글은 같은 비교를 consistently 앞섰다고 적었고, 2026-10 글은 frequently 앞섰다고 적는다. 권고대로 subagent 마다 재는 편이 안전하다.
  • 지연 2배는 고객 한 곳지연 숫자는 고객 한 곳이 잰 약 2배뿐이고, 그 시스템의 규모와 과제는 나와 있지 않다. 자기 시스템의 지연은 eval 실행에서 직접 잰다.
  • 사례가 고객 응대에 쏠려 있다2026-10 글, commerce 글, kit 의 예제가 모두 고객 응대나 상거래 agent 다. 넓게 병렬 탐색하는 research 에서는 2025-06 글이 multi-agent 가 90.2% 높았다고 했고, Applied AI 팀도 research frontier 에 subagent 의 자리가 있다고 인정한다. 넓은 탐색이 핵심인 시스템은 6장의 병렬 조건부터 확인한다.
  • kit 기록은 얇다실제 모델 실행은 한 사람이 한 모델로 두 번 돌린 것이다. merge 단계와 완성된 single_loop 버전은 실제 모델로 돌리지 않았고, kit 은 관리하지 않는 reference implementation 이다. 9장의 숫자는 방향을 보여 주는 예로만 읽는다.
  • 2026-10 글은 합친 뒤의 context 비용을 숫자로 싣지 않았다2026-10 글은 한 context 에 skill 본문과 tool 결과가 쌓이는 비용을 숫자로 보이지 않고, system prompt, context window, memory, 메모를 규율 있게 다뤄야 한다고만 적는다. 반대쪽 계산은 LangChain 문서에 있다. 언어마다 약 2,000 토큰 문서를 둔 세 언어 비교 시나리오에서(측정 방법은 밝히지 않는다), skill 방식은 3번 호출에 약 15K 토큰을, context 를 따로 둔 subagent 방식은 5번 호출에 약 9K 토큰을 처리한다. kit 의 결과 파일에는 행마다 입력 토큰이 남아 있지만 9장은 지연과 호출 수만 합산했다. 긴 대화를 다루는 agent 라면 합친 뒤의 턴당 토큰과 context 길이를 eval 실행에서 함께 잰다.
  • 모델 능력 주장은 자기 평가Opus 4.5 부터 한 loop 에서 훨씬 많은 일을 다룬다는 주장에는 측정 근거가 붙어 있지 않다. 80% 를 줄이고도 잴 만한 손실이 없었다는 결과는 Anthropic 이 자기 코딩 eval 로 잰 것이므로, 다른 영역의 agent 는 prompt 를 줄이기 전과 뒤를 자기 eval 로 비교한다.
  • 업계 대조는 지금 판의 문서에 기댄다3장과 12장의 업계 문서는 2026-10-25 에 받은 판이다. 업계 웹 문서에는 게시일이 없고, OpenAI 가이드는 PDF 정보의 생성일과 수정일이 모두 2025-04-07 이다. 업계 웹 문서의 문장이 언제부터 있었는지는 이 사본으로 가릴 수 없으므로, 3장은 지금 실무자가 읽는 가르침으로 읽는다. 그 framework 로 만든 시스템의 성능도 담지 않으므로, 자기 시스템은 12장의 짝을 대어 본 뒤 eval 로 잰다.
