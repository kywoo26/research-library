소유자가 원하는 것은 두 도구가 같은 연구 절차를 지키면서 역할에 맞게 모델을 위임하는 체계다. 이를 같은 설정 파일이나 같은 모델 이름을 쓰는 것으로 판단하면 실제 차이를 놓친다. 이 감사에서는 아래 조건을 공통 합격 기준으로 삼았다. 각 harness의 기능이 달라도 이 조건을 만족하면 같은 연구 체인으로 사용할 수 있다.

이번에 실행한 check-harness --versions는 정의 일치를 보고했고, 선택한 기존 hook·ship·trust·runner 테스트도 모두 통과했다. 그런데 추가한 작은 재현에서는 보호 창 문제가 드러났다. 따라서 기존 테스트 통과를 전면 호환의 증명으로 쓰면 안 된다. 반대로 이 결함 때문에 공통 스킬 구조 자체를 버릴 이유도 발견하지 못했다.

설치 버전은 Claude Code 2.1.330과 Codex 0.171.0이었다. 대응표의 실측 기준은 각각 2.1.311과 0.164.0이므로 현재 동작의 근거로 그대로 승격하지 않았다. 실제 Codex app-server가 연구 profile의 hook 설정을 읽는 것까지 확인했지만, 설정 조회는 이벤트가 발생하고 연구가 완료되는 시험을 대신하지 않는다.

연구자 진입은 다르지만 집필과 판정은 한 경로를 공유한다

Claude는 named researcher를 별도 worktree에서 실행한다. Codex는 launcher가 worktree와 권한 profile을 준비한 뒤 별도 root 세션을 감독한다. 이 차이는 현재 native agent의 권한과 worktree 지원 차이를 처리하는 어댑터다. Codex의 일반 subagent 정의 하나로 연구자의 독립 권한까지 옮길 수 있다는 근거는 공식 계약에서 찾지 못했다.

Codex launcher는 저장소 profile을 사용자 영역에 복사하면서 hook trust 상태를 보존한다. 현재 hook hash와 trust 기록을 대조한 뒤 실행하며, root turn의 종료만으로 성공이라고 하지 않는다. runner는 출고 게이트, 출고 이후 Stop 게이트, 최종 문서 해시와 열린 PR을 함께 확인한다. 이처럼 모델의 완료 선언을 외부 판정으로 보완하는 부분은 유지할 가치가 있다.

현재 Claude 설정은 검토자 hook을 agent frontmatter 대신 settings에 둔다. 연구자가 검토자를 띄울 때 foreground를 요구하고, 두 lens를 한 메시지에 함께 호출하도록 한다. Codex는 검토자 시작과 완료 이벤트를 직접 기록하며 저자 대화 상속을 막는다. 같은 절차를 위해 native 동작이 다른 지점을 따로 처리하는 것이다.

Claude의 새 AGENTS.md 지원 때문에 bridge가 당장 불필요하다고 결론내리기는 어렵다. 기본 동작은 상위 또는 현재 경로에 CLAUDE.md나 CLAUDE.local.md가 있으면 AGENTS.md 대신 그것을 읽는 방식이다. 반면 이미 CLAUDE.md가 AGENTS.md를 import하면 그 경로로 읽는다. 현재 한 줄 bridge는 이 조건 차이를 피하며 유지 비용도 작다. Claude가 .agents 아래 스킬을 직접 찾는다는 계약은 여기서 확인되지 않으므로 스킬 링크도 유지한다.

같은 파일의 경로 표기와 동시 시작에서 보호 창이 빈다

보호 창은 두 lens가 원고를 읽는 동안 저자가 원고와 근거를 고치지 못하게 하는 장치다. 여기에 두 문제가 있다. 하나는 파일의 실제 위치 대신 상대 경로 문자열을 그대로 비교하는 것이고, 다른 하나는 검토자 대기 목록의 읽기와 쓰기를 한 작업으로 잠그지 않는 것이다. 두 문제 모두 현재 코드로 만든 fixture에서 확인했다.

현재 pretool은 절대 경로만 저장소 상대 경로로 바꾸고, 상대 경로는 그대로 둔다. 그래서 정상 경로는 보호 집합과 일치하지만 앞에 ./가 붙으면 일치하지 않는다. 이 시험은 Codex 입력 형태의 hook 응답을 확인했다. 실제 원고를 수정하거나 PR까지 발행한 시험은 아니다. 상대 경로도 저장소 기준으로 resolve한 뒤 같은 표준 형태로 비교하면 이 차이를 없앨 수 있다.

검토 기록을 쓰는 updateHooks에는 이미 lock이 있다. 그러나 별도 파일인 lens-window의 open·close·변경 알림은 잠금 없이 읽고 수정한 뒤 저장한다. 원본 openWindow를 별도 프로세스에서 함께 호출하자 한 역할이 목록에서 사라졌고, 남은 역할을 닫으면 창도 사라졌다. 파일을 임시 파일로 바꿔 쓰는 것만으로는 충분하지 않다. 두 작업이 같은 옛 값을 읽는 것부터 막아야 한다.

최종 ship에는 검토 전후 보호 집합 해시와 문서 해시를 보는 방어선이 남아 있다. 따라서 이 재현으로 잘못된 ready PR까지 나왔다고 말할 수는 없다. 재현한 문제는 사전 편집 차단과 즉시 알림의 신뢰성이다. 사후 검사가 있으니 그대로 두기보다, 기존 상태 갱신의 범위를 좁혀 고치는 편이 낫다.

수정 지점과 재현 조건

scripts/hooks/pretool.mjs:57의 상대 경로 처리와 scripts/hooks/docs.mjs:87의 문자열 비교. 창의 read-modify-write는 같은 파일 openWindow, closeWindow, windowChanges다. fixture는 원본 함수를 호출하고 별도의 가상 원고·web 파일을 사용했다. 기존 hooks.json 기록을 꾸며 이 감사의 검토 완료로 세지 않았다.

역할 본문을 공유하더라도 모델을 고르는 정책은 vendor별로 둬야 한다. 현재 저장소도 그렇게 한다. 다만 frontier와 workhorse라는 이름을 양측의 능력이나 가격이 같다는 보장으로 읽으면 안 된다. 아래는 실제 역할 정의와 정책표를 대조한 설정값이다.

Claude researcher에는 model 필드가 없어 부모 모델을 상속한다. Codex researcher는 profile이 모델을 정하며 launcher가 허용한 모델 인자로 바꿀 수도 있다. Codex 검토 역할의 frontier/workhorse는 현재 같은 모델을 가리킨다. 이는 정책 선택이며 당장 잘못된 위임이라는 증거는 없다. 다만 roles.mjs의 상속 설명과 profile 주석 일부가 뒤의 고정 설정과 함께 남아 있어, 실제 값을 먼저 읽어야 한다. researcher의 모델 선택 방식도 정책표와 검사에 명시하면 이런 혼선을 줄일 수 있다.

Codex 공식 계약상 custom agent 파일은 부모 provider와 sandbox, MCP 서버를 바꾸지 못한다. 따라서 이 체인이 지원하는 것은 Claude 경로와 Codex 경로를 각각 운영하는 것과 각 경로 안의 모델 선택이다. 한 연구의 수치 lens는 OpenAI, 독자 lens는 Anthropic으로 보내는 혼합을 뜻하지 않는다. 그 요구가 생기면 외부 감독자가 별도 세션들을 실행하거나 provider routing을 가진 runtime을 검토해야 한다.

현재 판정은 모델 관측이 비었다는 이유만으로 draft를 만들지 않고, 확인 못 했다고 보고한다. 이 구분은 정직하다. 새 model request hook이 있다고 SQLite 관측기를 바로 지우면 안 된다. 공식 설명상 그 hook은 진단용이고 요청을 막지 못하며, 서버의 실효 모델 identity까지 보장하지 않는다. app-server의 model/rerouted는 더 적합한 공식 사건이지만, 감독 실행 경로를 바꾸고 오류·재개·중복 외부 작업까지 시험할 비용이 든다.

Superpowers는 본문을 action 중심으로 쓴다. 공통 skills는 “스킬을 호출한다”, “subagent를 띄운다”처럼 행동을 말하고, 실제 도구 이름은 host별 mapping이 연결한다. porting guide는 깨끗한 세션에서 개발 요청을 주었을 때 brainstorming이 코드 작성 전에 자동 호출되는지 acceptance test로 요구한다. 우리 저장소에서도 연구 요청이 올바른 researcher 진입으로 연결되는지 시험하는 데 쓸 수 있는 방법이다. 모든 세션에 Superpowers식 강제 bootstrap까지 넣어야 한다는 뜻은 아니다.

같은 프로젝트의 Codex manifest는 skills를 지정하면서 hooks를 빈 객체로 둔다. Claude용 기본 hooks 파일이 Codex에 자동 유입되지 않도록 한 구체적 선택이다. 따라서 “manifest만 공통화하면 hook도 같다”는 설계보다, 공통 본문과 native bootstrap·이벤트 등록을 나누는 쪽에 근거가 있다. 모델 선택 가이드는 역할과 판단 난도에 따라 명시적으로 고르도록 하지만, 그 권고가 이 저장소에서 더 싼 결과를 냈다는 실험은 없다.

BMAD 안정판은 하나의 설치기를 경로 표로 설정한다. skill manifest를 읽는 공통 설치기가 Claude의 .claude/skills와 Codex의 .agents/skills로 같은 SKILL.md 본문을 복사한다. 숨김·캐시 파일은 걸러 내므로 소스 디렉터리 전체의 무조건적인 byte 복사는 아니다. 두 host 설치 경로와 이름을 fixture에서 검사하는 시험이 있고, shared renderer는 고정된 workflow snapshot을 만든다. 이 시험은 출력 파일을 검증하며 두 모델의 workflow 준수까지 증명하지 않는다.

BMAD 기본 브랜치도 확인했지만 그 안내는 v7 preview alpha라고 명시한다. 그쪽은 외부 Skills CLI로 설치하는 경로와 설정 가능한 eval harness를 쓴다. 안정판의 설치기, preview의 새 구조, live 모델 결과를 섞어서 “성숙한 통합 구조”의 증거로 쓰지 않았다. 특히 안정판의 Codex global 경로는 최신 공식 user 경로와 다르므로 그 경로 값을 그대로 복사할 근거로도 삼지 않는다.

Vercel Skills는 같은 파일이 도구별 위치에 도달하게 한다. 구현에는 canonical .agents 경로와 agent별 경로가 있고 symlink를 만들지 못하면 copy로 돌아가는 처리가 있다. self-loop나 기존 경로가 symlink인 경우의 회귀 시험도 있다. local lock의 content hash와 frozen 검사는 외부 스킬을 재현 가능하게 받을 때 유용하다. 현재 내부 스킬은 이미 저장소 commit으로 관리되므로 별도 설치 CLI와 lock을 넣을 실익은 작다. 설치기가 모델 위임과 두 lens의 병렬 실행까지 보장하는 것은 이 경로의 역할이 아니다.

OpenCode는 provider 선택을 runtime에서 수행한다. 새 child의 모델은 명시 override, agent 설정, 부모 모델 순으로 정한다. 새 세션에 전달받은 prompt를 넣고, 부모가 해당 agent를 띄울 수 있는지도 실행 중 검사한다. child가 자기 agent 권한을 쓴다는 문서 설명에 더해, 코드에서는 부모 session 권한도 상속하고 agent 규칙과 합친다. 이런 선언과 강제의 구분이 모델 위임을 이해하는 데 필요하다. Markdown 묶음에 이 기능이 저절로 생기는 것은 아니다.

현재 저장소는 workflow 공유와 판정에 집중하면 된다. 실제 provider 혼합이 필요할 때 runtime 도입을 별도 판단한다.

이번 결과는 양측의 실제 연구 품질과 가격 우열을 판정하지 않는다
