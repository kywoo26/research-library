Claude Code effort 단계가 바꾸는 것과 단계를 고르는 법

Claude Code 의 effort 는 Claude 가 한 요청에 들일 일의 양을 정하는 설정이다. 단계를 올리면 Claude 는 파일을 더 읽고 더 검증하고 혼자 더 판단한 뒤에 돌아온다. 그래서 높은 단계에서 놓친 edge case 는 크게 줄지만, 잘못된 판단은 덜 줄고 문제를 다르게 해석한 실패는 오히려 늘었다. Anthropic 문서는 Opus 5.5 에서 기본값 medium 으로 시작해 자기 평가로 여러 단계를 재 보라고 권한다.

Anthropic 사람이 쓴 Claude Code 글 둘과 공식 문서 한 절이다. Claude Code 블로그의 Thariq Shihipar 글 「Spending your effort」(2026-09-25), Claude Code 팀 Lydia Hallie 의 「Choosing a Claude model and effort level in Claude Code」(2026-07-07), Claude Platform 문서 「Prompting Claude Opus 5.5」의 Calibrate effort 절이다. 2026-10-25 에 받은 사본 기준이다.

  • 놓친 경우는 59 → 24건으로 약 59% 줄고, 잘못된 판단은 133 → 107건으로 약 20% 준다. 이 비율은 원문의 두 값을 나눠 계산했고, 원문에는 이 비율이 없다.
  • 잘못 고른 해석만 25 → 47건으로 늘었다. 원문은 이 증가를 따로 설명하지 않는다.

그래서 자기 작업의 실패가 edge case 를 놓친 쪽이면 단계를 올려 볼 만하다. 문제를 여러 방식으로 해석할 수 있는 일에서는 높은 단계에서 잘못된 해석을 고른 실패가 늘었으므로, 해석을 명세로 정해 주거나 사람이 루프에 남는다.

공식 문서 §Calibrate effort

  • Thariq 의 경험칙에는 xhigh 가 없다. 그림과 사례에는 xhigh 실행이 나온다.
  • Thariq 이 새 기능에 쓰는 루프는 명세를 주고 빠진 것을 인터뷰하게 한 뒤, low 로 구현하고 검토하며 고치고, high 로 검증하고 시험한다.
  • Hallie 는 단계를 과제마다 바꾸기보다 하는 일의 종류에 맞춘 일반적인 선호로 정하라고 권한다. Thariq 은 과제에 따라, 대화 중에도 /effort 로 바꿔 보라고 권한다.

두 저자의 권고는 단계를 얼마나 자주 바꾸는지에서 갈린다. 두 글 어느 쪽도 이렇게 묶어 말하지는 않지만, 일의 종류마다 기본 단계를 정해 두고 검증만 따로 높은 단계로 돌리면 두 권고 모두와 어긋나지 않는다.

통과와 함께 토큰과 시간을 적고, 향상이 없으면 낮은 쪽을 기본으로 둔다

앞 절반은 공식 문서 §Calibrate effort, 뒤 절반은 원문에 없는 귀결

다시 잰다
  • ③ 에서 실패를 가를 때 Thariq 의 그림 B 분류를 함께 쓸 수 있다. 테스트가 놓친 버그는 단계를 올리면 많이 줄었고, 잘못 고른 해석은 늘었다.
  • 공식 문서는 몇 번 돌릴지 정하지 않는다. Thariq 의 통과 횟수는 과제마다 5번 시도한 값이고, 그의 그림은 통과율을 시도당 토큰과 함께 그린다.
  • 공식 문서는 Opus 5.5 medium 이 Opus 5 high 와 같거나 넘었다고 적고, 여러 코딩 평가에서는 low 도 그 결과에 가까이 가면서 비용이 훨씬 적었다고 적는다. 그렇다면 잴 때 medium 아래 단계도 함께 돌려 볼 만하다.
  • Claude Code 에서는 /effort 로 대화 중에도 단계를 바꾼다. Thariq 은 최신 모델이 Claude Code 에서 단계를 바꿔도 prompt cache 를 깨지 않는다고 적는다.
  • API 에서는 최상위 effort 값을 요청 사이에 바꾸면 prompt cache 가 무효가 된다. 공식 문서는 캐시를 지키는 메시지별 effort 변경(beta)을 쓰라고 하고, 바꾼 값은 다음 변경까지 이어진다.

평가 세트가 없다면 같은 과제를 두 단계에서 여러 번씩 돌려 실패를 ③ 의 두 종류로 나눠 보는 것부터 시작한다. 덜 시도한 실패가 높은 단계에서 꾸준히 사라지고 늘어난 토큰과 시간을 감당할 만하면, 그 일의 기본 단계를 한 단계 올린다.

숫자는 Anthropic 내부 실행이라 자기 작업에서 다시 재야 한다

세 글 모두 Anthropic 사람이 쓴 글이고, 숫자는 Anthropic 의 실행에서 나왔다. 아래는 그 숫자를 자기 결정에 쓸 때 걸리는 조건이다.

  • 내부 실행과 꺼 둔 안전 장치Thariq 의 숫자는 과제마다 5번 시도한 내부 실행이고, Fable 5.1 은 운영 안전 개입을 끈 채 돌렸다. 공개 leaderboard 나 출시 글의 값과 맞지 않으니, 두 값을 섞어 비교하지 않는다.
  • model judge 의 실패 분류그림 B 의 실패 종류는 model judge 가 붙인 근사치다. 자기 작업의 실패는 직접 읽고 가른다.
  • Opus 5.5 가 빠진 그림그림 B 와 C 의 값은 Fable 5.1 이고 Opus 5.5 는 탭에 없다. Opus 5.5 에서 같은 경향이 나오는지는 원문으로 확인할 수 없어 직접 잰다.
  • 조건이 다른 Opus 5.5 실행그림 A 의 Opus 5.5 는 약 3주 뒤에 응답 128k 토큰 제한과 GitHub·PyPI 접근 없이 돌렸다. 다른 모델과의 차이 일부는 이 조건에서 왔을 수 있다.
  • Opus 5.5 이전의 글Hallie 의 글은 2026-07-07 에 나왔고 예로 든 모델은 Opus 4.8 과 4.7 이다. 기본값을 쓰라는 권고는 기본값이 medium 으로 내려간 Opus 5.5 에서 다시 확인한다.
  • 그림만으로 읽은 곡선Hallie 의 토큰 곡선 그림은 설명용이고 실측이 아니라고 캡션에 적혀 있다. 7배라는 값도 한 예시 그림의 캡션이다.
  • Claude Code 의 단계 목록세 글은 Claude Code 의 /effort 가 어떤 단계를 받는지 나열하지 않는다. 쓰는 버전의 /effort 에서 xhigh 를 고를 수 있는지 직접 확인한다.
