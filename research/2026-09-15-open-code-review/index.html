OpenCodeReview가 Codex와 Claude의 코드 리뷰에 더하는 실행 관리

OpenCodeReview는 Alibaba가 공개한 코드 리뷰 CLI다. 이번 비교에서는 기존 Codex·Claude 리뷰를 기본으로 두고, 파일별 규칙과 실패 기록을 직접 관리할 팀에 OCR managed 시험을 권한다. 실행 상태를 남길 수 있지만, 선택되기 전에 빠진 파일까지 그 기록이 보증하지는 않는다.

Alibaba 개발팀의 OCR 코드, OpenAI의 Codex 코드·공식 문서, Anthropic 공식 plugin을 대조했다. OCR·AACR-Bench 논문은 Alibaba와 대학 공동 연구진의 평가다. 2026-10-29 갱신 기준이며 각 코드 commit은 출처에 고정했다.

최근 달라진 부분 · 완료 기록 밖의 누락 · 논문 성능표 · 팀에서 시험할 조건

tl-dr

반복 운영의 부담이 클 때 OCR을 시험할 이유가 생긴다

자체 리뷰에서 이미 만족할 결과를 얻는다면 전환 비용부터 생긴다. OCR의 이점은 리뷰 모델을 바꾸는 일보다 같은 범위·규칙·결과 형식을 반복 적용하는 일에서 찾아야 한다.

기본 리뷰를 계속 쓸 조건

작은 변경을 로컬에서 빠르게 검토하고 기존 AGENTS.md·CLAUDE.md 지침을 적용하면 충분한 팀이다. 새 CLI·API 설정·session 보관을 맡을 이유가 약하다.

OCR managed를 시험할 조건

여러 모델·CI에서 파일별 규칙과 실패·재개 기록을 공통으로 남겨야 한다. 이 경우 OCR runtime이 제공하는 상태와 설정을 운영에서 활용할 수 있다.

delegation을 시험할 조건

현재 host 모델을 유지하면서 OCR의 파일 목록과 rule routing만 가져오고 싶다. 실제 탐색·검증·완료 보고는 host의 지시 이행에 달린다.

채택을 보류할 조건

리뷰 누락을 자동으로 막는 merge gate가 필요하거나, 중요한 실제 결함을 더 잘 찾는다는 근거가 필요하다. 입력 집합 대조와 자체 평가를 먼저 준비해야 한다.

codex

Codex 내장 리뷰도 전용 실행 경로를 갖는다

OpenAI 공식 안내는 /review가 선택한 diff를 별도 reviewer로 읽고 working tree를 수정하지 않는다고 설명한다. 공개 코드는 리뷰 전용 설정과 결과 처리를 보여 준다.

별도 대화를 시작한다

review task는 전용 rubric을 설정하고 initial_history 없이 sub-Codex를 시작한다. review_model이 없으면 현재 model을 사용한다.

도구와 요청을 조정한다

이 경로는 web search와 collab 기능을 비활성화하고 approval policy를 Never로 둔다. base-branch 요청은 merge base를 구해 review prompt에 넣는다.

출력에도 코드가 관여한다

마지막 응답을 ReviewOutputEvent로 해석한다. JSON 해석이 끝내 실패하면 plain text를 overall_explanation에 보존한다. 구조 처리와 내용의 진위 판정은 별개다.

sample skill은 따로 있다

공개 review-agent sample은 전체 diff와 주변 코드, tests·call sites 확인을 지시한다. 이 sample을 설치한 실행과 내장 /review가 같은 경로라고 가정하면 안 된다.

review task · repository rule attribution · review-agent sample · OpenAI 공식 안내

OpenAI는 AGENTS.md의 짧고 범위가 좁은 불변 조건을 review rule로 권한다. 규칙을 적용하는 기능만 필요하다면 기존 지침부터 다듬어 볼 수 있다. OCR rule.json으로 옮길 때는 지침을 두 곳에서 관리하는 비용도 생긴다.

이후 OCR은 선택 집합을 고정하고 completed·reused·failed·waived를 기록한다. task_done에 닿지 못한 파일도 comment가 있으면 completed가 될 수 있다. 따라서 completed를 모든 hunk의 충분한 검토나 bug coverage로 읽으면 안 된다.

보고자의 실행은 재현하지 않았다. 이번에는 해당 코드 분기와 release의 동일 파일을 확인했다. trial에서는 독립적으로 얻은 변경 파일 목록과 OCR preview·제외 목록을 대조하고, 설명할 수 없는 누락이 있으면 merge gate에 쓰지 말아야 한다.

reflection

filter의 정보 경계가 참인 발견을 보존하는지는 따로 봐야 한다

OCR filter는 group diff와 새 후보로 별도 메시지를 만든다. 같은 model을 호출하며 앞 리뷰의 tool 관찰 전체를 이어받는 검증 loop와 입력이 다르다.

위치 일치는 내용 검증과 다르다

OCR은 기존 코드 snippet으로 위치를 찾고 실패하면 다른 diff 파일, LLM relocation 순서로 진행한다. 올바른 줄에 붙은 comment도 실패 시나리오의 가정이 틀릴 수 있다.

diff가 입증하는 오류만 지우라고 한다

filter prompt는 보이지 않는 맥락을 앞 agent가 보았을 수 있다고 전제한다. diff가 직접 반박하는 후보만 삭제하도록 지시한다.

삭제-only에도 손실 가능성이 있다

참인 유일 후보를 지우면 recall이 줄어든다. 이는 설계상 반례이며 이번 실행에서 측정한 손실률이 아니다. confirmed는 filter 단계 뒤 남은 후보를 뜻하며, filter 생략·실패로 그대로 남은 후보도 포함한다.

no-filter로 비교할 수 있다

현재 구현은 --no-filter이면 이 호출을 건너뛴다. 같은 PR을 filter 유무로 비교해 버린 참인 후보와 줄어든 오탐을 함께 세어 볼 수 있다.

delegation

delegation은 OCR 규칙을 현재 host 리뷰에 더하는 선택이다

API endpoint를 따로 구성하지 않고 preview와 rule 결과를 받은 host가 직접 diff와 주변 코드를 읽는다. OCR managed benchmark를 이 모드의 성능으로 옮겨 적을 수 없다.

공통 규칙을 다른 host에 전달managed reflection·round·manifest를 이 경로로 실행하지 않는다host 완료 보고와 managed 상태를 혼동하지 않는지

delegate preview는 host의 context window를 쓰므로 OCR의 per-file diff token ceiling을 적용하지 않는다. 큰 파일을 목록에 올리는 것과 host가 그 파일을 충분히 검토하는 것은 별개다. 해당 skill은 “review and fix” 요청에서 수정을 진행하도록 지시한다.

operations

OCR을 추가하면 버전과 session 보관도 팀이 관리한다

OCR의 LICENSE는 Apache-2.0이다. managed는 별도 provider 설정과 모델 호출이 필요하며, CLI·통합 skill·release가 서로 맞는지도 확인해야 한다.

항목확인한 구현 또는 공식 안내팀이 정할 것
예산main loop가 총 token 초과를 검사하고 마지막 제출 호출을 허용한다청구액 hard cap으로 쓰지 말고 provider 측 지출 제한도 별도 설정
재개입력·rule identity를 검사하고 묵시적 provider/model 변경을 거부한다서로 다른 모델의 재사용 결과가 섞였는지 lineage 확인
결과 상태partial·skipped도 exit 0이 될 수 있다CI에서 exit code와 함께 manifest·warnings 확인
NPM 설치wrapper가 background에서 최신 버전을 확인하고 npm install을 실행한다시험 버전 고정, OCR_NO_UPDATE=1 또는 static binary 사용
로컬 저장~/.opencodereview/sessions에 JSONL을 쓴다코드·prompt·응답을 포함한 기록의 접근과 보존 기간
외부 전송managed는 provider로 리뷰 자료를 보낸다. telemetry 문서는 내용 전송과 별도로 설명한다endpoint·MCP·telemetry 설정을 실제 배포 조건에 맞춰 검토

예산 뒤 호출 · resume 검사 · exit 계약 · 자동 갱신 · session 저장

제거할 때는 설치한 CLI와 host plugin·skill을 제거하고, 보존할 session을 내보낸 뒤 ~/.opencodereview와 project의 .opencodereview 설정을 정리하면 된다. 자동 갱신 중지와 plugin 버전 고정도 시험 환경에 포함하자.

decision

같은 PR에서 중요한 발견과 검토 시간을 함께 비교하자

현 시점의 권고는 managed trial이다. 다음 기준은 저자 benchmark의 절차가 아니라 이번 비교에서 제안하는 팀 평가다.

비교할 상황비교 방법채택을 보류할 신호
로컬 작은 변경현재 Codex /review 또는 Claude의 해당 local review workflow와 비교새 운영 비용에 비해 읽을 finding이나 시간이 개선되지 않음
파일이 많은 변경전체 변경 집합·preview·제외 이유·manifest를 대조설명되지 않는 파일 누락 또는 partial을 성공으로 처리
파일 사이의 계약 변경API·caller·tests가 함께 바뀐 PR을 넣고 근거 경로 확인group 경계 또는 diff 중심 검증에서 중요한 결함을 놓침
팀 고유 규칙위반 사례·허용된 예외·무관한 변경을 함께 넣음특정 glob이 기본 지침을 가리거나 무관한 변경에 오탐
filter와 예산기본 설정·no-filter·제한된 예산의 결과와 warning 비교참인 후보 삭제, 비용 초과, 미완료를 알아채기 어려움

동일한 PR의 고정 revision에서 각 리뷰를 독립 실행하고, 결과의 출처를 가린 채 사람이 결함과 중요도를 판정하자. 중복을 합친 참인 발견, 놓친 중요한 결함, 오탐을 읽는 시간, 총 지연, 실제 청구 비용을 함께 기록하자. LLM 변동이 결론을 바꾸는지도 반복 실행으로 확인하자.

중요 결함을 더 놓치지 않으면서 사람이 읽을 분량이나 운영 부담이 줄면 채택할 근거가 생긴다. 그 기준을 못 맞추면 기존 리뷰를 유지하고 OCR의 rule routing 또는 상태 기록만 참고할 수 있다.

critique

현재 결론은 구현 비교와 과거 평가의 범위에 묶여 있다

직접 실행한 LLM 품질 실험은 없다. 원문 저자의 보고, 코드에서 읽은 동작, 이번 비교의 권고를 구분해 적용해야 한다.

현재 모델의 품질과 비용

현재 Codex·Claude 모델과 OCR을 같은 PR에서 실행하지 않았다. model·effort·cache·billing 조건을 맞추기 전에는 최신 품질이나 청구 비용의 승자를 정할 수 없다.

운영 보고의 재현

#1824의 원 실행과 로그를 재현하지 않았다. 해당 commit의 누락 분기를 확인했지만 모든 저장소에서 누락이 얼마나 자주 생기는지는 측정하지 않았다.

공개 코드의 경계

공개 Codex CLI runtime과 공식 plugin을 읽었다. Codex cloud review·Claude의 별도 managed 서비스까지 같은 구현으로 일반화하지 않는다.
