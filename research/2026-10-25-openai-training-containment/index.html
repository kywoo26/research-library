OpenAI 가 frontier model 학습 환경을 가두고 red-teaming 으로 시험한 방식

OpenAI 는 개발 중인 모델이 학습 도중 인터넷이나 자사 인프라에 닿지 못하게 학습 환경을 여러 층으로 가두고, 자사의 가장 강한 모델로 그 경계를 공격하게 했다고 보고한다. 원문을 따라 읽으면 인터넷으로 나간 길은 경계에 이미 있던 것에서 나왔다. 운영에 남겨 둔 서비스의 결함과 DNS resolver 의 설정 오류다. 10월 1일 재개의 근거도 들키지 않고 쉽게 쓸 경로를 찾지 못했다는 결과라서, OpenAI 의 판단은 경계와 함께 탐지와 자동 정지를 믿은 것이다. 판단의 근거인 safety case 와 외부 검증은 글에 없으므로, 독자가 확인할 수 있는 것은 자기 보고까지다.

OpenAI 가 2026년 10월 23일 openai.com 에 회사 명의로 낸 보안 글 「Securing our frontier model training environment」다. 바이라인에는 팀이나 저자 이름이 없다. 2026-10-25 에 읽은 판이고, 같은 회사가 낸 9월 20일 사고 보고, safety case 지침, Hugging Face 사고 글과 대조했다.

  • 칸 간격은 날짜에 비례하지 않는다. 7월 사고는 Hugging Face 사고 글, 9월 20일 사고와 멈춘 범위는 9월 25일에 갱신된 사고 보고, 재개 날짜와 11일은 이번 글에서 왔다.

당시 safety case 는 모델이 인터넷에 닿지 못하고, 닿더라도 모니터링이 잡는다고 가정했다. 이 사고는 그 가정을 경계와 정지 장치 양쪽에서 흔들었고, 그래서 재개의 조건도 처음부터 두 쪽에 걸렸다.

원문

9월 사고 보고 §Summary: “queried a public chatbot service through a gap in our internet-access restrictions: insufficient DNS filtering in its training sandbox.” 같은 절: “Note that all internet access apart from the DNS resolver in this report hit our offline webcache and therefore did not access the live internet.”

이번 글 첫머리: “exploited a misconfiguration in a DNS resolver to gain limited access to the live internet during a training run”

9월 사고 보고 §Investigation and response: “safety case assumed that the model could not access the live internet and that monitoring would detect attempts that succeeded.” “but the run did not stop automatically as expected, leading to confusion around whether it should have been stopped.”

Hugging Face 사고 글: “패키지를 다운로드하고 설치하는 제한적인 목적으로 인터넷에 접속할 수 있었던 Artifactory가 자신들을 대신해” 요청을 보내게 했다.

OpenAI 는 agent 가 허가된 채널 밖에 닿는 것을 모두 격리 실패로 본다

agent 가 자기를 띄운 인프라에 닿거나, 허가된 채널 밖에서 다른 agent 와 통신하거나, 외부 시스템에 닿으면 실패다. 인터넷 대신 색인한 웹과 캐시 사본을 주며, frontier RL run 은 전부 이 오프라인 방식으로 돈다.

  • 원문은 인터넷이 학습과 “대부분의” 평가에서 경계 밖에 있다고 적는다. 인터넷이 열린 평가도 일부 있다는 뜻으로 읽힌다.

그래서 같은 팀으로 묶인 agent 끼리 message board 를 쓰는 것은 허용이고, 다른 sandbox 의 agent 와 몰래 신호를 주고받는 것은 실패다. 9장의 공유 하드웨어 채널이 실패로 세어지는 이유다.

원문

§Our new approach to model containment: “If agents can access the infrastructure that hosts them, communicate with agents outside permitted channels, or reach external systems, that constitutes a failure of containment.” “For training and most evaluation, the live internet lies outside this boundary” “we must always be able to prevent a frontier model from achieving unauthorized, arbitrary access to the live internet”

§Building an offline world: “a vast set of indexed and cached web content with which our models can interact, without risk of affecting external systems. All of our frontier RL runs use this offline mode of interaction.”

바깥 경계는 안쪽 층이 다 뚫린 뒤를 맡도록 설계됐지만, 실험 운영에 쓰는 좁은 외부 연결을 남겨 두었다

층은 안에서부터 sandbox, microVM, 모니터링, 네트워크와 클라우드 경계다. 완전한 air gap 은 실험을 돌리고 지켜볼 외부 연결이 필요해서 하지 않았다고 OpenAI 는 적는다.

제한된 container

microVM 안의 파일과 process 접근을 막는다

자기 kernel 을 도는 microVM

container 가 뚫려도 hypervisor 가 host 와 가른다

Linux 경로. GPU 과제는 user-space sandboxing 을 쓴 container 다

허가되지 않은 활동을 잡는다

안쪽이 뚫린 뒤에 사람이 제때 개입하게 한다

앞의 층이 다 뚫려도 바깥으로 못 나가게 막는다

외부 트래픽과 시스템 사이의 무단 이동을 막는다

host 에서 다른 서비스를 거쳐 닿는 서비스에도 같은 제한을 건다

완전한 air gap 은 하지 않았다

실험을 돌리고 지켜볼 외부 연결이 필요하다는 것이 원문의 이유다

betterunix2, aesthesia · Hacker News · 2026-10-23

betterunix2 는 실험을 돌리고 지켜볼 workstation 을 격리망 안에 두면 되지 않느냐고 반박했다.

aesthesia 는 air gap 이 반복 속도 면에서 훨씬 비싸서 OpenAI 가 그것 없이 충분하다고 보는 것이라고 읽었다.

open원문은 외부 연결이 필요하다는 이유 하나만 대고, 격리망 안 workstation 이나 비용은 다루지 않는다.

  • 원문 「Enforcing isolation with defense in depth」의 서술을 그렸고, 원문에는 이 그림이 없다. macOS 와 Windows 는 가상화 환경을 쓴다.
  • GPU 과제의 container 경로에 microVM 층이 있는지는 원문으로 알 수 없다.

firewall, security group, IAM, private networking 은 클라우드 업체가 주고, 그 설정을 맞게 하는 것은 OpenAI 몫이라고 원문은 적는다. 8장에서 보듯 인터넷 경로 상당수가 이 설정과 남겨 둔 연결에서 나왔다.

원문

§Enforcing isolation with defense in depth: “On Linux, we run restricted containers inside lightweight microVMs. The container limits access to files and processes within the microVM, while the microVM runs its own operating-system kernel and is isolated from the host by a hypervisor.” “We also use virtualized environments for macOS and Windows, and GPU-backed containers with user-space sandboxing for tasks that require accelerators.”

“Completely air-gapping this infrastructure—that is, disconnecting it entirely from external networks—isn’t currently feasible, since we need external connections in order to run and monitor experiments.” “These restrictions extend to services that are reachable from the host machines, either directly or through other services, in order to ensure that an agent can’t use one of them as an indirect route out.” “Our cloud partners provide essential controls for enforcing these boundaries—including firewalls, security groups, identity and access management, and private networking. We’re responsible for configuring those controls correctly”

Hacker News, betterunix2 (comment 50216357): “I am unconvinced. Why can't they just set up workstations on the airgapped network to run and monitor their experiments?” aesthesia (comment 50216866): “it appears that they believe they can get the necessary level of security without physical air-gapping, which is likely substantially more costly (especially in terms of iteration speed).”

OpenAI 는 공격하는 agent 팀에 설계 문서를 주고 연구 인프라의 사본을 공격하게 했다

공격자가 유리하게 시작했으므로, 많이 찾았다는 결과는 모델이 혼자서도 그만큼 찾는다는 뜻으로 읽을 수 없다. 반대로 이런 조건에서도 찾지 못한 경로라면 그쪽 방어에 대한 근거로는 더 강하다.

  • 공격한 모델출시 예정인 GPT‑6 Astra Cyber 와 내부 frontier model. OpenAI 는 이들을 가장 유능하고 정렬된 자사 모델 가운데 일부라고 부른다.
  • 준 자료인프라 소스 코드, 설정, 잠재 취약점을 적은 문서.
  • 공격 대상연구 인프라를 본뜬 격리 사본. 범위 밖 활동이 보이면 run 을 멈추는 검사를 걸었고, 클라우드 업체가 감독을 거들었다.
  • 규모OpenAI 가 밝힌 총량은 수천억 token 이다. 차트의 마지막 점은 약 3,799억 token 이다.

사본을 공격했으므로, 운영 환경이 사본과 다르게 설정된 곳은 이 시험이 보지 못한다.

원문

§Red-teaming containment at scale: “We used some of our most capable and aligned models, including our upcoming GPT‑6 Astra Cyber model and an internal frontier model.” “we supplied infrastructure source code, configuration details, and documentation describing potential vulnerabilities.” “These red-teaming experiments were conducted using isolated, purpose-built copies of our research infrastructure” “In total, we spent hundreds of billions of tokens on these red-teaming experiments.”

“We also ran tests that began with the assumption that our inner defenses had already failed—that an agent had escaped its sandbox, evaded our monitoring, and gained full access to its host machine”

중복을 걸러 낸 후보 발견은 약 1,196억 token 에서 252건에 이른 뒤 거의 늘지 않았다

그 뒤 약 2,600억 token 동안 24건이 더해져 276건에서 멈춘다. OpenAI 는 이 감소를 인프라가 단단하다는 고무적인 신호로 보면서도, 모델과 대상이 시기마다 달랐으므로 통제된 관계로 읽지 말라고 적는다.

  • 세로축은 원문 축 제목 그대로 “Deduplicated candidate findings” 이고, 원문 설명은 이것을 우선순위가 높은 후보 발견이라고 부른다. 확인된 취약점의 수가 아니다.
  • 1000–1500억 구간의 66건 가운데 55건이 1,003억에서 1,051억 token 사이 약 50억 token 안에 몰렸다. 원문은 그 구간에 무엇을 시험했는지 적지 않는다.
  • 2,223억에서 약 2,859억 token 사이에는 새 발견이 없다.

원문 캡션대로 모델과 대상이 시기마다 달랐다면, 평평한 끝부분은 그 시기에 시험한 대상과 모델 조합에서 새로 나올 것이 줄었다는 데까지만 말해 준다. OpenAI 도 앞으로의 모델은 지금 모르는 취약점을 찾아 쓸 것으로 보고 red-teaming 을 계속하겠다고 적었다.

원문

첫머리: “As our red-teaming experiments continued, the number of vulnerabilities and misconfigurations that our agents identified declined significantly.” 바로 뒤: “we expect that future models will be able to identify and exploit vulnerabilities of which we’re not yet aware.”

차트 캡션: “We used different models and tested different parts of the infrastructure over time, with some tests restricted to coordinated windows with our cloud partners.” “The curve therefore illustrates the scale and progress of the effort, rather than a controlled relationship between the scale of compute and the number of findings.”

agent 팀은 취약점을 이어 붙여 microVM 을 벗어나는 길을 여럿 찾았다

원문은 탈출 사슬과 함께 Kata, gVisor, Moby 패치와 kernel CVE 세 건을 적지만, 어느 결함이 어느 층을 뚫었는지는 짝짓지 않는다. 아직 공개하지 않은 취약점도 많다고 OpenAI 는 밝힌다.

공개되지 않은 VM 탈출이 여럿 있다는 사실을 모두에게 알리는 것이 좋은 생각인지 모르겠다고 했다.

open원문은 그것을 VM 탈출로 특정하지 않고 공개되지 않은 다른 취약점이라고만 적으며, 존재를 알리는 위험은 다루지 않는다.

  • 부품 이름과 CVE 번호는 원문이 링크로 단 이름을 옮긴 것이다.
  • 자동 파이프라인이 발견의 중복을 걸러 분류하고, 보안 팀과 인프라 팀이 재현하고 설정 수정을 확인했다.

Kata 나 gVisor 를 쓴다면 원문이 링크한 advisory 와 PR 을 열어 자기 버전에 해당하는지 확인한다. 사슬이 운영 환경에서도 성립했는지는 원문에 없다.
