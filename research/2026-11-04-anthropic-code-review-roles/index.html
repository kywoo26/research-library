Anthropic Claude Code 팀의 코드 리뷰 역할과 책임

Claude Code 팀은 agent가 만든 변경을 여러 검증 층으로 리뷰한다. 저자들은 반복적인 코드 읽기를 AI로 옮기면서 사람에게 목적·위험·검증 근거·결과의 책임을 남긴다. 이 분석에서는 승인 완화의 전제를 검증과 복구 체계에서 찾는다. 팀 지식 공유와 승인 조건의 자동 강화는 아직 풀어야 할 과제다.

Anthropic Claude Code 팀의 Addy Osmani, Morgan Westlee Lunt, Qing Wang이 쓴 「How the Claude Code team does code review」(2026-10-15)와 연결된 공식 문서·공개 security review 구현을 읽었다. 내부 관행과 공개 제품의 기능은 구분했다.

리뷰 시간의 절감은 장애 수습 시간이 늘지 않을 때 성립한다

저자들은 리뷰하는 시간과 잘못된 변경을 고치는 시간을 함께 사람의 비용으로 본다. 그래서 처리량과 승인 수만으로 성공을 판단하지 않는다.

종전 흐름은 코드를 쓰고 PR을 연 뒤 동료를 기다리는 방식이다. agent가 변경을 계속 만들면 마지막 단계의 사람 읽기가 밀린다. Claude Code 팀은 작성 중 검증을 반복하고, 사람이 보기 전에 일상적인 오류를 줄이는 쪽으로 이동했다. 저자들이 설명한 종전 흐름을 비교 기준으로 삼는다. 모든 팀의 기존 리뷰가 같았다는 뜻은 아니다. [1]

저자들의 목표는 Claude Code의 CLI·desktop·web·mobile 저장소에서 대부분의 PR이 작성자를 포함해 사람 한 명 이하의 개입으로 merge되는 것이다. 이는 목표의 진술이다. 실제로 그 비율을 달성했다는 집계는 붙어 있지 않다. 사람 승인 수의 중앙값·95th percentile, 사람 댓글, 사람을 기다린 시간을 추적한다. revert와 incident의 비율이 오르면 시간이 수습으로 옮겨 갔다고 판단한다.

관측 대상과 기간공개된 관측이 값으로 판단할 수 있는 범위
Claude Code codebase, 2026년 6월→9월merge된 PR 수가 2배를 넘게 증가했다. revert된 PR의 비중은 40퍼센트 넘게 감소했다.팀이 보고한 전후 변화다. 전체 PR 수와 실제 revert 비율은 없으므로 절대 사고량이나 인과효과를 계산할 수 없다.
Anthropic monorepo, 2026년 5월→9월일평균 merge 변경 약 2,500건→30,000건 초과별도 source control 글의 규모다. Claude Code 자체 저장소의 일일 PR 수로 읽으면 안 된다. [6]

원글은 Claude가 자체 코드의 약 90퍼센트를 쓴다고도 말한다. 이 비중은 검증 체계가 필요한 배경이다. 리뷰의 정확도나 사람이 책임지는 변경의 비중을 나타내지는 않는다. 핵심 질문은 사람이 코드를 읽었는지에서, 어떤 실패를 어느 검사로 잡을지로 바뀐다.

사람은 읽기 수행자에서 검증 체계를 책임지는 쪽으로 이동한다

저자들은 결함 탐색을 AI에 넓게 맡긴다. 변경을 만들 가치와 위험을 판단하고 결과를 소유하는 의무는 사람에게 남긴다.

행위자종전 리뷰에서 묶여 있던 일달라진 수행과 계속 남는 의무
변경 작성자 또는 agent 지시자변경을 설명하고 reviewer의 지적을 고친다.agent에 목적과 검증 수단을 준다. 테스트·되돌리기 근거에 직접 확인 의사를 표시한다. agent가 쓴 변경도 사람이 책임진다. 작은·중간 변경의 문제는 보통 merge한 사람이 고친다.
사람 reviewer와 code ownerdiff 읽기에서 오류·설계·팀 맥락을 함께 확인한다.구축 가치, 범위, 위험 코드, 다른 코드가 따를 아키텍처를 판단한다. 검사가 놓치는 것을 설명할 수 없으면 깊은 리뷰를 요청한다. code owner는 REVIEW.md에 실제 실패와 근거 기준을 적는다.
AI reviewer동료 reviewer가 diff에서 결함을 찾는다.PR 전과 PR에서 결함을 찾고 다른 agent가 후보를 검증한다. 원인·영향·위치를 제시한다. 요구된 사람 승인 자리는 채우지 못한다.
자동 검증·운영 시스템CI가 일부 결함을 차단하고 배포 후 감시를 돕는다.필수 CI, 열린 finding, 위험 승인 조건, merge queue, 단계 배포와 복구를 연결한다. 시스템이 검사 조건을 집행해도 결과 책임자는 사람이다.

이 표는 원글의 의무를 행위자별로 재구성한 분석이다. 저자들이 제시한 공식 직무 분장표는 아니다. 리뷰 도구를 붙이는 것만으로 사람의 역할이 바뀌지는 않는다. 사람이 어떤 실패를 검사해야 하는지 정하고, 그 증거를 생성할 도구와 실패 후 회복 경로를 갖춰야 읽기 업무를 옮길 수 있다. [1, §Where humans stay in the loop·You land it, you own it]

방향 판단은 더 일찍 필요해진다. agent로 쉽게 시작한 작업도 만들 이유가 약하면 닫거나 범위를 바꾼다. 저자들은 완성된 PR을 막을 때까지 기다리기보다 공개 작업 채널에서 예전 결정과 더 단순한 대안을 먼저 제시한다고 설명한다. 따라서 사람의 역할에는 코드를 고치는 일뿐 아니라 작업을 중단할 판단도 남는다.

변경의 검증은 PR 전부터 배포 후 복구까지 이어진다

원글은 각 층이 일부 문제를 잡고 일부를 놓친다고 설명한다. FIG B의 구멍은 이 원리를 그린 개념도다.

변경이 지나는 시점내부 팀의 장치책임의 연결
PR 전테스트·build·화면 비교, fresh-context subagent, bug 탐색·단순화·end-to-end skills작성 지시자는 agent가 검사할 방법과 원하는 동작을 준비한다.
PRAI bug review, 별도 security review, 필수 lint·type·여러 플랫폼 테스트·buildfinding은 수정하거나 이유를 남겨 닫는다. 요청한 사람은 testing·revert 설명을 확인한다.
승인과 merge위험과 신뢰에 따른 사람 승인, main과 합친 상태의 merge queue 검사owner가 필요한 사람 수를 정한 정책을 적용한다. 요구된 사람 승인을 bot이 대신하지 못한다.
배포 후직원 대상 flag, latest 후 stable, telemetry·on-call·신속한 revert작성자와 on-call이 놓친 문제를 발견하고 복구한다. 사고 검토는 놓친 검증 층을 찾는다.

FIG A의 전체 경로를 위 표로 풀었다. AI 리뷰의 동의는 테스트 성공과 다른 증거다. 테스트 성공도 통합 상태나 실제 사용자 환경의 성공을 전부 보장하지 못한다. 그래서 앞 단계의 확인을 다음 단계의 검사를 생략할 이유로 삼지 않는다.

검증 가능한 출력과 강제 규칙을 마련해야 agent가 스스로 고친다

공개 best-practices guide는 실행 명령과 결과를 요구한다. 사람이 명세와 관찰 지점을 준비해야 agent의 수정 루프가 올바른 방향을 향한다.

원글의 PR 전 검증은 테스트를 돌렸다는 문장으로 끝나지 않는다. 실행한 명령과 출력, 설계와 비교한 화면을 제출한다. 새 맥락의 reviewer가 diff를 다시 본다. 작성한 이유를 함께 기억하지 않는 검토는 작성자의 설명을 그대로 따라가는 경향을 줄이려는 장치다. 서로 다른 맥락이 서로 다른 오류까지 보장하는 것은 아니므로 실행 검사는 따로 필요하다. [2, Give Claude a check to run]

공개 skills 글은 검증 과정을 영상으로 남기거나 각 단계의 상태를 assertion으로 확인하는 기법을 설명한다. browser·simulator·TTY 등 검증 대상에 맞는 도구가 필요하다. 이는 내부 skills의 활용 설명이다. 원글에서 썼다는 bug hunt·simplifier·end-to-end skill의 실제 구현을 공개한 것은 아니다. [8]

사람이 갖춰야 할 기술남겨야 할 자료·장치그것이 필요한 이유
요구 동작을 실패 가능한 검사로 바꾸기명세, fixture, 회귀 테스트, 화면 비교, 실제 실행 출력agent가 같은 오해로 코드와 테스트를 함께 만들 수 있다. 사람이 기대 결과를 확인해야 한다는 분석이다.
저장소의 함정을 짧게 설명하기CLAUDE.md의 목표·관례·명령, REVIEW.md의 failure 정의·file:line·제외 경로재발한 지적을 일회성 댓글에서 다음 변경의 입력으로 옮긴다.
정책과 검사를 집행하기hook, CI, branch protection, 경로별 소유권공개 guide는 항상 지켜야 할 조건을 지침 파일에만 두지 말라고 권한다. 지침 준수와 강제 실행은 다르다.

규칙이 실제로 적용됐는지도 확인해야 한다. 현재 공식 문서에서 서비스형 Code Review는 CLAUDE.md와 REVIEW.md를 읽지만 local /code-review는 CLAUDE.md만 읽는다. REVIEW.md만 바꾼 뒤 local 결과로 규칙의 효과를 검증하면 다른 조건을 비교하게 된다. 서비스는 PR이 수정한 REVIEW.md를 그대로 쓰지 않고 base/default branch의 사본을 읽는다. 제외와 Nit cap 같은 완화 규칙에는 보호된 default branch의 root 파일이라는 조건도 있다. [10]

Boris Cherny가 말한 품질 2–3배 개선은 개인 게시물의 추정이다. 팀의 검증된 생산성 효과로 읽지 않는다. [13]

의미 있는 finding은 실제 실패 경로와 코드 근거를 설명한다

내부 reviewer는 diff를 저장소와 PR 의도에 비춰 읽는다. 다른 agent들의 검증을 거친 뒤 severity에 따라 finding을 게시한다.

내부 merge 정책

관리자는 저장소별 Quick·Standard·Deep으로 검토 깊이를 정한다. 저자들은 한 번의 bug 누락 비용이 추가 검토 시간보다 큰 곳에서 Deep을 쓸 가치가 있다고 본다. 사람 승인 수를 정하는 위험 정책과 함께 AI의 검토 노력도 조절한다. [1] [3]

저자들은 style·diagnostics·cleanup만 다루는 후보를 걸렀고, 필터를 내부 PR에서 A/B 비교했다고 설명한다. 실제 효과 크기는 제시하지 않는다. 공개 Code Review 문서도 병렬 탐색→검증→중복 제거와 정렬→게시를 설명한다. 그러나 공개 서비스는 코드를 build하거나 실행하지 않는다. 따라서 여기서 검증은 코드에 비춰 후보의 타당성을 확인하는 과정이다. 실행 결과의 보증으로 읽으면 안 된다. [1] [3]

공개 TrueNAS PR에는 근거가 구체적인 예가 남아 있다. Claude bot은 문자열인 dataset 이름을 dict 목록과 비교하면 key cache의 항목이 사라진다고 설명했다. 반환값의 형태, 비교식, 영향, 수정 방법을 연결했다. bot은 이를 Pre-existing으로 표시했고 작성자는 별도 PR이 필요하다고 답했다. 이 기록은 결함의 기원과 이번 PR의 수정 범위를 구분하는 예다. 이 분석에서 해당 서비스를 실행해 확인한 사례는 아니다. [15]

이 예에서 도출할 수 있는 실무 기준은 이름만 보고 추측하지 않는 것이다. reviewer는 호출 경로와 자료형, 결함이 나타나는 조건, 사용자에게 미치는 영향을 연결해야 한다. code owner는 이 기준을 REVIEW.md에 적고 실제 출력이 따르는지 따로 평가해야 한다.

사고를 찾는 능력과 해로운 지적을 함께 평가해야 한다

내부 팀은 실제 실패를 전문가가 확인한 eval로 만들고 매일 실행한다. 사람의 댓글 반응과 깨끗한 PR에서의 해로운 수정 유도도 따로 본다.

평가 자료내부 팀이 확인하는 것해석할 때 남는 조건
사고를 낸 과거 PR + fix-forward·revert코드를 아는 엔지니어가 bug와 위치를 확인한다. reviewer를 매일 평가하고 prompt·tool·model 변경을 전체 사례에 채점한다.실제 실패를 회수하는 능력에 초점이 있다. 과거 사고 목록이 모든 미래 결함을 대표하지는 않는다.
게시한 각 댓글과 사람의 응답수정, 틀렸다고 판단, 의도된 동작, 중요하지 않음으로 분류한다.고쳤다는 행동이 곧 객관적 정답은 아니다. 답하기 쉬운 지적을 고친 경우를 분리할 필요가 있다는 분석이다.
깨끗하다고 아는 PR잘못된 지적 때문에 해로운 변경을 하게 될 수 있는 경우를 센다.댓글 수가 적다는 것보다 불필요한 수정의 피해를 묻는다.

저자들이 적은 우선순위는 실제 bug를 먼저 잡고 그 다음 리뷰 회수를 줄이는 것이다. noise만 줄이면 조용하지만 중요한 결함도 놓치는 reviewer가 될 수 있다. 그래서 recall과 rounds-to-pass를 함께 추적한다. 수렴을 개선했다는 수치만으로 그 때 recall도 보존됐다고 단정할 수는 없다.

발표 당시 substantive comment가 붙은 내부 PR 비율은 16%→54%였다. 이 비율은 더 많은 PR이 지적을 받았다는 뜻이다. 알려진 결함 중 얼마를 잡았는지를 나타내는 recall은 아니다. 같은 발표의 incorrect로 표시된 finding이 1% 미만이라는 값도 표시 행동의 비율이다. 전체 지적을 독립 판정한 precision으로 바꿀 수 없다. [4]

자체 평가를 만든다면 사건별 정답과 댓글별 판정을 별도로 보관할 필요가 있다. 같은 실패를 가리키는 여러 댓글은 하나의 bug에 연결한다. 위험 영역별 누락과 잘못된 수정 유도를 함께 본다. 이 데이터 설계는 원글의 평가 방식을 운영 가능한 형태로 풀어 쓴 제안이다. 구체적 내부 schema나 계산식은 공개되지 않았다.

재검토 범위를 줄이고 중복을 막아야 리뷰가 수렴한다

한 CLI PR은 밤새 50회 넘게 리뷰와 수정을 반복했다. 팀은 계속 지적된 코드의 약 59%가 첫 리뷰 때부터 있었다고 설명한다.

이 59%는 false-positive 비율이 아니다. 새로 만든 bug보다 이미 있던 코드를 다음 회차에 조금씩 더 찾는 문제가 컸다는 git blame 관찰이다. 사람이면 넘길 사소한 지적도 agent는 수정한다. 그 수정이 commit과 재검토를 부르므로 두 agent가 서로 일을 계속 만들 수 있다. [1, How we make the reviewer better]

새 finding

FIG D는 내부 PR의 전후 비교다. 표본 수, 전후 기간, 저장소별 구성과 같은 조건을 공개하지 않는다. 여러 수렴 조치를 함께 바꿨으므로 각 조치의 효과를 분리할 수도 없다. 특정 회차에 반드시 멈춰도 안전하다는 인과 증거로 쓰면 안 된다. cap의 의미도 자동 통과가 아니다. 작성자가 접근법을 다시 판단하도록 만드는 장치다.

사람 승인 수는 변경의 위험과 작성자 신뢰를 함께 따른다

내부 classifier가 변경의 위험을 정하고 다른 classifier가 추가 사람의 필요를 묻는다. 정해진 사람 승인을 AI가 대신할 수는 없다.

원글의 위험 등급예시필요한 사람
Low문서·copy, 내부 전용 기능, flag 뒤의 추가 변경자동 리뷰와 security 검사 통과 후 필수 승인 없음
Medium일반 제품 변경, caching·auto-updater·system prompt 같은 민감 영역 변경한 명
High가장 위험한 코드, 항상 두 사람이 필요한 일부 경로두 명

이 표는 단독 승인 알고리즘이 아니다. owner가 민감하다고 정한 경로와 모든 CI workflow 파일은 항상 사람이 필요하다. trusted list의 작성자만 가벼운 경로를 쓰고, 그 밖의 작성자는 두 번째 사람의 승인이 필요하다. 변경이 위험 등급을 정하고 작성자 신뢰가 완화 자격을 제한하는 구조다. [1, Human approval, scaled by risk]

agent가 만든 PR에서는 agent를 지시한 사람이 요구된 reviewer 중 한 명으로 센다. 따라서 Medium의 한 명이 항상 동료 한 명을 추가한다는 뜻은 아니다. 필수 승인이 없는 Low에도 지시한 사람의 결과 책임은 남는다. 이 구별이 있어야 사람 승인 수 감소를 책임자 부재로 오해하지 않는다.

승인은 특정 commit을 대상으로 한다. 이후 agent push나 수동 merge처럼 시스템이 보증하지 못하는 commit이 들어오면 다시 승인한다. 위험 분류의 정답률, 내부 trusted list의 운영 기준, 추가 사람을 요구하는 classifier 구현은 공개되지 않았다. 외부 팀은 파일 이름 예시만 복사해서 승인 완화를 자동화할 수 없다.

공개 제품내부 팀의 운영 정책
Code Review는 finding·summary·check run을 남긴다. PR을 승인하거나 차단하지 않으며 check run도 failure로 끝내지 않는다. [3]열린 bug·security finding은 merge를 막는다. 수정하거나 이유를 남겨 닫아야 한다. 위험과 신뢰에 따른 별도 승인 조건도 적용한다. [1]

즉, reviewer를 설치하는 일과 merge 조건을 집행하는 일은 따로 구축해야 한다. GitHub 문서의 필수 status checks, 대화 해결 요구, code owner 승인과 stale approval 취소가 공개 구성 수단이다. GitHub의 리뷰 문서에서 PR 작성자는 자신의 PR에 승인 리뷰를 줄 수 없다. 원글의 지시자 한 명 산정과 내부 classifier를 같은 설정으로 그대로 재현할 수 있다고 가정하면 안 된다. [11]

캐시 변경의 검사가 통과해도 근거와 승인 범위는 다시 확인한다

다음은 원글의 규칙을 적용한 가상 사례다. trusted 지시자가 agent에게 캐시 만료 동작을 바꾸게 했다고 가정한다.

배포할 가치와 허용 동작은 사람이 정한다

만료 경계와 동시 접근을 확인한다

구체적 테스트 항목은 이 사례의 제안이다

조건을 충족한 사람 수를 확인한다

Medium·추가 조건 없음이면 지시자 한 명도 가능하다

통과

사람이 출력에서 정상 요청만 확인했다면 동시 접근 실패를 설명할 근거가 부족하다. 이 경우 저자들의 원칙에 따라 더 깊은 리뷰를 요청한다. AI reviewer가 침묵했다는 이유로 승인할 수는 없다. 반대로 실제 명세와 실행 결과, 누락 가능성이 이해되고 내부 승인 조건을 충족한다면 모든 사람이 diff를 다시 줄마다 읽어야 한다는 규칙은 원글에 없다. [1]

조건을 바꾸면 경로도 달라진다. trusted list에 없는 작성자라면 두 번째 사람이 필요하다. CI workflow까지 바꾸면 항상 사람을 거쳐야 한다. 분류 결과가 High이거나 추가 classifier가 사람을 더 요구하면 그 조건을 따른다. merge 뒤 오래된 값이 잘못 노출되면 작성자와 on-call이 탐지·복구하고, 놓친 조건을 회귀 검사나 eval로 남긴다.

이 사례의 캐시 테스트 설계는 연구자의 예시다. 내부 classifier가 어떤 만료 변경을 어느 등급으로 판정할지는 공개되어 있지 않다. Medium과 추가 조건 없음은 경로를 설명하기 위한 가정이다.

승인 완화는 탐지와 되돌리기를 운영할 사람을 전제로 한다

내부 팀은 작은 변경과 flag·단계 배포·빠른 revert로 실패 비용을 제한한다. 작성자의 소유는 on-call과 팀의 지원 안에서 작동한다.

merge queue는 변경을 최신 main에 합친 상태로 검사를 다시 돌린다. 각각 통과한 두 PR의 상호작용을 확인하려는 장치다. 검사가 다루지 않는 충돌까지 없애 주지는 않는다. 새 동작은 보통 직원에게 flag 뒤에서 먼저 공개하고, public latest 다음 stable로 간다. flag는 새 배포 없이 끌 수 있다. [1, Merge queue·Fast detection]

작은·중간 변경이 문제를 내면 merge한 사람이 보통 고친다. 그 사람이 맥락을 가장 많이 갖고 있기 때문이다. weekly on-call, 대시보드, 내부 사용과 telemetry가 탐지를 돕는다. 사고 검토는 누가 잘못했는지보다 어느 층이 잡았어야 했는지를 묻는다. 공개 작업 채널에서는 다른 구성원도 문제를 짚고 복구에 참여한다.

저자들은 revert·incident 지표가 나빠질 때 승인 조건을 자동으로 강화하는 circuit breaker를 아직 갖추지 못했다고 명시한다. 더 많은 zero-human merge로 가기 전에 필요한 장치라는 팀 내 요구다. 따라서 지표를 기록한다는 사실과 그 지표가 자동으로 위험 경로를 닫는다는 주장을 구별해야 한다.

AI 설명만으로 복잡한 diff를 평가할 이해가 생기느냐고 묻는다.

open저자들은 지식 공유의 공식 과정이 없다고 밝힌다. 대체 효과를 검증한 자료도 제시하지 않는다.

원글은 설명을 몇 분 안에 얻을 수 있고 실제 변경할 모듈을 배우는 편이 단순 copy 수정 diff를 읽는 것보다 낫다고 본다. 연결된 HTML 활용 글도 관련 코드를 읽고 흐름도·핵심 코드·주의점을 한 페이지에 만들도록 요청하는 예를 제시한다. 이는 학습 방법을 보여 준다. 팀원의 이해를 독립적으로 시험한 결과는 아니다. [1] [9] [14]

그 간극은 위험과 아키텍처 판단에 바로 연결된다. 사람이 코드에 대한 설명을 평가할 수 있어야 어떤 검사가 빠졌는지도 말할 수 있다. 이 분석에서는 설명을 받은 담당자가 실제 호출 경로와 실패 조건을 코드에 연결해 다시 설명하도록 제안한다. 팀 전체의 이해를 유지하는 검증법으로 원글이 이미 운영한다는 주장은 아니다.

공개 Slack 채널에서 진행 중인 작업을 보고, 예전 결정과 대안을 일찍 제시하는 문화도 함께 작동한다. PR 승인을 줄여도 맥락 공유와 방향 토론까지 자동으로 줄어드는 구조는 아니다. 오히려 완료 전에 작업의 이유를 묻는 사람의 개입이 중요해진다.

사람의 부담이 실제 줄었는가?PR별 승인·댓글·대기와 실제 검토·수정·수습 시간을 함께 본다.전자는 원글의 대리 지표. 실제 시간 수집은 총시간 목표를 확인하기 위한 제안이다.
실패가 늘지 않았는가?관찰 기간의 merge PR에 연결된 revert·incident, 심각도와 탐지·복구 시간revert·incident guardrail은 원글. 심각도·시간과 관찰 창의 고정은 제안이다.

위 지표는 같은 기간과 비슷한 위험 구성을 비교해야 한다. reviewer 변경 전후에는 고정 사례와 새로 보류한 사례를 함께 평가하면 알려진 사고에만 맞추는 위험을 점검할 수 있다. 보류 평가도 연구자의 제안이다. 승인 완화의 보편적 임계값은 원글에 없으므로 팀이 허용할 피해와 복구 능력에 맞춰 정해야 한다.

CI의 운영 품질도 전제다. 연결된 test impact analysis 글에서 listener는 실행 결과를 모으고 selector는 그 이력으로 테스트를 고른다. 이력이 밀리면 새 테스트나 고친 테스트의 반영도 늦어진다. 이 글은 Anthropic의 별도 CI 사례다. Claude Code 저장소가 같은 구현을 쓴다는 근거로 삼지 않는다. 검증 시스템이 최신 근거로 검사 대상을 고르는지 점검해야 한다는 조건을 보강한다. [7]

공개 관측은 승인 완화의 보편적 안전성을 입증하지 않는다

원글은 내부 운영의 경험 보고다. 공개 자료의 범위에 맞춰 전환을 해석해야 한다.

  • Claude Code의 처리량·revert 관측과 FIG D는 전후 비교다. 표본 수·구성·비교 기간의 상세가 없어 인과효과나 다른 팀의 기대 성과로 바꿀 수 없다.
  • 내부 bug reviewer의 투표 정족수, classifier 정확도, 평가셋 크기와 recall 값, 필터 A/B 효과, 총 운영 비용은 공개되지 않았다. 품질·비용의 재현을 원하면 자체 측정이 필요하다.
  • 공개 서비스는 실행 검증을 하지 않는다. 공개 security review OSS의 코드 독해도 실제 API 호출이나 운영 실험을 대신하지 않는다.
  • 잘못된 지적을 줄이는 필터는 놓치는 결함을 늘릴 수 있다. 리뷰 회수 감소와 noise 0, 인간 대체, 보안 보증은 같은 주장이 아니다.
  • 저자들은 팀 지식 공유의 공식 과정과 지표 악화 시 승인 조건을 자동 강화할 circuit breaker를 아직 갖추지 못했다고 밝혔다. 이를 완성된 자율 개발 체계로 소개하면 원글보다 강한 주장이다.

따라서 외부 팀이 가져올 수 있는 핵심은 책임을 보존한 채 반복 검증을 옮기는 설계 원리다. 회복할 수 없는 변경이나 결과를 판단할 사람이 없는 영역에서는 같은 승인 완화를 도출할 수 없다. 이 결론은 원글의 위험·소유·복구 조건에서 얻은 해석이다.

원글의 전체 논증과 핵심 reference의 본문을 확인했다

원글 전체, FIG A–D의 SVG 값과 구조, 아래 공식 문서와 공개 구현을 읽었다. 내부 시스템의 재현 실험은 수행하지 않았다.

공식 best-practices·Code Review·Customize·security review Help Center를 열었다. 발표 글과 연결된 TrueNAS PR의 bot 분석·작성자 응답도 확인했다. source control·CI·skills·HTML 활용 글, Boris Cherny의 개인 게시물은 각 주장에 필요한 본문을 읽었다. HN 반응은 원글과 대조할 수 있는 코드 이해 문제만 사용했다.

security review 저장소는 anthropics/claude-code-security-review@0c6a49f1fa56a1d472575da86a94dbc1edb78eda로 고정했다. README, action.yml, findings_filter.py의 제외·후보 판정, github_action_audit.py의 호출·출력, comment-pr-findings.js의 게시, filtering 문서와 eval README를 읽었다. 나머지 API client·prompt·eval 엔진·tests는 전체를 추적하지 않았다. 그래서 모델별 판정 품질이나 전체 실행 동작을 검증했다는 주장은 하지 않는다.

원글이 open channels에 연결한 Claude Tag 제품 소개는 책임 정책의 구현 근거로 사용하지 않았다. 그 밖의 제품 소개·하위 설정 문서·관련글 전체는 읽지 않았다. 내부 skills·risk classifier·운영 dashboard는 공개 자료로 확인할 수 없어 원글의 보고 수준으로 한정했다.
