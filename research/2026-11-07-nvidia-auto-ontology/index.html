NVIDIA Auto Ontology가 메타데이터로 만든 의미를 text-to-SQL에 쓰는 방식과 인증의 범위

NVIDIA Auto Ontology는 데이터베이스의 스키마, 표본 값, 질의 이력에서 Term, attribute, join 관계를 LLM으로 뽑아 agent의 text-to-SQL 문맥으로 쓰는 오픈소스 라이브러리다. 코드를 읽어 보면 LLM이 추론한 join 관계는 SQL 프롬프트에 검증된 경로로 들어가고, 사람이 켜는 인증 플래그는 이 경로를 바꾸지 않는다. 그래서 운영 전에 semantic FK 목록과 답의 SQL을 사람이 직접 봐야 한다. 공개된 정확도 수치는 아직 없다.

NVIDIA의 Auto-Ontology 팀이 GitHub에 공개한 라이브러리 저장소(NVIDIA/auto-ontology, v1.2.0 직후 커밋 c447003)와 같은 팀이 관리하는 평가 저장소(NVIDIA/auto-ontology-eval, 커밋 ec41b2c)다. NVIDIA 개발자 사이트의 소개 문구와 관리자의 커밋 메시지 두 건을 함께 읽었다.

LLM이 제안하고 데이터로는 겹침 0만 거른다

BEAVER dw에서 semantic FK 137개 중 17개가 이 검사로 지워졌다

 추론한 join은 검증된 경로로 프롬프트에 들어간다

SQL attribute는 참고로, 기준 열은 강한 힌트로 소개된다

 기본 설정은 실행 오류와 빈 결과에서만 고친다

결과가 나오는 틀린 SQL은 그대로 답이 된다

 사람의 인증 플래그는 이 경로를 바꾸지 않는다

배지 계산에만 쓰이고, 인증만 바꾸면 검색 색인도 다시 만들지 않는다

 정확도 개선 폭은 공개되지 않았다

eval 저장소에는 harness만 있고 결과 파일은 커밋되지 않는다

Auto Ontology는 agent가 읽을 의미 사전의 초안을 메타데이터에서 만든다

agent가 "매출"을 물으면 먼저 그 말이 어느 테이블의 어느 열인지, 어떤 join을 거쳐야 하는지 알아야 한다. Auto Ontology는 이 대응을 사람이 처음부터 쓰는 대신 연결된 데이터베이스에서 초안을 뽑는다.

NVIDIA는 README에서 동작을 생성, 사람의 인증, 답변의 순서로 설명한다. 생성 단계는 사람의 손을 거치지 않는다. ingestion이 스키마와 표본 값을 catalog에 넣고, semantic compile이 LLM을 불러 아래 표의 앞 세 가지 정의를 Postgres와 pgvector에 쓴다. custom analysis는 사람이 따로 등록한다.

NVIDIA 개발자 사이트는 이 결과를 업무 전문가가 시험하고 다듬고 인증할 "starting ontology"라고 부르고, NVIDIA 테스트에서 ontology 작성 시간이 90% 줄었다고 적는다. 측정 조건은 페이지에 없어서, 자기 팀의 작업 시간이 얼마나 줄지는 이 숫자로 가늠할 수 없다.

semantic FK가 이 구조에서 가장 무게가 크다. 4장에서 보듯 답을 만들 때 join 경로가 이 그래프에서 나오기 때문이다. 선언된 FK가 있으면 대개 그대로 옮기지만(대상 열에 attribute가 없으면 LLM 단계로 넘긴다), 선언이 없는 warehouse에서는 열 이름과 설명이 비슷한 후보 가운데 LLM이 고른 것이 join 경로가 된다. 그 뒤에 데이터로 확인하는 기준은 겹침 0 하나다. 이 검사는 선언된 FK와 추론한 FK를 가리지 않고 모든 semantic FK에 돈다. 그래서 아직 적재되지 않아 비어 있는 열의 선언된 FK도 지워진다. 관리자는 실제 참조도 대상 값의 대부분을 놓칠 수 있어서 겹침 비율이 낮다는 것만으로는 틀렸다고 할 수 없다고 설명한다. 그래서 값이 조금이라도 겹치는 잘못된 FK는 남는다.

이 가지치기는 2026-11-03에 들어왔다. BEAVER는 사설 data warehouse에서 가져온 enterprise text-to-SQL benchmark다. 관리자는 커밋 메시지에서 BEAVER의 dw 데이터베이스에 적용했을 때 semantic FK 137개 가운데 17개(값이 겹치지 않는 것 10개, 원본 열이 빈 것 7개)가 지워졌고, 지워진 것 가운데 정답 질의 300개에 join으로 쓰인 것은 없었다고 적었다. 남은 120개가 모두 맞는지는 이 측정이 말해 주지 않는다.

그래서: 선언된 FK가 적은 데이터베이스에 붙인다면, compile 직후 semantic FK 목록부터 사람이 훑어보길 권한다. 답의 join이 모두 여기서 나오므로, 코드를 읽은 결과로는 검토 한 번의 효과가 가장 크다고 본다.

Term은 프롬프트에 따로 한 덩어리로 들어가지 않고, 두 길로 검색에 영향을 준다. 첫째, 열(ColumnAttribute)을 색인할 때 열 이름 옆에 Term의 이름과 동의어를 붙이므로, 이 둘이 어떤 열이 걸리는지를 바꾼다. LLM은 걸린 열 가운데 하나를 기준 열로 고르고, 동의어는 "TERM GLOSSARY"로도 프롬프트에 붙는다. 둘째, 질문의 주어로 Term 하나를 따로 검색하는데, 이 색인에는 Term의 설명이 들어간다. 여기서 걸린 Term에 묶인 테이블이 후보 테이블에 더해진다. 그래서 Term의 설명을 고치면 어느 Term이 주어로 잡히는지, 곧 어떤 테이블이 후보에 오르는지가 달라질 수 있다.

모델이 보는 스키마는 ontology에 한정되지 않는다. 준비 단계는 질문과 개체로 원래 catalog의 테이블도 따로 검색해 "AVAILABLE TABLES"로 넣고, SQL이 실패해 데이터가 모자라다고 판단되면 재구성 단계가 테이블을 더 찾는다. 따라서 ontology에 없는 테이블도 쓰일 수 있지만, join 조건만큼은 semantic FK 경로가 가장 강한 지시를 받는다.

README는 SQL attribute를 "검토된 SQL 식"이라 부르고, agent가 이를 재사용하므로 같은 지표는 늘 같은 방식으로 계산된다고 설명한다. 프롬프트에서는 같은 정의가 참고 자료로 들어가므로, 모델이 다른 식을 쓰면 같은 지표도 질문마다 다르게 계산될 수 있다. custom analysis는 질문과 가까우면 전체 SQL을 출발점으로 그대로 써도 된다고 소개된다. 반대로 join 경로는 compile이 추론한 semantic FK에서 왔는데도 "verified"라는 말과 함께 들어간다. 모델은 이 경로를 고르면 그대로 따르라는 지시를 받는다.

  • 무게는 프롬프트 문구에서 읽은 것이다. 모델이 실제로 얼마나 따르는지는 잰 자료가 없다.

그래서: 같은 지표가 늘 같은 식으로 계산돼야 한다면, 답에 붙은 SQL에 그 SQL attribute의 식이 들어갔는지 사람이 확인해야 한다. 코드에는 그 일치를 확인하는 단계가 없다.

사용자가 "지역별 매출"을 물으면 준비 단계는 이 FK가 든 경로를 SQL 프롬프트에 검증된 join으로 넣는다. 의도 검증 LLM도 의미 모델에서 온 경로를 따른 join은 유지하라는 지시를 받는다. SQL은 창고 이름별 합계를 돌려주고 결과가 비지 않으므로 빈 결과 수리도 돌지 않는다. 답은 SQL과 함께 정상으로 나간다. 실행 전 join 경로 검사를 켜도 결과는 같다. 이 검사는 먼저 semantic FK 그래프에 그 edge가 있는지 보는데, 잘못된 edge가 그래프에 있기 때문이다.
