NVIDIA Auto Ontology가 메타데이터로 의미를 만들고 SQL을 검사하는 방식

NVIDIA Auto Ontology는 DB 메타데이터와 쿼리 이력에서 LLM으로 업무 개념(Term), 재사용할 계산식(SQL attribute), 표 사이의 join을 만들어 SQL 작성 프롬프트에 넣는 라이브러리다. 코드를 읽어 보면 기본 설정의 결정적 검사는 문법 오류, 실행 오류, 빈 결과를 잡는다. 그래서 행이 나오는 잘못된 join은 LLM 검토만 거치고 certify 표시도 답변에 쓰이지 않으니, 답의 SQL에서 join 컬럼을 직접 확인해야 한다.

NVIDIA의 Auto-Ontology 팀이 Apache-2.0으로 공개한 저장소를 커밋 c447003(2026-11-06) 기준으로 읽었다. 성과 주장은 NVIDIA 공식 블로그(Erik Pounds, 2026-10-21), NVIDIA Developer의 Agent Knowledge Foundation 페이지, 같은 회사의 평가 저장소 ontology-sql-eval에서 확인했다.

관계를 표와 표 사이에 두지 않고 컬럼과 Term 사이에 두는 점이 이 설계의 중심이다. 예를 들어 README의 Wide World Importers 예시에서 invoicelines 표의 stockitemid 같은 FK 컬럼은 코드대로라면 Term의 attribute가 되지 않는다. 대신 ③ 단계에서 Stock Item Term의 column attribute를 가리키는 semantic FK가 된다. 그래서 질문에 나온 단어가 Term에 닿으면 그 Term에 붙은 semantic FK를 따라 join 경로를 얻는다.

선언된 FK는 대부분 그대로 semantic FK가 된다. 자기 표를 가리키는 선언은 버리고, 대상 컬럼에 attribute가 없으면 추론 경로로 넘긴다. 선언이 없으면 컬럼 이름과 설명, 샘플 값으로 한 번, 이름만으로 한 번 embedding 검색을 해서 값이 유일한 컬럼의 attribute를 3개씩, 합쳐 최대 6개 얻는다. LLM이 그중 하나를 고르고, LLM이 고르지 않으면 이름이 같은 후보 컬럼에 FK의 샘플 값이 모두 들어 있는지 DB에 물어 정한다. 그래서 FK 제약을 걸지 않은 warehouse일수록 관계의 많은 부분이 LLM의 판단과 샘플 값의 일치로 정해진다. 컴파일을 중간에 취소하면 Term까지만 남고 ③과 ④는 건너뛴다.

② 단계의 프롬프트에는 관련 표의 schema와 중요 컬럼, SQL attribute, Term의 동의어, join 경로가 들어간다. SQL attribute는 계산식과 전체 SQL을 참고하라는 안내 절로 들어가고, 모델이 그 식을 그대로 쓰는지 코드가 확인하지는 않는다. join 경로는 semantic FK 그래프에서 찾는데, 이 탐색은 컴파일 때(2장의 ③) 기본으로 정한 join만 쓴다. 그래서 같은 표를 가리키는 FK가 여럿이면 프롬프트에는 기본 join 하나만 경로로 실린다.

③ 단계의 의도 판정 LLM은 질문, SQL, 쓰인 표와 컬럼, join 경로를 받는다. 기본 설정에서는 join 경로가 "검증된 경로이니 따르는 join은 유지하고 문제 삼지 말라"는 문구와 함께 들어간다. 지시는 심각한 문제가 없으면 통과시키라는 쪽이다.

다시 쓰기는 첫 시도에서 오류의 종류를 LLM으로 분류한다. 필요한 데이터가 빠졌다고 보면 표를 더 찾아 후보에 넣고, 고칠 수 있는 오류면 지금 표로 다시 쓴다. 어느 단계가 돌려보냈든 다시 쓰기 한 번으로 세고, 7번이 쌓인 뒤 검증이나 실행에서 또 걸리면 답할 수 없다는 응답으로 끝난다. 빈 결과 확인과, 켜 두었을 때 실행 직전에 도는 값과 join 경로 검사는 다시 쓰기가 5번을 넘기면 더 막지 않고 SQL을 보낸다.

  • 판은 text_to_sql_graph.py의 add_conditional_edges를 따라 그렸고, 실행과 빈 결과 확인에서 다시 쓰기로 돌아가는 화살표는 생략했다. Kumo 예측 분기와 메타데이터 질문 분기도 뺐다.
  • GROUP BY가 무의미한 집계를 잡는 검사는 DETECT_VACUOUS_GROUP_BY를 켜야 돈다.

기본 join과 다른 역할의 FK를 묻는 질문은 잘못된 join으로 답이 나와도 검사를 통과한다

maintainer가 코드 주석에 든 treatments 표를 따라간다. 이 표의 prescribing_clinician_id와 reviewing_clinician_id는 둘 다 clinicians 표를 가리키고, 아래 결과는 가상의 질문을 코드의 분기에 대어 본 예측이다.

컴파일에서 두 컬럼은 모두 Clinician Term에 semantic FK로 이어지고, LLM이 처방한 의사 쪽을 기본 join으로 골랐다고 하자. 이제 "검토한 의사별 치료 건수"를 묻는다. SQL 작성 프롬프트의 join 경로에는 기본 join인 prescribing_clinician_id만 실린다. 모델이 이 안내를 따르면 처방한 의사로 묶은 SQL이 나온다. 이 SQL은 실제 표와 컬럼만 쓰므로 parse와 카탈로그 검사를 통과하고, 실행하면 행도 나온다. 그래서 빈 결과 수리도 움직이지 않는다. 남은 의도 판정 LLM은 같은 join 경로를 검증된 경로로 받고, 그 경로를 따르는 join은 문제 삼지 말라는 지시도 받는다. 그래서 기본 설정에서는 이 SQL을 막으라는 지시가 어느 단계에도 없다.

join 경로 검사를 켜도 결정적 검사는 이 SQL을 통과시킨다. 이 검사는 SQL의 join을 semantic FK 그래프의 경로와 맞춰 보고, 같으면 바로 통과시킨다. 처방한 의사로 묶은 SQL은 그래프의 기본 경로와 같다. 대신 의도 판정 LLM의 프롬프트가 바뀐다. 검증된 경로 절이 빠지고, join이 질문에 비해 틀린 엔티티에 닿았고 더 맞는 실제 관계를 댈 수 있으면 문제로 표시하라는 지시가 들어간다. system prompt는 그 예로 같은 개념의 다른 역할을 든다. 그런데 같은 호출의 user prompt는 같은 개념의 다른 역할로 한 join은 괜찮다고 적는다. 그래서 이 설정에서도 의도 LLM이 역할 오류를 잡을지는 두 지시 중 어느 쪽을 따르느냐에 달려 있고, 코드로는 알 수 없다.

join 경로 검사 자체는 JOIN ON의 등호 조건 중 한쪽이라도 semantic FK에 걸린 컬럼인 것만 본다. 쓴 컬럼 쌍이 그래프의 경로와 다르면 두 컬럼의 값 겹침을 재고, 20% 미만이거나 재지 못하면 검사에 걸린다. 그래프가 같은 두 표의 다른 컬럼 쌍을 알면 그 쌍으로 고치고, 중간 표를 거치는 경로만 알면 그 경로로 고치거나 다시 쓰기로 돌려보낸다. 아무 경로도 모르면 지어낸 join으로 표시한다. 두 컬럼이 같은 hub 표를 가리키고 어느 쪽도 PK나 unique가 아니면, 겹침과 상관없이 hub 표를 거치라고 표시한다.

설정기본 join을 따라 역할이 틀린 SQL관계가 없는 id 컬럼끼리 join한 SQL
기본값, join 경로 검사 꺼짐의도 LLM은 이 join을 문제 삼지 말라는 지시를 받으므로 실행된다의도 LLM이 잡지 않고 결과가 비지 않으면 실행된다
join 경로 검사 켬 (DB_PROBE_JOIN_PATH_CHECK)결정적 검사는 통과하고, 서로 다른 두 지시를 받은 의도 LLM만 남는다한쪽이 semantic FK에 걸린 컬럼이고 그래프가 모르는 쌍이면, 값 겹침이 20% 미만이거나 재지 못할 때 검사에 걸린다
  • 표는 db_probe/join_path_check.py:262-479, sql_parse_validation.py:1024-1056의 분기와 .env.example:119-157의 기본값에서 만든 예측이다. 실제로 실행해 본 결과는 아니다.
  • proactive filter 값 검사(DB_PROBE_PROACTIVE)와 JSONB 경로 검사도 기본으로 꺼져 있다.

그래서: 역할이 여럿인 FK가 있는 표라면 어느 컬럼이 기본 join인지 확인해야 한다. model export에 semantic FK마다 use_in_join_paths 값이 실리므로 거기서 볼 수 있다. 다른 역할을 묻는 질문은 답의 SQL에서 join 컬럼을 직접 확인한다.

README는 사람이 이름, 설명, SQL attribute를 certify한다고 설명한다. 저장소 코드에서 이 표시가 어디서 읽히는지 따라가면 답변에 닿는 길이 없다.

certify는 Term의 이름과 설명, column attribute, SQL attribute마다 붙은 true나 false 값이다. 기본값은 false이고, 컴파일은 이 값을 쓰지 않는다. 사람이 UI의 checkbox나 PATCH API로만 바꾼다. 이 값을 모아 Term마다 certified, partial, pending 중 하나를 정하고, Terms 목록이 그 배지를 보여 준다.

답변 경로의 코드인 auto_ontology/retrieval에서 certif를 찾으면 literal_check.py의 주석 하나만 나온다. SQL attribute를 후보로 가져오는 함수도 certified 컬럼을 고르지 않는다. 그래서 certify하지 않은 SQL attribute도 certify한 것과 같은 자격으로 프롬프트에 들어간다. MCP의 ask_question도 같은 chat API를 부르므로 이 경로를 탄다. semantic FK를 저장하는 column__semantic_fk 표에는 certified 컬럼이 아예 없어서, join 관계는 certify할 수도 없다.

README의 Validate 항목은 생성된 쿼리를 certified 정의와 lineage에 비춰 검사한다고 적는다. 읽은 코드에서 이 설명에 해당하는 검사는 찾지 못했다. 같은 저장소의 management skill도 지금의 certify 값은 원자적인 검토나 승격 체계가 아니라고 적는다. 그래서 운영에서 certify를 승인 절차로 쓰려면 certify하지 않은 정의를 답변에서 빼는 장치를 따로 만들어야 한다.

  • 검색: grep -rn -i certif auto_ontology/retrieval → literal_check.py:765 주석 1건. auto_ontology/dal/sql_attributes.py의 fetch_sql_attributes_with_sql은 certified를 고르지 않는다.
  • frontend 코드는 열지 않았다. UI가 certify하지 않은 정의를 숨기는지는 확인하지 않았다.
