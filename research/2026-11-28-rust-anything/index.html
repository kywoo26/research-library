rust-anything의 Rust 이식 검사와 보장 범위

rust-anything은 기존 프로그램의 동작을 기록하고 Rust 이식을 재검사하는 migration harness다. 코드 분석상 이점은 bridge·반복 검사·점진 전환을 재사용하는 데 있다. 다만 TS/JS는 서로 다른 예외도 일치로 세며, 일반 agent보다 이식 성공률이 높다는 A/B 결과는 아직 없다.

CLI가 이식 대상을 좁히고 실패 결과를 agent에게 돌려준다

사용자가 느린 명령을 주면 go가 그 workload를 profile한다. 구현은 실행 시간 비중으로 정렬한 후보 중 인자를 받는 export를 고르며, bridge 가능 여부와 대기 시간을 확인한다. 그래서 사용자가 임의의 작은 함수부터 Rust로 바꾸는 시행착오를 줄일 수 있다. 다만 어떤 workload를 줄지는 사용자의 몫이다.

정적 분석인 analyze는 import 관계로 이식 순서를 만들고 위험 구문·크기·의존성·테스트 유무를 점수에 반영한다. readiness는 이식 성공 확률로 보정한 값이 없으므로 우선순위용 heuristic으로 읽어야 한다. 속도가 목적이면 실제 profile과 benchmark가 이 판단을 보완한다.

도구는 Rust crate, binding, 원본의 입출력 기록과 작업 지시를 준비한다. 실제 계산 로직은 agent 또는 사람이 구현한다. 기본 agent 호출 예산은 3회이고, build·diff·gate가 실패하면 진단을 다음 지시에 붙인다. 예산을 다 쓰면 실패 상태로 끝나므로 “끝날 때까지 무한히 고친다”는 실행 계약을 기대하면 안 된다.

다시 실행하면 profile을 다시 하고 이미 있는 crate와 유효한 기록을 재사용한다. 통과 뒤에도 benchmark가 원본보다 느리면 자동 전환을 멈춘다. 이 검사는 해당 기록과 측정 환경에서의 관찰이므로 실제 트래픽의 지연이나 처리량은 전환 전에 별도로 확인해야 한다.

parse 한 건을 따라가면 생성 코드와 이식 코드의 경계가 보인다

저장소에 포함된 vercel/ms의 parse는 기간 문자열을 숫자로 바꾸는 실제 이식 예다. manifest는 원본의 src/index.ts export와 타입을 가리킨다. 기록 파일에는 정상 결과와 오류가 함께 남고, 생성된 wrapper가 호출을 Rust로 넘긴다. 아래 흐름은 포함된 artifact와 CLI 코드를 연결한 추적이며, native binary를 새로 빌드해 실행한 결과는 아니다.

원본 export     src/index.ts의 parse(str: string)
       ↓ bridge가 타입·export를 읽음
도구가 준비    rust-anything.json · cases.jsonl
              src/lib.rs · index.cjs · port.rs의 빈 함수
       ↓ 사람 또는 agent가 구현
이식 코드      port::parse(String) → Result<f64, String>
       ↓ 생성된 binding을 통해 호출
호출자         index.cjs → parseWire → port::parse
       ↓ diff / gate 결과를 TASK와 함께 돌려줌
검사 뒤 전환   go의 bench 통과 → enable의 원본 재바인딩

이식된 함수는 문자열 길이를 encode_utf16().count()로 센다. JS의 길이 검사가 UTF-16 code unit을 기준으로 하기 때문이다. Rust에서 문자열 byte 길이나 문자 개수를 쓰면 emoji에서 원본과 다른 입력을 받아들이게 된다. 어떤 Rust 표현이 원본 동작에 맞는지 판단해 구현하는 일은 agent에게 남는다.

bridge는 이 결정을 도울 공통 장치를 제공한다. TS/JS 기록 codec은 일반 JSON으로 사라지는 undefined, NaN, 음의 0과 잘못 짝지어진 UTF-16을 marker로 표현한다. 타입에 맞는 binary wire와 변환 helper도 생성한다. 그렇지만 모든 JS 값을 그대로 운반하는 것은 어렵다. generator, 함수 값, 일부 클래스 identity 같은 경계는 제외하며, Rust String을 받는 생성 wrapper는 lone surrogate를 거부한다.

담당실제로 맡는 일남는 판단
도구타입 추적, crate와 binding 생성, 사례 수집·재실행도메인에 맞는 입력과 전체 사용 범위
agent / 사람원본을 읽고 port.rs에 알고리즘·오류·언어 의미 구현원본의 버그를 유지할지, 의도적 변경을 승인할지
호출자 통합enable로 지원 언어의 함수를 재바인딩하거나 app wire로 연결batch API 사용과 rollout 시점

성능도 경계에서 달라진다. 작은 함수를 원소마다 호출하면 변환과 FFI 비용을 원소마다 낸다. batch는 데이터를 Rust에 한 번 넘겨 보관하고 loop를 그 안에서 돌리도록 생성된다. 따라서 빨라진 사례에는 병렬화나 인덱스 재사용도 포함될 수 있다. 같은 알고리즘을 다른 언어로 적은 효과와 구분해 측정해야 한다.

gate 통과는 기록과 비교 정책에 맞았다는 뜻이다

핵심 계약은 기록된 입력에 Rust 후보를 다시 실행해, 비교기가 관찰하는 결과가 허용 범위 안에 드는지 확인하는 것이다. 원본은 expected 값을 만들어 주므로 agent가 자기 구현에 맞춰 expected까지 작성하는 위험을 줄인다. 하지만 그 expected와 비교 규칙을 어떻게 정했는지에 따라 같은 “통과”의 의미가 달라진다.

검사구현이 확인하는 것해석할 때 필요한 조건
build · fmt · clippy · test빌드, 형식, 경고, Rust 테스트 명령 성공테스트가 요구사항을 충분히 담는지는 별도 판단
API · behavior기록을 재생하며 호출한 export의 누락과 diff 실패를 검사공개 API 전체나 모든 입력에 대한 동등성으로 확대할 수 없음
recording저장한 unit fingerprint 변경, 기록 앞부분 수정·삭제 감지unit 밖 dependency 변경과 metadata 부재는 더 확인해야 함
error cases · coverage감지한 오류 함수에 실패 사례가 있는지 검사; coverage 표시함수 안의 오류 분기별 도달 검사가 아님; 낮은 coverage도 통과
unsafe · cheat guard · testsSAFETY 주석, 의심스러운 literal, 테스트·assert 개수 패턴안전성 증명이나 악의적 agent를 막는 신뢰 경계로 쓸 수 없음

특히 오류의 동등성은 느슨하다. TS/JS는 함수와 클래스 호출 모두 양쪽에 오류가 있으면 메시지가 달라도 일치로 센다. 메시지가 Rust panic:으로 시작하면 실패시킨다. Python은 같은 오류 종류를 허용하고, Rust 쪽이 TypeError이면 원본의 다른 오류 종류도 허용한다. 사용자가 메시지나 예외 타입으로 분기한다면 별도의 엄격한 검사가 필요하다.

이를 확인하려고 고정 소스의 JS 비교 script와 Python 비교 함수 정의를 그대로 추출해 실행했다. JS 후보는 직접 만든 stand-in이고 Rust binding은 쓰지 않았다. 그러므로 아래 표는 실제 comparator 정책의 실행 확인이며, native bridge나 gate 전체의 재현 결과로 읽으면 안 된다.

경로기록과 후보의 차이실행 결과
TS 함수원본 오류 → 전혀 다른 TypeError 메시지통과
TS 클래스생성자 오류 메시지를 변경통과
TS 함수정상 반환값 1 → 2실패
TS 함수원본 오류 → Rust panic: 접두 오류실패
PythonValueError의 메시지만 변경통과
PythonValueError → TypeError통과
PythonValueError → RuntimeError실패

agent에게 주는 TASK는 오류 메시지까지 원본과 맞추라고 지시한다. 그러나 TS/JS comparator는 그 요구를 강제하지 않는다. 프롬프트에 적힌 요구와 실행 코드가 통과시킨 범위를 구분해야 하는 구체적인 예다.

사용자가 설정하는 허용 정책도 결과를 넓힌다. known-diffs.jsonl의 함수·입력·실제 결과가 같은 차이는 사유와 함께 통과에 포함된다. 저장된 float tolerance나 key-order 무시 설정도 후속 gate에 적용된다. 따라서 통과 건수만 볼 때는 의도적으로 허용한 차이와 비교 설정도 함께 열어야 한다.

“모든 오류 경로”도 구현에 맞춰 좁혀 읽어야 한다. 코드는 export 안에서 처음 발견한 throw/raise 같은 구문을 찾고, 그 함수 이름에 오류 기록이 하나라도 있는지 확인한다. coverage 항목은 결과를 표시하되 항상 통과로 추가한다. 별도 분기 coverage나 중요한 입력 조합을 채우지 않은 상태에서도 gate가 통과할 여지가 있다.

부정행위를 줄이는 검사 역시 유용한 heuristic이다. literal 검사는 기록 답의 단순 복사를 찾고 테스트 검사는 개수 감소를 찾는다. 그러나 assert의 의미가 약해졌는지나 계산 전체가 진짜 Rust로 옮겨졌는지까지 판정하지 않는다. 기록 metadata도 같은 작업 폴더에 있고, 없거나 읽지 못하면 일부 무결성 검사를 건너뛴다. 독립된 CI에서 원본·기록·비교 설정을 보호하고 재검사해야 더 강한 운영 조건이 된다.

앱 전체 이식은 외부 동작을 기록하고 원본 의존을 줄여 간다

함수 단위 bridge로 앱 전체의 호환성을 판단하기 어려우므로, 별도의 app 경로가 바깥에서 프로그램을 실행한다. CLI는 출력·종료 상태·파일 변화 등을 기록하고 HTTP 서버는 요청과 응답을 기록한다. Rust front door를 앞에 두고 이식한 unit을 연결하면, 아직 Rust가 처리하지 못하는 작업은 원본으로 보낼 수 있다.

unit의 gate가 통과하는 것과 앱 요청이 원하는 결과를 내는 것은 서로 다른 검사다. app replay는 외부 기록을 비교하고, fallback 집계는 그중 얼마가 원본에 의존하는지 보여 준다. lift는 기록 사례에 fallback이 남아 있으면 거부한다. 이후 복사본에서 binding과 fallback을 제거하고 build·replay를 통과시킨 뒤 결과를 반영하도록 짜여 있다.

이 방식은 부분 이식을 배포하고 되돌리는 작업을 구체화한다. 다만 fallback이 0이라는 수치는 실행한 사례 집합을 기준으로 한다. 아직 주지 않은 요청이나 동시 실행에서 처리할 경로까지 전부 옮겼다는 의미는 추가 검증이 필요하다.

원본을 반복 실행해 달라지는 값을 정규화하는 기능은 timestamp 같은 잡음을 줄이지만, 지워진 차이는 그만큼 비교에서 빠진다. side effect 수집도 설정한 email·webhook·DB 같은 경계에서 수행한다. shadow에 실제 결제나 메일을 두 번 실행시킬 수 있는 시스템이라면 해당 효과를 분리해 한 번만 발생시키는 경로부터 검증해야 한다. 원본의 비결정적 결과 자체를 정답으로 삼을 때는 단순 masking보다 어떤 사건을 재생할지 설계하는 일이 더 중요해진다.

“이 코드를 Rust로 바꾸고 테스트하라”는 요청만 주면 agent가 이식 경계와 expected 값, 테스트와 완료 조건을 함께 정하게 된다. rust-anything은 원본 runtime에서 사례를 수집하고 같은 CLI로 다시 판정하므로, agent가 세션마다 검증 절차를 새로 만드는 부담을 줄일 수 있다. 이는 코드 구조에서 얻는 판단이며 성공률 향상을 측정한 결론은 아니다.

능숙한 agent 작업에도 자동 검사 loop는 이미 있다. 예를 들어 Aider 공식 문서는 수정 후 lint와 지정한 test 명령을 실행하고 실패를 고치게 하는 기능을 설명한다. 그러므로 “도구가 있으면 검사한다”만으로 차별성을 설명하기는 부족하다. 여기서 재사용할 자산은 여러 언어의 bridge, 원본 기반 characterization, mismatch 진단과 전환 장치의 조합이다.

팀이 이미 독립된 differential test와 운영 shadow를 갖췄다면, 같은 원리의 검증을 기존 agent로 수행할 수 있다. 그 팀은 rust-anything의 경계를 적용하는 비용과 재사용 이익을 비교하면 된다. 반대로 테스트가 빈약하고 원본을 실행할 수 있는 라이브러리라면 기록부터 시작하는 기본 경로가 도움이 될 가능성이 크다.

원본을 oracle로 쓰는 원리는 다른 migration에서도 적용됐다. Anthropic Engineering의 Messages API 사례는 기존 시스템과 비교하고 production shadow를 통해 차이를 찾으며 사람의 리뷰를 거쳤다. 이 사례는 검증 전략의 외부 근거다. rust-anything을 사용했다는 증거나 이 도구가 같은 운영 체계를 제공한다는 근거로 옮겨 읽을 수는 없다.

지원 여부도 command별로 봐야 한다. TS/JS·Python·Go·Java·Ruby는 profile 경로가 있지만 나머지 언어에는 대체 profiler를 안내하는 분기가 있다. 자동 in-place 전환은 TS/JS·Python·PowerShell에 한정된다. C++처럼 unit adapter가 없는 언어도 프로그램 바깥의 app record/replay 대상으로는 삼을 수 있다. 언어 이름 하나가 전체 자동화를 뜻하지 않는다.

setup은 agent 설정에 MCP server와 skill을 추가한다. Codex에서는 설정 파일과 skill 폴더가 대상이다. bridge는 프로젝트 안에 Rust crate와 기록을 만들고, enable은 원본 파일에 표시된 재바인딩 block을 삽입한다. disable은 그 block을 제거하며 runtime switch로 원본을 선택할 수도 있다. 설치 설정 제거와 프로젝트 이식 artifact 정리는 별개 작업으로 잡는 편이 안전하다.

  • pilot의 기준을 원본과 함께 고정한다실제 입력, 오류 메시지·타입, key 순서, 허용 오차와 의도한 차이를 검토하고 기록을 보호한다.
  • agent가 고치기 어려운 별도 판정기를 둔다새 입력과 중요한 오류 분기를 독립 CI에서 검사하고, Rust가 실제 계산을 맡는지 리뷰한다.
  • 실제 배포 조건에서 성능과 복귀를 확인한다같은 자원과 호출 패턴으로 측정하고 shadow와 원본 복귀 경로를 확인한 뒤 전환한다.

이 조건을 갖추면 rust-anything은 agent가 매번 수작업으로 준비하던 migration 절차를 시작하는 도구가 된다. 전체 동작 보장과 agent 대비 생산성 향상은 그 위에 쌓는 입력 coverage, 독립 검사와 실제 비교 실험으로 판단해야 한다.

출처와 확인한 범위

주 자료는 Erkam Yaman의 rust-anything v5.0.1, commit a1e9509b31bd89e0cbf039e86a39ca338d2c67fe다. README·CLAUDE·명령 설명과 STATUS·실제 이식·평가 문서를 읽고, go·profile·analyze에서 bridge·record·diff·gate·enable까지 이어지는 구현을 추적했다. 오류 검사·recording 무결성·codec·Python comparator, app replay·lift의 핵심 분기도 확인했다. vercel/ms는 manifest·기록·wrapper·Rust port를 연결해 읽었다.

언어별 codegen과 adapter 전체, 모든 통합 테스트와 demo port 전체를 열지는 않았다. 따라서 언어 전반의 동작을 독립 재현했다고 해석할 수 없다. 이력이 없는 고정 snapshot을 읽었으므로 기여자 수·release 주기 같은 유지보수 통계도 결론에 사용하지 않았다.

직접 실행한 범위는 추출한 JS/Python comparator와 Python scorer의 no-op 음성 대조다. Rust toolchain을 사용할 수 있는 설정이 없어 새로 설치하지 않았고, CLI build·native bridge·gate 전체 및 agent A/B는 실행하지 않았다. 실증 표의 이식·성능 수치는 maintainer의 자체 보고다.
