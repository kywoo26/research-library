When a query returns two columns with the same name, the Postgres, MySQL and SQLite connectors return wrong data and no error. All three build each row as a dict keyed by column name, so one value overwrites the other before the DataFrame is created:

## What happens

With one customer and one order:

```sql
SELECT c.id, o.id, c.name, o.name
FROM customers c JOIN orders o ON o.customer_id = c.id;
```

| Connector | Columns | Row |
|---|---|---|
| Expected | `id, id, name, name` | `1, 100, Ada, first order` |
| Postgres 17.7 | `id, name` | `100, first order` |
| MySQL 9.4 | `id, id, name, name` | `100, 100, first order, first order` |
| SQLite | `id, id, name, name` | `1, 1, Ada, Ada` |
| DuckDB (not affected) | `id, id_1, name, name_1` | `1, 100, Ada, first order` |

`SELECT *` over the same join behaves the same way. Aliasing the columns avoids it.

The problem reaches the text-to-SQL path. `_run_sql` on Postgres returns `[{"id":100,"name":"first order"}]` with `error=None`, so nothing triggers a retry and the customer's values are simply gone.

`_deduplicate_result_columns`, added in #397, can't help here because it only sees the frame afterwards. On Postgres the duplicates have already collapsed. On MySQL and SQLite it renames the labels, but the values are already wrong: `{"id":1,"id__2":1,"name":"Ada","name__2":"Ada"}`. Its test passes because it builds the frame by hand with `dialect="postgres"`, a frame the Postgres connector can't produce.

I reproduced this at the connector and `_run_sql` level against real Postgres, MySQL and SQLite databases. I didn't run it through the full chat flow with a model.

## Reproduce

SQLite, so no server is needed:

```python

import tempfile
from pathlib import Path

from auto_ontology.connectors.sqlite import SQLiteDatabase

with tempfile.TemporaryDirectory() as tmp:
    path = Path(tmp) / "shop.db"
    conn = sqlite3.connect(path)
    conn.executescript("""
        CREATE TABLE customers (id INT, name TEXT);
        CREATE TABLE orders (id INT, customer_id INT, name TEXT);
        INSERT INTO customers VALUES (1, 'Ada');
        INSERT INTO orders VALUES (100, 1, 'first order');
    """)
    conn.close()

    df = SQLiteDatabase(f"sqlite:///{path}").execute(
        "SELECT c.id, o.id, c.name, o.name "
        "FROM customers c JOIN orders o ON o.customer_id = c.id"
    )

```

On `caced11e` this prints `[[1, 1, 'Ada', 'Ada']]`.

## Possible fix

Use tuple rows and take the names from `cursor.description`, as the Trino and Snowflake connectors already do:

```diff
# postgres.py
-    with conn.cursor(row_factory=dict_row) as cur:
+    with conn.cursor(row_factory=tuple_row) as cur:
         ...
         rows = cur.fetchall()
-    return pd.DataFrame(rows)
+        columns = [column[0] for column in cur.description]
+    return pd.DataFrame(rows, columns=columns)

# mysql.py
-            cursor = connection.cursor(dictionary=True)
+            cursor = connection.cursor()

# sqlite.py
-            [dict(row) for row in rows], columns=[col[0] for col in cur.description]
+            [tuple(row) for row in rows], columns=[col[0] for col in cur.description]
```

[issue #428 open by codersgl (NONE) created 2026-11-05T14:51:54Z] Docs: `SQLDatabase` documents a `dialect` constructor argument that does not exist
### Where

`auto_ontology/connectors/base.py` — the `SQLDatabase` class docstring (~lines 100–113),
and the abstract `__init__` declared just below it (~line 132).

### What looks wrong

The class docstring documents two constructor parameters:

```
Parameters
----------
connection_string:
    A driver-specific connection string or database path.
dialect:
    SQL dialect used by this connector (e.g. ``"duckdb"``, ``"snowflake"``).
    Used by the text-to-SQL agent to emit dialect-appropriate SQL.
```

But `dialect` is not a constructor parameter. It is an abstract property:

```python
@property
@abstractmethod
def dialect(self) -> str:
    """Return the dialect of the database."""
```

and the abstract constructor takes only a connection string:

```python
@abstractmethod
def __init__(self, connection_string: str) -> None: ...
```

Every implementation returns a hard-coded constant — `clickhouse.py` → `"clickhouse"`,
`databricks.py` → `"databricks"`, `duckdb.py` → `"duckdb"`, `kyuubi.py` → `"spark"`,
`heavydb.py` → `"postgres"` — and no connector accepts a `dialect` argument.

### Secondary point

The same abstract signature is narrower than reality: `SnowflakeDatabase`,
`DatabricksDatabase`, `KyuubiDatabase` and `TrinoDatabase` all accept
`schemas: list[str] | None` as a second constructor parameter.
`registry.create_connector` absorbs that difference by dispatching on the class, so
nothing breaks at runtime — but a reader of `base.py` cannot see that the capability
exists.

### Impact

Documentation only. I could not find runtime behaviour that depends on either
mismatch.

It matters for two audiences:

- anyone reading `base.py` to understand the connector contract (the docstring
  suggests `dialect` is per-connection configuration, which is exactly what the
  abstract property prevents);
- anyone writing a connector outside this repo, who would implement `__init__` from
  the documented signature and then be surprised by the `schemas` variants.

For clarity, this is not the same `dialect` that `model_interchange` reads from a
saved connection — that one is an engine label on the stored connection form.

### Suggested fix

- Drop `dialect` from the `Parameters` section and describe it as the abstract
  property subclasses implement. `dialect`'s own property docstring already says
  what it returns, so nothing needs to be added there.
- Decide whether `schemas` belongs in the base `__init__` signature or should at
  least be documented as a per-connector extension.

No code change is required for correctness; both are documentation fixes.

### What happens

#### 1. Dropped or newly denied tables leave `term` and `column_attribute` rows that escape `delete_semantic_layer(database_name)` and `delete_all_data(database_name)`

1. Suppose table `shop.orders` (`id = 'tbl-1'`) in database `D` is ingested and compiled into a `Term` (`id = 'term-1'`, `name = 'Order'`) and `ColumnAttribute` rows (`table_id = 'tbl-1'`).

[issue #453 open by CactusQuill (NONE) created 2026-11-07T09:03:32Z] SQLite connector drops foreign keys written without a column list or in a different case
### Summary

`SQLiteDatabase.get_fks()` passes `PRAGMA foreign_key_list` output straight through. That PRAGMA reports the constraint as it was written in the DDL, not as resolved by SQLite:

1. **Implicit parent key.** `REFERENCES customer`, with no column list, is valid SQLite and means "customer's primary key". The PRAGMA reports the referenced column (`to`) as `NULL`, so `get_fks()` emits `referenced_column = None`.
2. **Case.** SQLite identifiers are case-insensitive, so `FOREIGN KEY (CUSTOMER_ID) REFERENCES customer(ID)` against `CREATE TABLE Customer (Id ...)` is valid. The PRAGMA returns `CUSTOMER_ID` / `customer` / `ID` as typed, while the catalog stores the declared names `customer_id` / `Customer` / `Id`.

`catalog/store/schemas.py:add_fks()` looks up both ends by exact `(schema, table, column)` and silently `continue`s if either is missing. Both kinds of key are therefore dropped from the catalog without a warning. No relationship gets stored, so join paths and the ontology lose that edge.

### Reproduce

```python
import sqlite3, tempfile, os
from auto_ontology.connectors.sqlite import SQLiteDatabase

path = os.path.join(tempfile.mkdtemp(), "shop.sqlite")
c = sqlite3.connect(path)
c.executescript("""
CREATE TABLE customer (customer_key INTEGER PRIMARY KEY);
CREATE TABLE orders (id INTEGER PRIMARY KEY, customer_id INTEGER REFERENCES customer);
""")
c.close()
print(SQLiteDatabase(f"sqlite:///{path}").get_fks()[["column_name", "referenced_table", "referenced_column"]])
#   column_name referenced_table referenced_column
# 0 customer_id         customer              None     <- add_fks skips this row
```

Composite keys (`FOREIGN KEY (a, b) REFERENCES parent`) are affected the same way: every row gets `None`.

### Expected

`get_fks()` returns the parent's primary-key column(s), paired with the child columns in key order using the PRAGMA's `seq`, and uses the declared case for every table and column name. Explicit, correctly cased references are unchanged.


[issue #459 open by negativeskew (NONE) created 2026-11-07T17:55:39Z] Semantic-key overlap check stops when the column types are different, and a key with no shared values stays
## Summary

The function `prune_disjoint_semantic_fks` in `auto_ontology/semantic/semantic_fk.py` finds
semantic keys with no shared values. It uses this condition: `{sc} IN (SELECT {tc} FROM {target})`.

`semantic FK overlap check skipped` to the log at INFO level, and the key stays.

target attribute. Thus a key that cannot join can become a join path again on each scheduled pass.

## Environment

- auto-ontology `2a24f5d`, Docker Compose, DuckDB connector.
- `duckdb` 1.5.5 in the backend image.

## Steps to reproduce

```python

c.sql("CREATE TABLE waves(wave_id VARCHAR); INSERT INTO waves VALUES ('astrolabe/agent_work/waves/W083-x')")

      "WHERE wave_count IN (SELECT wave_id FROM waves) LIMIT 1)")
```

Result:

```
BinderException: Binder Error: Cannot compare values of type INTEGER and VARCHAR in IN/ANY/ALL
clause - an explicit cast is required
```

## What we saw in our deployment

The compile made three keys from `INTEGER` columns to a `VARCHAR` column:

- `repositories.wave_count -> waves.wave_id`
- `repositories.protocol_era_from_wave -> waves.wave_id`
- `repositories.legacy_before_wave -> waves.wave_id`

These columns share no values. We disabled the three keys. Then the ingestion service restarted,
and the scheduled pass enabled `repositories.protocol_era_from_wave -> waves.wave_id` again.

## Expected result

The pass removes a key with no shared values, for all column types. If the check cannot run, the
log shows a WARNING, and the pass does not enable the key again.

## Possible fix

Use the native comparison first. If it fails, compare the values as text. Do not always cast to
text, because then values such as `1` and `1.0` do not compare as equal.

```python
text_sql = (
    f"SELECT COUNT(*) AS n FROM (SELECT {sc} FROM {source} "
    f"WHERE {sc} IS NOT NULL LIMIT 1) AS present "
    f"UNION ALL SELECT COUNT(*) FROM (SELECT {sc} FROM {source} "
    f"WHERE CAST({sc} AS VARCHAR) IN (SELECT CAST({tc} AS VARCHAR) FROM {target}) "
    f"LIMIT 1) AS shared"
)
try:
    try:
        result = connector.execute(sql)
    except Exception:
        result = connector.execute(text_sql)
    present, shared = (int(v) for v in result.iloc[:, 0])
except Exception:
    ...  # existing skip and log
```

We use this change as a local patch. On the next scheduled pass, the service wrote
`semantic FK removed, no shared values` to the log for the three keys.

`CAST(... AS VARCHAR)` is correct for DuckDB and PostgreSQL. Other connectors can need a different
text type.
