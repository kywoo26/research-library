NVIDIA Auto Ontology Shows That Text to SQL Was Never the Hard Part
The usual fix for unreliable data agents is a better model writing better SQL. NVIDIA's open-source Auto Ontology starts from the opposite premise: an agent can write flawless SQL against the right database and still return the wrong revenue number, because nobody told it which of three "revenue" columns finance actually means. The interesting part is not the agent. It is the 79,000 lines of Python built to tell the agent what the data means.

The promise: by the end of this issue you will understand how Auto Ontology compiles a semantic layer from database metadata, how its text-to-SQL graph validates and repairs queries, and which of its headline promises are enforced in code versus left to the agent.
The fence: we cover the Auto Ontology repository (1,354 commits since April 6, 2026, latest November 3), its MCP server and agent skills, and the separate evaluation harness (367 commits since June 15). For context we use Spider 2.0 and BEAVER, two enterprise text-to-SQL benchmarks. We did not deploy the stack or run the benchmark; this is a code and docs read plus our own analysis. The web UI is out of scope.
What It Actually Does
Auto Ontology sits between your databases and your agents. It connects to a warehouse, extracts the schema, and uses an LLM to compile a semantic layer: a catalog of business terms ("Customer", "Open Order", "Net Revenue"), each mapped to real columns and to reviewed SQL attributes (expressions like a margin or a rolling total), plus inferred foreign keys and relationships. Agents then ask it questions or read that layer directly.

The pitch has four verbs: Discover (generate an ontology from metadata), Ground (give agents trusted business meaning), Validate (check queries against certified definitions and lineage) and Learn (fold certified corrections back in). The first two are deep in the code. The second two are thinner than the README suggests.
The Architecture, Unpacked
Caption: Meaning is compiled once per table and stored; every question then flows through a validate, execute and repair loop that checks SQL against the live database, not against the catalog's certification flags.
Four design decisions matter most.
One: compile meaning from metadata. For each table, the LLM proposes foreign keys, describes columns and extracts a business term. Three workers run in parallel, but commits land in table order so the catalog stays deterministic.
Two: retrieval before generation. The graph first classifies intent, extracts entities and retrieves candidate tables, terms and SQL attributes from pgvector before any SQL is written. Reuse of a reviewed SQL attribute is preferred over inventing arithmetic.
Three: check against the data, not just the parser. Validation probes the database: are the filter literals real stored values, do joins follow valid paths, did a LIKE return nothing because of casing? Failures route to a reconstruct node with the error attached.
Four: read-only for agents, writes for humans. MCP exposes nine read tools by design. Edits to terms, attributes and certification go through the authenticated REST API and UI.
The Code, Annotated
First, the repair loop's budget, verbatim from auto_ontology/retrieval/text_to_sql/text_to_sql_graph.py (trimmed).
copy# Stop after seven reconstruction calls.
MAX_RECONSTRUCTION_ATTEMPTS = 7
def route_sql_validation(state: AgentState) -> str:
if state["decision"] == "unconstructable":
return "unconstructable"                    # e.g. unreachable DB: no rewrite can fix it
failed_attempt_count = len(state["path_state"].get("failed_attempts") or [])
if state["decision"] == "invalid_sql":
if failed_attempt_count >= MAX_RECONSTRUCTION_ATTEMPTS:
return "unconstructable"               # ← give up honestly instead of returning bad SQL
return "invalid_sql"                       # loop back to reconstruct_sql with the error
return "valid_sql"
Caption: With _MAX_FULL_PIPELINE_ATTEMPTS = 2 in main.py, one question can trigger up to 16 SQL generations. Reliability is bought with retries, and retries cost latency and tokens.
Second, how the validation chain is wired, from the same file (trimmed).
copygraph.add_conditional_edges("validate_sql_query", route_sql_validation, {
"valid_sql": pre_execute_target,           # → precheck_combined: literal, join-path, JSONB-path probes
"invalid_sql": "reconstruct_sql",
"unconstructable": "unconstructable_sql_response",
})
graph.add_conditional_edges("execute_sql_query", route_sql_execution, {
"valid_sql": "check_empty_like_result",    # empty result from a LIKE? maybe a casing problem
"invalid_sql": "reconstruct_sql",
"unconstructable": "unconstructable_sql_response",
})
graph.add_conditional_edges("check_value_repair", _make_soft_check_router("check_value_repair"), {
"valid_sql": "format_and_respond",
"invalid_sql": "reconstruct_sql",          # ← an empty answer is treated as a bug, not an answer
})
Caption: Successful execution is not the finish line. An empty result triggers value repair, because "no rows" is more often a wrong literal than a true zero.

It In Action
Input: "calculate the customer count by state province name", one of the eval harness's WideWorldImporters questions, asked through MCP ask_question against a Postgres copy of Microsoft's sample database.
Step one, ground. The agent calls search_terms for "customer" and "state province". The compiled layer maps "Customer" to sales.customers and finds that state names live in application.stateprovinces, two hops away through application.cities.
Step two, retrieve. Inside ask_question, intent classification routes to CALCULATION, entity extraction pulls "customer count" and "state province name", and candidate retrieval brings back the three tables with their inferred foreign keys.
Step three, construct and validate. The model writes SQL. The value check confirms no filter literals are needed; the join-path precheck confirms deliverycityid → cityid → stateprovinceid is a valid path, not a guess.
Step four, execute and respond. The query runs, returns rows, skips value repair because the result is not empty, and streams back over SSE with the SQL as provenance.
Output: the gold SQL from the eval dataset, which a correct run must match:
copyselect sp.stateprovincename as state_province_name, count(c.customerid) as customer_count
from sales.customers c
join application.cities ct on c.deliverycityid = ct.cityid
join application.stateprovinces sp on ct.stateprovinceid = sp.stateprovinceid
group by sp.stateprovincename
order by state_province_name desc;
Caption: The question and gold SQL come from the eval dataset; the step-by-step path is our illustration of how the graph handles it. A schema-only agent must guess that "state" means delivery city's province, not a billing address; the compiled join path is what removes that guess.

Why This Design Works, and What It Trades Away
Why it works. Enterprise text-to-SQL fails on meaning, not syntax. BEAVER's warehouses average 77.5 tables per database and 4 joins per query, and GPT-4o scored 0.0% there against 30.9% on BIRD. Spider 2.0's best agent solved 21.3% of enterprise tasks against 73.0% on BIRD. Compiling terms, relationships and reviewed SQL attributes in advance turns "find the right three tables among hundreds" into a retrieval problem, and database-backed validation catches the errors parsers cannot see.
What it trades away.
Compile cost scales with table count. Roughly three LLM calls per table with three workers: under an hour for a few hundred tables, more than a day for a 10,000-table lakehouse at our assumed call time.
Latency per question. Up to 16 SQL generations, plus retrieval and probes. The MCP server itself calls ask_question "far slower and more expensive" than the read tools.
Credentials at rest. Connections added through the UI are stored as plaintext JSON in Postgres unless Vault is fully configured; a partial Vault config falls back to plaintext with only a log warning.
A trusted internal port. The FastAPI service accepts an x-auto-ontology-user-id header without verifying it; the docs say that port must never be exposed publicly.
The default model is not the tested one. Defaults are Nemotron NIMs, but the eval harness is tested with Claude Opus 4.8 and Sonnet 5.5 through NVIDIA's inference gateway.
Technical Moats
Database-grounded repair. Literal checks against stored values, join-path probes, empty-LIKE detection and value repair are tedious, dialect-specific engineering across ten connectors. That is where most homegrown text-to-SQL agents quietly fail.
Honest evaluation tooling. The eval harness uses deterministic execution match (each benchmark's official rule), a schema-only control arm, and refuses to print a headline number if more than 5% of either arm's runs are broken.
Agent-ready packaging. A read-only MCP surface, signed agent skills synced to NVIDIA's skills catalog, and evals for the skills themselves.
NVIDIA distribution. Default wiring to NIM endpoints and Nemotron models, plus an optional KumoRFM predictive-query path in the same graph.
Insights
Insight One: "validate against certified definitions" is a workflow, not a guarantee. The README promises that agents "check generated queries against certified definitions and lineage." In the code, certification is a set of boolean flags (name_certified, description_certified, certified) that humans toggle through the API. The text-to-SQL graph never reads them; its validation checks SQL against the live database. The project's own management skill is blunt: "Current Auto Ontology certification fields are not an atomic review/promotion system... do not claim atomic certification, promotion, supersession, or rollback." The query skill then asks agents to verify grain, joins and lineage themselves. That is a sensible design, but "certified" governance currently lives in instructions to the agent, not in an enforced gate.
Insight Two: an accuracy layer launched without an accuracy number. The README sends readers to the benchmark repository for results. That repository publishes none: no BIRD, BEAVER or FDABench delta, only the tooling to compute one. Its README also warns that the BIRD configuration it calls "the reported BIRD delta" gives the ontology arm question-specific few-shot examples and value anchors that the schema-only control "cannot be given," so that delta "covers those inputs as well as the ontology grounding." Credit to NVIDIA for documenting this so candidly. But until a clean, ontology-only delta is published, "more reliable SQL" is a hypothesis, and enterprises should run the harness on their own schema before believing it.
Surprising Takeaway
The most instructive file in the project is a postmortem about a fake result. A 60-question BIRD run once scored 13.3% execution accuracy. Two thirds of its 1,126 HTTP calls had been rate-limit rejections, so 37 of 60 questions produced empty SQL that looked exactly like a weak model. NVIDIA's response was to make the comparison tool refuse to print a headline whenever more than 5% of an arm's runs are broken. For anyone evaluating agent accuracy, the lesson transfers directly: an evaluation that cannot distinguish "wrong" from "never ran" is measuring your rate limit, not your agent.
TL;DR For Engineers
Auto Ontology compiles business terms, SQL attributes and relationships from your schema with an LLM, stores them in Postgres and pgvector, and serves them to agents over read-only MCP, REST and CLI.
Its text-to-SQL graph validates against the live database (literals, join paths, empty results) with up to 7 reconstructions and 2 full retries per question.
"Certified definitions" are flags humans set; the query graph does not enforce them. Governance relies on agent skills.
No benchmark numbers are published. Run the eval harness's control-versus-ontology comparison on your own warehouse.
Configure Vault before adding connections, keep the FastAPI port private, and budget hours of compile time for large schemas.
Explain It Like I'm New
Companies keep their numbers in huge databases with thousands of tables and cryptic column names. Ask an AI assistant "what was revenue last quarter?" and it can write a database query in seconds. The problem is that "revenue" might live in five places, each meaning something slightly different, and only the finance team knows which one is official.
Auto Ontology tries to write that knowledge down once, for every AI tool to share. It reads the database's structure, then uses an AI model to build a dictionary of business terms: what "customer" means here, which tables connect to which, and how key numbers like margins are calculated.
When an assistant gets a question, it consults the dictionary first, like a new employee checking the company glossary before pulling a report. Then it writes the query, tests it against the real data, and fixes it if the results look wrong.
The idea is sound. The open questions are how much it actually improves accuracy, which NVIDIA has not yet published, and who keeps the dictionary correct as the business changes.
As companies deploy many AI agents at once, a shared, trusted definition of their data may matter more than any single smarter model.

Meaning Is the Product, Proof Is the Gap
Auto Ontology gets the diagnosis right. Enterprise data agents fail because they do not know what the data means, and NVIDIA has built a substantial system to compile that meaning, serve it safely to agents and test queries against real data before trusting them. Its evaluation tooling is unusually honest about how benchmarks lie. What is missing is the result those tools were built to produce, and an enforcement path for the "certified" definitions the pitch leans on. Use it as a semantic layer and a well-engineered repair loop today. Treat "governed, certified SQL" as a roadmap until the numbers and the gate ship.
