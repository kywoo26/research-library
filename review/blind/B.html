NVIDIA Auto Ontology 가 에이전트용 의미층을 만드는 방식과 enterprise 실증

Auto Ontology 는 NVIDIA 가 공개한 서비스로, 회사 DB 의 스키마와 샘플 값, 쿼리 기록을 LLM 으로 읽어 테이블마다 사업 용어와 조인 관계, 재사용할 SQL 식을 Postgres 에 만든다. 이 의미층(semantic layer)을 에이전트에게 읽기 전용 MCP 도구로 건넨다. 코드를 읽어 보면 LLM 이 쓴 초안을 정해진 규칙으로 정리하고, 확신이 없으면 비워 두는 데 공을 들였다. 그런데 README 가 약속한 '인증된 정의로 검증'은 답을 만드는 경로에 아직 들어가 있지 않다. 정확도가 얼마나 오르는지도 공개되지 않아서, enterprise 실증은 평가 방법을 내놓은 단계에 머문다.

NVIDIA Auto Ontology 팀의 오픈소스 저장소 NVIDIA/auto-ontology (커밋 c447003, 2026-11-06, v1.2.0 이후)와 평가 저장소 NVIDIA/auto-ontology-eval (ec41b2c)를 읽었다. 여기에 NVIDIA 의 발표 페이지와 The New Stack 인터뷰, Hacker News 스레드, 독립 리뷰 세 편, GitHub 이슈를 더했다.

Auto Ontology 는 DB 위에 사업 용어 사전을 컴파일해 에이전트에게 건네는 서비스다

라이브러리 하나보다는 다섯 개 서비스로 된 스택에 가깝다. 데이터 팀이 설치하고 원천 DB 를 연결하면, 컴파일이 의미층 초안을 만들고 사람이 그것을 고쳐 인증한다.

회사 DB 에 바로 붙은 에이전트는 SQL 을 잘 쓰더라도 '매출'이 어느 테이블의 어느 컬럼인지, 어떤 테이블끼리 조인해야 하는지를 매번 추측한다. NVIDIA 는 README 첫머리에서, 에이전트에게 데이터가 어디 있고 무슨 뜻이며 어떻게 써야 하는지를 알려 주는 context layer 가 필요하다고 말한다. Auto Ontology 는 이 층을 회사 메타데이터에서 자동으로 만들고, MCP, CLI, API 로 어떤 에이전트 harness 에든 내놓는다고 소개한다.

구성은 Next.js 웹 앱(3000), 질문에 답하는 FastAPI 백엔드(3001), 원천 DB 를 읽고 컴파일하는 ingestion 서비스(3002), MCP 서버(3003), 그리고 카탈로그와 의미층과 벡터를 함께 담는 Postgres 와 pgvector 다. 원천으로는 PostgreSQL, Snowflake, Databricks, ClickHouse, Trino 같은 엔진 열 가지를 읽는다. 모델은 기본으로 NVIDIA 가 호스팅하는 Nemotron 을 부르고, 역할마다 OpenAI 호환 엔드포인트로 바꿀 수 있다.

쓰는 사람은 둘로 나뉜다. 데이터 팀은 웹 화면에서 생성된 용어와 SQL 식을 고치고 인증한다. 에이전트는 MCP 도구로 용어를 찾아보고, 답할 수 있는 질문인지 미리 확인한 뒤, 질문을 던져 답과 SQL 과 행을 받는다.

코드의 출신도 눈여겨볼 만하다. NVIDIA 는 2026년 2월 이스라엘 스타트업 Illumex 를 인수했는데, Calcalist 는 Illumex 의 제품이 Generative Semantic Fabric(GSF)이라는 의미층 자동 생성 플랫폼이었다고 전한다. 이 저장소의 첫 커밋(2026-04-06)에 있는 README 는 'GSF' 라는 제목과 'generative semantic fabric' 이라는 한 줄이 전부다. Python 패키지 이름도 gsf 였다가 2026년 9월 23일 커밋에서 Auto Ontology 로 바뀌었다. 권한 코드의 주석에는 'Illumex 는 이렇게 했다'는 비교가 남아 있다. 그래서 Auto Ontology 는 Illumex 의 GSF 를 NVIDIA 스택 위로 옮긴 것으로 읽힌다. 이름까지 같아 정황은 강하지만, NVIDIA 가 이 계보를 직접 밝힌 문장은 찾지 못했으므로 해석으로 둔다.

Auto Ontology 의 온톨로지는 클래스 계층 없이 테이블마다 용어 하나를 둔다

온톨로지는 한 분야의 용어와 그 관계를 기계가 읽을 수 있게 적은 명세다. 같은 이름을 쓰는 세 전통과 나란히 놓으면 Auto Ontology 는 semantic layer 쪽에 가장 가깝다.

Stanford 의 Noy 와 McGuinness 가 쓴 입문서는 Gruber 의 정의를 빌려 온톨로지를 한 분야의 용어와 그 관계에 대한 명시적이고 형식적인 명세라고 설명한다. 그 중심은 클래스다. 와인이라는 클래스 아래에 레드 와인 같은 하위 클래스를 두고, 클래스마다 속성(slot)을 붙이고, 실제 와인 한 병은 그 클래스의 인스턴스가 된다. 이 계층이 있어서 '모든 보르도 와인은 와인이다' 같은 사실을 기계가 따라갈 수 있다.

기업 소프트웨어에서 같은 말은 조금 다르게 쓰인다. Palantir 는 Foundry 의 Ontology 를 조직의 디지털 트윈이라고 부르고, 객체와 속성과 링크 같은 의미 요소에 action 과 function 같은 동작 요소까지 함께 담는다. dbt 의 MetricFlow 는 YAML 로 semantic model 과 metric 을 사람이 적고, semantic model 의 entity 를 조인 키, 곧 모델 사이의 길로 본다.

Auto Ontology 의 컴파일 프롬프트는 LLM 에게 테이블 하나에 Term 하나를 강하게 권하고, IS_A, PART_OF, ROLE 관계는 제안하지 말라고 못 박는다. 그래서 만들어지는 것은 클래스 계층이 없는 사업 용어 목록이고, 용어 사이의 관계는 어떤 컬럼으로 조인되는가 하나뿐이다. 아래 표의 비교는 원천 문서들에 없는 것으로, 각 문서의 설명을 같은 항목에 맞춰 놓은 것이다.

Auto Ontology 를 OWL 식 지식 그래프로 기대하면 추론 기능이 없어 실망하고, dbt 식 semantic layer 를 LLM 이 대신 써 주는 도구로 보면 맞는 기대가 된다. semantic model 을 주고받는 열린 형식인 Apache Ossie 를 dbt MetricFlow 와 Auto Ontology 가 함께 지원한다는 점도 이 위치를 뒷받침한다.

NVIDIA 는 온톨로지를 RAG 다음 단계의 context layer 로 놓고, 권한은 데이터 플랫폼에 맡긴다

NVIDIA 가 말하는 온톨로지는 에이전트가 데이터를 쓰기 전에 물어야 할 여섯 질문에 답하는 층이다. 이 층을 기존 데이터 플랫폼 위에 얹는 부품으로 내놓았다.

NVIDIA 는 2026년 10월 21일 GTC Berlin 에서 Agent Knowledge Foundation 을 발표했다. 검색용 Nemotron Retriever 모델, 표 데이터 예측용 Kumo 모델, CUDA-X 데이터 처리 라이브러리에 Auto Ontology 를 묶은 오픈 부품 모음이다. NVIDIA 의 agentic AI 제품 부사장 Adel El Hallak 은 The New Stack 인터뷰에서 RAG 가 비슷한 텍스트 조각을 가져올 뿐이라서, 개념과 관계는 지식 그래프가 더 잘 표현한다고 말한다. 그가 든 예는 이동통신사의 tier 와 plan 이 같은 것이라는 사실인데, 사람에게는 쉽지만 LLM 은 이것을 헷갈린다고 한다.

NVIDIA 는 이 부품들이 기존 데이터 플랫폼, 온톨로지, 벡터 DB 와 함께 쓰이며 새 플랫폼을 통째로 들일 필요가 없다고 소개한다. El Hallak 은 ACL 과 데이터 접근은 자신이 생각하는 일이 아니라서 파트너가 필요하다고 말한다. 그래서 NVIDIA 는 의미를 정리하는 층만 열어서 내놓고, 누가 무엇을 볼 수 있는지는 Snowflake, Databricks, Palantir 같은 플랫폼에 맡긴다. 같은 기사는 Databricks 도 6월에 Genie Ontology 라는 context layer 를 내놓았다고 전한다. 데이터 플랫폼들도 같은 자리를 노리는 셈인데, Genie Ontology 의 문서는 열지 않아 비교하지 못했다.

README 는 이 층이 답해야 할 질문을 여섯 가지로 적는다. 아래 표는 각 질문을 Auto Ontology 의 어느 부분이 맡는지 코드에서 찾아 붙인 것이다. 그 부분이 실제로 약속만큼 동작하는지는 8장에서 따진다.

의미층은 Postgres 표 몇 개로 이루어진 그래프이고, 조인 관계가 그 뼈대다

처음에는 Neo4j 그래프 DB 에 담았지만 2026년 9월에 Postgres 로 옮겼다. 노드와 엣지를 모두 일반 테이블로 둔다.

README 퀵스타트의 질문 하나로 구조를 따라가 보자. 'Pennsylvania 에서 2015년 6월 어떤 상품의 매출'을 물으면 에이전트는 invoice line, invoice, customer, city, state province 순서로 테이블을 조인한다. 의미층에서 이 테이블들은 각각 Term 하나로 대표된다. 매출 금액이 담긴 extendedprice 컬럼은 Invoice Line 이라는 Term 의 속성으로 등록되고, 이 관계를 HAS_ATTRIBUTE 엣지가 적는다.

조인은 다른 엣지가 맡는다. invoicelines 테이블의 invoiceid 는 외래 키라서 컴파일이 속성으로 만들지 않는다. 대신 이 컬럼에서 invoices 테이블의 invoiceid 를 설명하는 속성으로 SEMANTIC_FK 엣지를 긋는다. 이 엣지를 이어 붙인 것이 답변 단계에서 프롬프트에 들어가는 조인 경로가 된다. 그래서 Auto Ontology 의 그래프에서 가장 많이 쓰이는 정보는 용어의 이름보다 어떤 컬럼으로 테이블을 잇는가 쪽이다.

인증은 Term 의 이름과 설명, 컬럼 속성, SQL 식 속성마다 붙은 참거짓 값 하나다. 사람이 화면에서 켜며, 기본값은 거짓이다. 컴파일이 만드는 Term 끼리는 이름이 겹칠 수 없어서, 다른 테이블이 이미 같은 이름을 가졌으면 새 Term 은 'Customer (db.schema.table)'처럼 테이블 경로를 붙인 이름을 받는다.

의미층은 ingestion 서비스가 네 단계로 만든다. 각 단계에서 판단은 LLM 이 하고, 그 판단을 저장하는 규칙은 코드가 쥔다.

① 테이블별 패스

Term 이 없는 테이블만 3개씩 병렬로. 1000행을 샘플링하고 LLM 이 외래 키 후보와 Term 을 제안한다

② semantic FK

선언된 외래 키는 그대로 쓰고, 없으면 벡터 검색 5개 중에서 LLM 이 고르며 모르면 비운다

③ SQL 식 제안

쿼리 기록에서 식을 뽑아 Term 마다 10개를 LLM 이 심사한다

④ bridge

외래 키로만 된 연결 테이블에 조인 SQL 식을 붙인다

취소되면 건너뛴다

Term 은 ①에서 이미 쓰였으므로 ②부터 ④는 오래 걸려도 필수가 아니라고 코드 주석이 설명한다

①에서 LLM 에게 맡기는 것은 '이 테이블이 무엇을 나타내는가'다. 코드는 그 답을 받아 이름 규칙에 맞지 않으면 테이블 이름으로 바꾸고, LLM 이 빠뜨린 컬럼은 첫 Term 에 붙인다. 테이블은 병렬로 처리하지만 저장은 테이블 이름 순서대로 줄을 세운다. 그래서 두 테이블이 같은 Term 이름을 원할 때 어느 쪽이 이름을 가져가는지가 실행마다 달라지지 않는다. 동시에 날아가는 LLM 요청은 6개로 묶는데, 테이블 단위와 테이블 안의 병렬이 곱해져 엔드포인트가 503 을 낸 적이 있어서라고 주석이 적는다.

②는 조인 관계를 만드는 단계라서 의미층에서 가장 중요하다. 선언된 외래 키가 없을 때 LLM 프롬프트는 확신이 없으면 null 을 돌려주라고 요구하고, LLM 이 고르지 못하면 실제 DB 에서 샘플 값이 겹치는 후보를 찾는다. 틀린 조인 하나가 이후 모든 답을 틀리게 만들 수 있으니, 비워 두는 쪽을 택한 설계다.

③은 회사가 실제로 쓰는 계산식을 쿼리 기록에서 건져 올리려는 단계다. 자주 쓰인 식부터 고르도록 사용량 점수를 매기게 되어 있는데, 이 점수 함수는 항상 0 을 돌려준다. 읽는 쪽 정규식과 저장하는 쪽 키 이름이 처음부터 달라서 점수가 매겨진 적이 없고, 메인테이너는 이것을 알려진 버그로 적어 둔 채 일부러 고치지 않았다. 고치면 어떤 SQL 식이 제안되는지가 바뀌어 제품 동작이 달라지기 때문이라고 한다. 지금은 Term 마다 쿼리 기록에서 먼저 나온 식 10개가 심사를 받는다.

의미층이 답에 들어가는 자리는 생성 단계의 프롬프트다. 후보로 고른 컬럼들을 잇는 조인 경로를 semantic FK 그래프에서 찾아 '의미 모델에서 나온 검증된 선택지'라는 제목 아래 넣고, 경로를 쓸 거면 중간 테이블을 빼지 말라고 지시한다. 서로 다른 DB 를 건너는 경로는 찾지 않는다. 그래서 같은 회사의 두 DB 에 흩어진 데이터를 한 쿼리로 묶는 일은 이 단계에서 일어나지 않는다.

검사는 기본 설정에 따라 많이 달라진다. 실행 전에 필터 값이 실제 컬럼 값에 있는지, 조인이 semantic FK 그래프에 있는 길인지, JSONB 키 경로가 실제로 있는지 확인하는 검사가 코드에 있지만 환경 변수로 켜야 돈다. .env.example 은 이 셋을 모두 false 로 적어 두었다. 코드 주석도 적듯이, 지어낸 조인은 문법이 맞고 행도 돌려주므로 오류 없이 틀린 값을 낸다. 기본 설정에서는 이것을 막는 검사가 꺼져 있고, 도는 것은 LLM 의 검증과 결과가 비었을 때만 도는 사후 수리다. 켜면 검증을 통과한 SQL 을 실행 전에 한 번 더 걸러 실패하면 다시 짓기로 보내는데, 일곱 번 상한과 따로 움직여서 실패가 다섯 번을 넘게 쌓이면 SQL 을 그대로 실행으로 넘긴다.

MCP 의 check_answerable 은 답변 전체를 돌리지 않고 질문이 의미층 안에 있는지 미리 재는 도구다. LLM 이 질문에서 엔티티를 뽑고, 각 엔티티와 거리 0.75 안의 컬럼 속성이 있는지 보고, 찾은 엔티티의 비율을 점수로 낸다. 비율 계산은 결정적이지만 엔티티를 뽑는 단계가 LLM 이라서, 같은 대상을 다르게 부르면 점수가 바뀐다. 저장소 이름을 넣은 질문이 낮은 점수를 받았다가 '저장소'라는 말을 붙이자 통과했다는 사용자 보고(이슈 #461)가 그 예다.

KumoRFM 예측 분기는 선택 사항이다. 코드는 KUMO_RFM_API_URL 이 있을 때만 이 분기를 그래프에 넣는데, README 는 KUMO_RFM_API_KEY 를 설정하면 예측 질문이 KumoRFM 으로 가고 연결된 테이블을 그 호스팅 서비스에 올린다고 적는다. 분기 안쪽 코드는 읽지 않았다.

그래서 재무 질문에는 검토된 정의만 쓰겠다는 규칙이 있는 조직이라면, 그 규칙은 배포하는 쪽이 만들어야 한다. 독립 리뷰를 쓴 Marginalia 의 필자도 1.1.0 코드를 읽고 같은 결론에 이르렀다. 이 리뷰와 별개로 커밋 c447003 에서 같은 검색을 다시 했고 결과가 같았다.

평가 방법은 공개되었다. 같은 모델에 스키마만 준 대조군과 Auto Ontology 를 쓴 처치군을 비교하는 설계인데, 그 결과값은 어디에도 실려 있지 않다.

enterprise 관점에서 Auto Ontology 의 의미는 두 가지로 볼 수 있다. 하나는 의미층의 첫 초안을 만드는 비용이다. 테이블 수백 개의 사업 이름과 조인 관계를 사람이 처음부터 쓰는 대신 LLM 이 초안을 쓰고 사람은 고치고 인증한다. NVIDIA 는 자사 테스트에서 온톨로지 생성 시간이 90% 줄었다고 하지만, 무엇을 기준으로 어떻게 쟀는지는 공개하지 않았다. 다른 하나는 에이전트가 데이터에 닿는 표면이다. 원시 스키마 대신 용어와 검토된 SQL 식을 거치게 하고, 사용자마다 자기 권한으로 MCP 를 쓰게 한다.

정확도를 보여 줄 장치는 평가 저장소에 있다. 같은 질문을 같은 모델에 두 번 묻는데, 대조군은 스키마 덤프만 받고 처치군은 Auto Ontology 의 에이전트가 의미층에서 문맥을 찾는다. 채점은 LLM 판정 없이 결과 행을 맞춰 본다. BIRD, BEAVER, FDABench, Wide World Importers, BIRD-Interact 를 지원한다. 그러나 README 에도 저장소에도 두 군의 결과 차이는 실려 있지 않다.

메인테이너가 PR 과 이슈에 남긴 수치는 있다. 2026년 10월의 한 PR 은 프롬프트 규칙을 넣기 전과 뒤를 BIRD dev 1,534문항으로 두 번씩 돌려 평균 76.34% 와 76.69% 를 얻었다고 적는다. 대조군 수치가 없어 Auto Ontology 가 몇 점을 더했는지는 알 수 없다. 같은 PR 은 같은 설정을 두 번 돌린 차이(12문항)가 두 설정의 차이(5.5문항)보다 커서 개선이라 부를 수 없다고도 적는다. 시간과 호출 수는 다른 이슈에 있다. 이전에 돌린 1,415문항 짝 비교에서 문항당 평균 생성 시간이 61.21초 대 9.27초, 모델 호출이 5.56회 대 1.00회였다고 메인테이너가 적었다. 시간으로 약 6.6배, 호출로 약 5.6배다. 이슈는 이 값이 예전 측정이라 지금 설치되는 릴리스를 대표하지 않는다고 덧붙인다. 또 이슈는 두 값을 'versus' 로만 잇는다. 같은 이슈가 목표를 'LLM-only 대비 몇 배'로 잡고 있어서 61.21초를 전체 파이프라인, 9.27초를 LLM 한 번으로 읽었는데, 이것은 해석이다. 그 LLM 한 번이 평가 저장소의 스키마만 준 대조군과 같은 설정인지도 알 수 없다.
